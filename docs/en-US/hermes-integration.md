# Atlas Evolution and the Hermes interfaces

**English** | [Português (Brasil)](../pt-BR/hermes-integration.md)

The integration uses the Hermes Agent 0.23.1 tree as its reference (commit `3b421578588243f920886e6fe79a6faa87ea026e`). This document lists what the plugin registers in Hermes, what it reads from a profile, which setting unlocks each capability, what it does not do and where further validation is most useful. [Official release](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.1) · [Public plugin API](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/website/docs/developer-guide/plugins/public-api.md)

The plugin relies on the published plugin API: it uses the `ctx` methods below and imports only the Hermes modules `hermes_constants`, `hermes_cli.config`, `agent.redact` (`redact_sensitive_text`) and `agent.secret_scope`, all listed in Hermes' public plugin API. Every optional `ctx` method is looked up first, so a host that lacks one still loads the plugin without that feature.

Some readings look at modules Hermes has already loaded in the process, without importing them. None of them is part of the published plugin API:

- the runtime guard takes the location of the `hermes_cli` package to know where the Hermes source is;
- the health radar reads the plugin list of Hermes' plugin manager (`hermes_cli.plugins`);
- the `hermes evolution` command reads the version of the loaded `hermes_cli` package for its update check;
- the turn hooks ask `agent.session_source` for the real origin of the running session (a Kanban worker runs with platform `cli`);
- `status` asks `hermes_cli.plugin_isolation` whether plugins run in a plugin host;
- the settings check asks `hermes_cli.managed_scope` for the administrator's managed configuration files;
- when a service runs without `hermes` on its `PATH`, the plugin looks for the `hermes` launcher next to the loaded `hermes_cli` package.

When a module is not loaded, that reading is skipped and the plugin falls back to what the hook payload says.

**Hermes' doctor checks** are the one place that uses Hermes internals directly: once a day, a separate short-lived process of Hermes' own Python imports `hermes_cli.doctor` and calls its `DOCTOR_CHECKS` ([Maintenance](maintenance.md#hermes-own-doctor-once-a-day)). Nothing of it is imported into the plugin's process. On a Hermes without `DOCTOR_CHECKS`, the checks do not run and the Environment screen says so.

| Prompt section `hermes-atlas-evolution.playbook`, up to 1,400 characters | `ctx.register_system_prompt_section` | `lessons` is `suggest` or `auto` |

Turning it on later needs `hermes gateway restart`; turning it off applies at once (the `check_fn` answers no). A toolset registered while off would read as "system dependency not met" in `hermes doctor` |
| Skill `hermes-atlas-evolution:evolution-review` | `ctx.register_skill` | when the host offers the method |

| Auxiliary task `evolution_reflector`, inheriting from `compression` | `ctx.register_auxiliary_task`, then `ctx.llm.complete_structured` | `reflector` is on when the plugin loads and the host offers both. Turned on later, it waits for `hermes gateway restart`; turned off, it stops at the next learning pass |
| Settings form with 14 options | `config_schema` in `plugin.yaml` | always; Hermes stores the values under `plugins.entries.hermes-atlas-evolution.settings` |

| Dashboard tab **Evolution** (`/evolution`) and its API: `GET /api/plugins/hermes-atlas-evolution/snapshot` and, for the logged-in owner, `POST .../decide` | `dashboard/manifest.json`, `dashboard/plugin_api.py` | the dashboard finds it by itself in the plugin's folder; Hermes refuses its API in a profile where the plugin is disabled ([The dashboard panel](#the-dashboard-panel)) |

| Background thread `hermes-atlas-evolution-clock`, a daemon that nudges the pass 2 minutes after the plugin loads and then every 10 minutes | none; stopped through `ctx.on_unload` | `autopilot_minutes` is not 0 and the host offers `on_unload` |

Most settings apply within a minute, without a restart ([The dashboard panel](#the-dashboard-panel), Settings). Four things are set when the plugin loads: which hooks are registered (`runtime_guard`, `tool_hints`), whether the agent tools are registered (`agent_tools`), the prompt section of a profile that loaded with lessons off, and the reflector's task. Each autopilot pass and each command read the settings again.

**Two copies in one profile.** When the profile also has an enabled copy under the old name `hermes-evolution`, the plugin registers nothing at all and logs a warning with the command that removes the old copy (`hermes plugins remove hermes-evolution`): both copies would observe the same turns and write to the same database.

**The version a process loaded.** A gateway or dashboard process that loads the plugin records the plugin version, its kind and when it started in the plugin's database, keyed by its process ID, so that `status` can flag one that still runs older code ([Status and owner notice](evolution-loop.md#status-and-owner-notice)).

## Hooks

The manifest declares the same 16 hooks, and a test compares the two lists.

| Hook | What the plugin does with it |
|---|---|
| `pre_tool_call` | Only with `runtime_guard` on. Runs the [runtime guard](#the-runtime-guard): vetoes agent terminal commands that would stop the gateway, delete what the running Hermes needs, or change this plugin's settings or switch it off. It also keeps, in memory only, a hash of the command of each terminal-like call, to tell later whether another plugin rewrote it. Not registered at all with the guard off, nor where Hermes runs plugins in a plugin host (see the guard). |
| `post_api_request` | Counts the call, its tokens and its duration per provider and model. |
| `api_request_error` | Counts every failed attempt, classified as rate limit, authentication, timeout, upstream or error. |
| `post_auxiliary_call` | Counts auxiliary calls and failures per task. |
| `post_tool_call` | Counts the tool outcome and its duration, classifies a failure into a signature (as `rewritten_command` when Hermes' `middleware_trace` names a change or the command that ran differs from the one `pre_tool_call` saw), counts a refused approval per session origin, counts the failure again when the turn served the owner (see [Who is served](evolution-loop.md#who-is-served)), times turns that use web research tools and, with the reflector on, keeps a scrubbed excerpt of an untemplated failure of the owner's own turns. |
| `transform_tool_result` | Adds the matching lesson to a failing result when `tool_hints` is `true`, which is off by default: Hermes keeps only the first plugin's change to a tool result. In a session that does not serve the owner, only template lessons are added. Registered only while `tool_hints` is on and lessons are not off. |
| `pre_llm_call` | Works out the turn's surface and whether it serves the owner (a delegated child through its parent's `parent_session_id`), starts the turn timer, classifies owner feedback in memory and attributes an owner correction to the skills of the previous turn. Returns no context, except once per chat session: when the sender turns out to be the owner (`owner_sender_ids`) in a direct chat (a DM, never a group, thread or topic) whose prompt this process built with template lessons only, it returns the lessons that prompt left out (at most 5 lines and 900 characters), which Hermes adds to that turn's user message. Never in a chat someone else wrote in. |
| `post_llm_call` | Closes the timing of a research turn and nudges the autopilot. |
| `on_session_end` | Records the outcome and duration of the turn and the outcome of each skill it loaded, and nudges the autopilot. |
| `on_skill_lifecycle` | Counts skill loads, patches and other lifecycle events, and attaches a loaded skill to its turn. |
| `subagent_start` | Remembers, in memory only, which session delegated each child, so the child serves whoever its parent served, its prompt included. |
| `post_compaction` | Counts the compaction, with the tokens before and after when Hermes reports them, for the radar's compaction reading and the digest, and carries what the plugin knows about the session (who it served, the parent of a child) to the id the compaction gives it. |
| `on_session_finalize` | Returns at most one short notice per UTC day about decisions waiting, only for a session of the owner's local surfaces (CLI, TUI, Desktop) that is not a subagent. Hermes 0.23.1 shows this text only when the classic CLI exits (`shutdown`) or starts a new session (`session_boundary`) and when the TUI or Desktop closes a session (no reason given); for any other reason the plugin returns nothing and the day's notice is not spent; the waiting decisions show in `status`, in the digest and in the dashboard panel. |
| `on_session_reset` | `/new` or `/reset` ended a session: drops what the plugin keeps in memory about the session that ended (who it served, its delegated children, whether its prompt was counted, the owner's lessons and the tool hints given, the last turn's skills and words). |
| `on_session_delete` | A session was deleted or archived: drops the same, for each session named. |
| `on_kanban_dispatch_tick` | Nudges the autopilot. Hermes fires it once per Kanban dispatcher tick, every 60 seconds by default, for the gateway's own profile, and only where the dispatcher runs inside the gateway (`kanban.dispatch_in_gateway`). The clock thread covers the other profiles a gateway serves. |

A nudge only compares two clocks; the pass itself runs in the autopilot thread (see [The autopilot](evolution-loop.md#the-autopilot)). Every callback fails open: a hook never raises into a turn, and a failure is logged at most once per event type. Hook writes go through one database connection per process and profile. While the database is busy an update waits in a queue of up to 512 entries and is written with the next event or when the plugin unloads. Overflow is counted and reported as `dropped_events`. The prompt section only reads the database and counts its display through the same queue.

On the development machine a hook event takes about 0.1 ms. This is a measurement on one machine, not a guarantee.

## The runtime guard

With `runtime_guard` on (the default), the plugin's `pre_tool_call` callback runs the guard (`guard`). Hermes calls it before every tool call of the agent, and a block directive replaces the call: its message becomes the tool result the agent reads. The guard looks at the `command` argument of terminal-like tools (`terminal`, `shell`, `bash`, `run_command`, `execute_command`), with their `workdir`, and at the `data` that `process_manage` `write` or `submit` sends to a background process, which is often a shell. It vetoes three kinds of command.

| Kind | Vetoed | What the agent is told |
|---|---|---|
| `gateway_stop` | Linux: `systemctl` with `restart`, `stop`, `kill`, `try-restart`, `reload-or-restart`, `try-reload-or-restart`, `condrestart`, `force-reload`, or `disable --now`, on a `hermes-gateway` unit, including a profile's `hermes-gateway-<profile>`, a custom home's `hermes-gateway-<hash>`, an instance and the `.service` suffix; `service` with `restart` or `stop` on that unit. macOS: `launchctl` `kickstart -k`, `stop`, `bootout`, `unload`, `remove` or `kill` on the LaunchAgent `ai.hermes.gateway` or `ai.hermes.gateway-<suffix>`, named bare, as `gui/<uid>/<label>` or by its plist. Windows: `sc` or `net` `stop`, PowerShell `Stop-Service`, `Restart-Service`, `Suspend-Service` and `Stop-ScheduledTask`, and `schtasks /End`, on the service or task `Hermes_Gateway` or `Hermes_Gateway_<suffix>`. A command word with a glob (`sys*ctl`, `/usr/bin/sys?ctl`) is matched against the commands it could expand to, and a busybox or toybox applet (`busybox kill`) counts as that command. Also `condstop`, `freeze` and `mask --now`, systemctl options with a value before the action (`--job-mode replace`, `-s KILL`, `-t service`, `-M`, `-H`), a unit given as a glob (`'hermes-gateway*'`) and, when the command names Hermes anywhere, a unit the shell fills in (`$U`, `xargs`); and systemd's `RestartUnit`, `StopUnit` or `KillUnit` called on a Hermes unit through `busctl`, `dbus-send` or `gdbus`. Anywhere: `pkill`, `killall`, `taskkill` or `Stop-Process` with an argument that contains hermes, and `pkill` or `killall` whose pattern selects the gateway process itself (`pkill -f python`, `killall python3`, `pkill -f 'gateway run'`), matched against the gateway's own name and command line; `kill` of `$PPID` (the agent's shell is a child of Hermes) or of `-1`; `kill` whose process ids the shell fills in, in a command that looks Hermes up (`kill $(pgrep -f hermes)`, `pgrep -f hermes_cli \| xargs kill`, ``kill `pidof hermes` ``, `kill $(cat ~/.hermes/gateway.pid)`) or selects the gateway process itself (`kill $(pgrep -f 'gateway run')`, `ps aux \| awk '/gateway run/{print $2}' \| xargs kill`): `pgrep` is matched against the gateway's command line with `-f` or `--full` and against its process name without it (`-x` exact), `pidof` against its exact name, and `grep`, `rg` or `awk '/re/{...}'` only when they read a process list from a pipe (no file operand). Option values (`-u root`, `-m1`) are not patterns, and a pattern that matches the empty string is ignored, so `kill $(cat app.pid)`, `kill $(pgrep -u root worker)` and `kill $(grep -o '[0-9]*' app.pid)` pass; `hermes gateway stop`, `restart` and `uninstall`, `start --all`, `run --replace` and `install --force`, with global options anywhere and a group or action the shell fills in (`hermes $G restart`). The `hermes` command counts under every name it runs by: `hermes-agent`, `python -m hermes_cli.main` (the gateway unit's own form), `python -m hermes_cli`, a virtual environment's `python .../bin/hermes`, `uv run hermes`, `uvx hermes` and `npx hermes` | the command would cut off the turns in progress, this one included; do not retry it in another form; tell the owner that a restart is needed and why; the owner runs `hermes gateway restart` from their own terminal, which lists the turns still running and asks before interrupting them |
| `runtime_removal` | `rm`, `rmdir`, `unlink`, `shred`, `mv` (its sources, also with `-t` or `--target-directory`), and on Windows `del`, `erase`, `rd`, `Remove-Item` and `Move-Item`, or `find` with `-delete` or with `-exec` running `rm`, aimed at a protected path, at a folder that contains one, or with a glob that matches one, after the shell's brace expansion (`mv .hermes{,.old}`, run in the home folder); anything inside a protected tree (`rm -rf venv/lib`, `rm -rf venv/*`); an `xargs rm` fed from a command that names a protected path (`ls -d <path> \| xargs rm -rf`); and `hermes profile delete`, which deletes a profile and stops its gateway. Whatever the verb: a write, truncation or attribute change inside the running interpreter or a protected tree (`truncate`, `dd of=`, `tee`, a redirect, `chmod`, `chown`, `chgrp`, `ln -sf`, `rsync --delete`, and `cp`, `mv` or `install` into it), and `chmod`, `chown`, `chgrp`, `ln` or `rsync --delete` aimed at the profile's folder, Hermes' root or a folder above them or above a protected tree, also after a `cd` or through a literal `VAR=` assignment earlier in the command (plain copies stay allowed: see below the table) | the command would delete or move that path, and Hermes would stop working until someone repairs it by hand; removing it is for the owner, from their own terminal, with Hermes stopped |
| `plugin_settings` | `hermes config set` or `unset` of the `plugins` section (the plugins Hermes enables, disables or isolates) and of `plugins.entries.hermes-atlas-evolution` (or its old name `hermes-evolution`), but not of another plugin's `plugins.entries.<id>`; `hermes config edit`; `hermes plugins disable`, `remove`, `rm`, `uninstall` or `trust` of `hermes-atlas-evolution`, and `hermes plugins install` of a source with that name, which would replace its code; removing or moving the plugin's own folder or anything in it; a command that writes a Hermes `config.yaml` (`sed -i`, `perl -i`, `yq -i`, a redirect, `cp`, `tee`, a Python one-liner that dumps or writes it) and names the plugins section, this plugin or one of its trust settings; a command that replaces a Hermes `config.yaml`, the profile's, the root's or another profile's (`cp`, `mv` or `install` over it, `ln`, `truncate`, `dd`, `tee`, a `>` redirect), even when it names no plugin setting, while appending to it with `>>` counts only when the command names the plugin's settings; and any write, truncation or attribute change inside the plugin's own folder. Global options that take a value, such as `-p <profile>`, are read wherever they sit, as Hermes reads them, and a word the shell fills in at the key, action or name (`$VAR`, `$'...'`, a command substitution) counts as such a change | the command would change who counts as the owner or the plugin's protections, or switch the plugin off; only the owner decides that, from their own terminal; do not retry it in another form; tell the owner what you wanted to change and why |

Ordinary work stays allowed: a plain write or copy into the home folder, into the Hermes root or into a shared folder such as `/usr/local/lib` (`cp report.pdf` into your home, `cp notes.md` into `.hermes/`) is never vetoed; only what changes the inside of a protected tree, or the permissions, owner, links or contents of a folder above one, is.

The protected paths are those the running Hermes needs: the prefixes of the running Python interpreter and its environment, the base interpreter a virtual environment points at (the `home` line of its `pyvenv.cfg` and `sys._base_executable`), the Hermes source (the folder that holds the `hermes_cli` package), the Hermes root and this profile. Each is protected both as written and as resolved, so a link counts under either name: uv's `cpython-3.11-...` link to `cpython-3.11.16-...`, or a `~/.hermes` that points to another disk. A path with fewer than three components, such as `/usr`, is never added to the list, so a system interpreter whose prefix is `/usr` is not covered.

For most of them only the path itself and the folders above it are protected. The **protected trees** are protected inside as well, because deleting any part of them stops Hermes: the virtual environment Hermes runs in, a Python runtime folder of its own (one whose name says python, such as `~/.hermes/tools/python-3.14...`), the standard library, and the Python packages and virtual environments at the top of the Hermes source (`hermes_cli`, `gateway`, `agent`, `venv`, ...). A shared prefix such as `/usr/local` is never a tree; only the standard library inside it is. The inside of the Hermes root and of the profile stays open to the agent, which works there. The plugin's own folder is protected inside too, as a `plugin_settings` veto: removing or changing it switches the plugin off.

How a command is read:

- It is split at `;`, `&&`, `||`, `|`, `&`, parentheses and line breaks, and in each part only the command word counts, after the shell words that open or negate a compound command (`if`, `then`, `elif`, `else`, `while`, `until`, `do`, `!`, `{`, `coproc`), variable assignments, the applet multiplexers `busybox` and `toybox`, and wrappers such as `sudo` (with its long options), `env`, `nohup`, `timeout`, `nice`, `ionice`, `stdbuf`, `exec`, `command`, `builtin`, `time`, `chrt`, `doas`, `setsid`, `systemd-run` with its options (timers such as `--on-active 30` included), `runuser`, `watch`, `flock`, `xargs`, `taskset`, `unshare`, `nsenter`, `chroot`, `strace`, `ltrace`, `uv run`, `uvx`, `pipx run`, `npx` and `rtk run` (or `rtk err` and the other `rtk` subcommands that run a command). The words `xargs` adds from its input count as words the shell fills in. A literal assignment earlier in the same command (`X=systemctl`, `export X=~/.hermes`, also with `declare`, `local`, `typeset` or `readonly`) is put in for `$X` and `${X}` after it; any other variable stays unknown. A command word with a glob is matched against the commands the guard reasons about. A command named inside another command's arguments, such as in `echo`, is not a command.
- A command given as one string is read, up to 8 levels deep: to a shell (`bash`, `sh`, `zsh`, `dash`, `ksh`) with `-c` or a flag group that contains it, such as `-lc` or `-ec`, to `su`, `runuser`, `script` or `flock` with `-c`, `--command` or `--command=` (`script -qc` too), to `eval`, to PowerShell (`powershell`, `pwsh`) with `-Command` or `-c`, to `cmd` with `/c`, to `env` with `-S` or `--split-string`, and to `watch`, which runs its operands as a shell string. So are `$(...)` and `` `...` `` command substitutions, also inside double quotes, where they still run; the command `find -exec` runs; the command given to `ssh localhost` (or `127.0.0.1`, `::1`); what a shell reads as its script on standard input: its here-documents (`bash <<EOF`), a here-string (`<<<'…'`, also glued to the shell), the words of an `echo` or `printf` piped into it, and a here-document a `cat` pipes into it (`cat <<EOF | bash`); and the string literals of an interpreter's inline program (`python -c`, `perl -e`, `ruby -e`, `node -e`, `php -r`), each alone and all of them joined, which is how `subprocess.run(['systemctl', ...])` reads. A command run from a script file, or through `ssh` to another host, is not looked into.
- Other here-document bodies are data written somewhere, not commands run now, so they are ignored, and so are shell comments.
- `~`, `~<the owner's user name>`, `$HOME` and `$HERMES_HOME` (this profile) are expanded at the start of a path, also as `${NAME}`, `${NAME:?...}` and `${NAME:-...}`, and so are `%USERPROFILE%`, `%LOCALAPPDATA%`, `%APPDATA%` and their `$NAME` and `$env:NAME` forms when they are set. On Windows, `C:\x`, `C:/x` and Git Bash's `/c/x` are the same path, compared without case. A relative path is taken from the terminal tool's `workdir`, or from a `cd` earlier in the same command, when that folder is known; otherwise it is not checked, nor is one that starts with another variable.
- Any doubt lets the command through: a quote without its pair, a tool that is not terminal-like. A long command is read on its first 20,000 characters, after its comments and here-document bodies are cut, so padding cannot push a command past the check. The work on commands inside commands has one budget (2,000 checks): any command up to 20,000 characters takes under 0.7 seconds, far below the 30 seconds after which Hermes blocks a tool.

The check is a pure function over the command: it reads and writes nothing, and its input is bounded. The callback never raises, because Hermes treats a `pre_tool_call` that fails or times out as a veto: an internal failure lets the command through and is logged, once per process, with its details. Each veto is counted by kind in `guard_daily` (the command is not stored), and `hermes -p <profile> evolution status` and the digest show the counts. The message follows the plugin's language. The operator's own terminal is not affected.

The guard was checked against about 350 commands written to get around it. The ones it still lets through are host-wide commands (`reboot`, `systemctl isolate`), text piped into a shell or an interpreter from a file, a download or another program, encoded text decoded into one, another user's or a relative path it cannot place, and commands scheduled through `at` or a script file. Those are for Hermes' own approval policy.

This guard exists because, on a real server, the agent restarted its own gateway with `systemctl` 13 times in a week, 12 of them from one chat on one day, cutting the turns in progress, and once deleted the Python runtime the gateway unit used, which kept Hermes down for about an hour. The same history also had a restart scheduled through `systemd-run`, which is why the guard looks at the command behind the wrappers above. The agent's `hermes gateway restart` is vetoed too: without a terminal, Hermes 0.23.1 refuses to restart while sessions are running, and its `--yes` would interrupt them, so the restart is left to the owner. The guard is a safety net for these cases, not a sandbox: Hermes' own approval policy for terminal commands still applies.

**Guard off or plugin host.** With `runtime_guard: false`, or where Hermes runs plugins in a separate host process (`plugins.isolation: host`), the plugin registers no `pre_tool_call` at all, so neither the guard nor the check for a command another plugin rewrote runs there (Hermes' middleware trace still marks its own rewrites). Every `pre_tool_call` is then a call into the host, and Hermes blocks a tool whose `pre_tool_call` fails: a host that crashed would block every tool of the profile. `status` says the guard is off for that reason.

## The dashboard panel

The plugin adds a tab, **Evolution**, to the Hermes dashboard and to Hermes Desktop, under Plugins in the sidebar. Hermes finds it by itself in the plugin's `dashboard/` folder (`manifest.json`, a script with no build step, a stylesheet that follows the dashboard's theme tokens, and `plugin_api.py`); nothing has to be configured. It works for the dashboard's own profile and for the other profiles selected in it.

| Tab | Shows, and lets you do |
|---|---|
| Overview | Active lessons, what waits for your decision, tool calls and turns with their error rates, guard vetoes in 7 days and the last pass. Each lesson that waits, with its exact text, **Approve** and **Reject**, and **Approve all**, which first lists every sentence it will approve; a lesson the agent proposed is left out of it and is approved on its own |
| Lessons | Every lesson with its status, origin, tool, sentence and measured effect; approve or reject one that waits, retire an active one, reactivate a retired one |
| Proposals | Open proposals grouped as changes the plugin applies, lessons, changes you apply and observations, each with its risk, what was seen, what to do, what applying it does and its undo. **Apply now** applies one change with Hermes' own command, and **Apply all** applies every change that may go in a batch (never turning a plugin off or moving a cache); **Dismiss** hides an observation for 30 days, and it comes back only if the situation is still there; a lesson is approved or rejected. A change the plugin does not apply shows its command, with Copy, for you to run in your terminal |
| Health | Hermes' health and the operating system: the gateway, free disk, memory, swap, the session database, old tool versions, updates waiting and a reboot the system waits for; what needs attention, and the terminal menu's command for the actions ([Maintenance](maintenance.md)) |
| Environment | For each profile in use, the last check by Hermes' own doctor (problems, warnings and when), then every profile of this Hermes and what to fix across them, each with its command ([The environment](evolution-loop.md#the-environment)) |
| Settings | Every option of the settings form, with **Apply the recommended setup** (lessons on `auto`, reflector on, and the chat channels that are yours by construction), and **Who is you in chats**: each channel of the last 30 days with its senders, the suggested ones marked |
| History | Every decision, from the terminal and the panel, newest first, with **Undo** |
| Digest | The digest of `hermes -p <profile> evolution report`, for 7, 14 or 30 days |
| Status | The page of `hermes -p <profile> evolution status` |

**Who may decide.** Every request is authenticated by the dashboard first. A decision is then accepted only from a logged-in owner (a password or OAuth login, which Hermes turns on when `dashboard.public_url` is a public address) or from the grant Hermes Desktop sends, and never from a request that carries the dashboard's session token in any form (its header, `?token=` or `Authorization: Bearer`, Hermes' legacy form). How the plugin knows depends on where Hermes runs its routes:

- **The dashboard's own profile** runs in the dashboard process, behind Hermes' login gate. The panel accepts the session the gate verified (`request.state.session`), except one verified by the deployment session token (`HERMES_DASHBOARD_SESSION_TOKEN`), which is not a person's login. On a host that publishes no verified session, the login cookie counts by its name, in each form Hermes gives it: `hermes_session_at` over HTTP, `__Host-hermes_session_at` over HTTPS (a public address behind a proxy), `__Secure-hermes_session_at` under a path prefix, with `_<gateway>` on the gateway's Webapp.
- **Every other profile** selected in the dashboard runs its own copy of the plugin in that profile's plugin host. Hermes forwards the request there without any credential (no cookie, no token), with a verdict that is the same for a login and for the open dashboard's token, and without the variables that would tell how the dashboard admits people. So the plugin host never decides: it answers read-only, with the reason `other_profile`. The panel then asks the plugin in the dashboard's own process, with `?profile=current` (the dashboard's profile, for Hermes) and `target=<the profile on screen>`, and that process reads and decides for the profile under the same login rule as above, when Atlas Evolution is installed and enabled there (`plugins.enabled` in its `config.yaml`); a name that is not a profile of this Hermes, a link or a path outside it is refused. This needs the plugin enabled in the dashboard's own profile too; without it, the other profiles stay read-only in the panel and are decided in the terminal menu.

A dashboard without a login hands its session token to anyone who loads the page, the agent's terminal included, so there the panel stays read-only, says why, and shows the command of the terminal menu instead; the snapshot then leaves out the sender ids of the chat channels and the text of lessons written by you, the reflector or the agent (lessons, waiting lessons, proposals, the digest), which reads "(text hidden: read it in your terminal)", as the terminal does in an agent's shell. An unexpected error answers `unexpected` with a plain sentence; the details go only to the dashboard's log. A decision also needs the header `X-Atlas-Evolution: 1`, which a page of another site cannot send without the browser asking the dashboard first. The runtime guard vetoes the agent's commands that call the decision route, however the address is spelled (`%`-escapes, `/./`, `/../`, quotes, a name the shell fills in). A value the plugin would not use as given (`autopilot_minutes: 5`, a sender id that is not text) is refused before anything is written, and a broken `settings.json` never takes the panel down: it falls back as the gateway does and the panel says so.

**What a decision does.** The same code decides from the terminal and from the panel (`decisions.py`), and every decision goes to a log (`decision_log`: ids, states, setting values and fingerprints, never lesson or memory text). **Approve all** sends the exact list of lessons shown, each with a fingerprint of its sentence, and approves only those still waiting with that sentence. **Undo** takes a decision back only while what it changed is still as it left it: an approval goes back to waiting and its measurement is dropped, a retirement is undone by activating the lesson again, a setting gets its value back, and an entry taken out of Hermes' memory is put back from the copy kept (only from the terminal menu or the panel's undo).

**Settings.** The panel and the terminal menu write them with Hermes' own public command, `hermes --profile <name> config set plugins.entries.hermes-atlas-evolution.settings.<key> <value>` (Hermes checks the key, takes its configuration lock and writes atomically), into the profile's `config.yaml`, after checking each value with the plugin's own rules. The running gateway picks a change up within a minute, without a restart: every hook and the plugin's clock compare the modification times of `config.yaml` and `settings.json` at most every 30 seconds and read them again only when they changed. Who counts as the owner, the lessons mode, switching the reflector off and its limit, the language, owner signals, the slow-turn threshold, the autopilot interval and `fleet_managed` apply at once. A few settings wait for `hermes gateway restart` (in the terminal: the next session): `runtime_guard` and `tool_hints`, which decide which hooks Hermes calls, `agent_tools` when it is turned on (turning it off applies at once), and `reflector` when it is turned on after a load with it off (its auxiliary task is registered at load). The panel and `status` list the waiting ones, `agent_tools` excepted, compared with what this load registered. A profile that loaded with lessons off has no prompt section at all until the next load either. Hermes also reloads plugins in a running gateway when one is enabled, disabled or updated from Desktop.

The API has two routes: `GET /api/plugins/hermes-atlas-evolution/snapshot?days=1..35&lang=en|pt` and `POST /api/plugins/hermes-atlas-evolution/decide`. They run in the dashboard's worker threads, so the store never holds up its event loop; while the store is busy they answer 503 and the panel says so. The panel speaks English or Brazilian Portuguese: the plugin's `language` setting when it is `en` or `pt`; with `auto`, the language chosen for the profile in Hermes (`HERMES_LANGUAGE` or `display.language`), then the dashboard's language, then the machine's locale, then English. Everything, lesson text included, is rendered as text, never as markup. Under `plugins.isolation: host` Hermes serves the routes through the plugin host.

## The reflector and Hermes' model access

The reflector is the only part of the plugin that involves a model, and it is on by default. When `reflector` is on at load time, the plugin registers the auxiliary task `evolution_reflector` with `inherit_from="compression"`: it starts from the compression task's timeout and other settings, and takes its provider and model too only once you grant it (`plugins.entries.hermes-atlas-evolution.llm.allow_task_override: true`; without it Hermes' default route for auxiliary tasks applies). You can give it its own provider and model in `auxiliary.evolution_reflector` of the profile configuration. A pass run inside Hermes (by the autopilot, `hermes -p <profile> evolution learn` or the weekly recipe) then calls `ctx.llm.complete_structured` with that task, a JSON schema, at most 300 output tokens and a 60-second timeout. Hermes resolves the provider, sends the request and accounts for it; the plugin opens no connection, and no transaction of the plugin stays open during the call. When the host offers no plugin model access, or while `lessons` is `off`, the loop runs without drafts. Three real calls through Hermes in production (provider DeepSeek, about 600 tokens and about 2 seconds each) produced three drafts in Portuguese. What is sent and what is accepted back is described in [The evolution loop](evolution-loop.md#the-reflector).

Failures only other people caused wait for approval. The reflector drafts lessons that wait for approval. The runtime guard vetoes the commands described above. Only `manual` counts from `settings.json`, and a `config.yaml` the plugin cannot read means `manual` too. |

## What the plugin does not do in Hermes

- It never archives, rolls back, edits or creates a skill. The only change to skills is `hermes curator lock` (and `unlock` to undo it): on your key, or by itself in Auto mode for a skill the curator keeps rewriting.
- It never changes a Hermes setting other than its own (`plugins.entries.hermes-atlas-evolution.settings.*`, through `hermes config set`, when you change one). A proposal that would change another setting is printed as a `hermes config` command.
- Hermes' memory: it only removes an entry said, the very same text, in both `MEMORY.md` and `USER.md` (by itself in Assist and Auto mode, never the last copy), or the entry you choose, after keeping a copy of the file; it reads nothing else of it beyond the structure counts above.
- It does not rewrite a prompt that is already in use or change tool arguments. The only changes to agent-visible content are the lessons at the start of a session, the sentence appended to a failing tool result with `tool_hints` on, and, once per direct chat whose sender is the owner, the lessons that chat's prompt left out, added to the owner's message.
- It does not stop, restart or kill anything. The one service it starts is the gateway's, right after repairing it, and only when no gateway of this Hermes runs. Outside Hermes' configuration, the one file it edits is that service's file (a copy kept, undone with `care undo-gateway`). The runtime guard only refuses a command; it never runs one.
- It does not write to Hermes' history: `state.db` and the logs are opened read-only.
- Other profiles: in Auto mode, from the one profile that looks after the whole Hermes, it installs itself in a profile used in the last 7 days that never had it, by itself only by its catalog name (never where you removed it: its data folder `evolution/evolution.sqlite3` stays and marks it), and moves a failed install's folder (`plugins/.install-*`) to its trash. On your key only, one proposal at a time: turning off one of two plugins, and moving a package cache that rebuilds itself (`uv`, `pnpm`, `npm`, `pip`, `yarn`, `huggingface`, `piper-voices`) to its trash. Any other cache folder (the browser's logins, conversation attachments, generated images…) is never moved: the item gives a `du` command to look inside. Everything else there (removing or updating a plugin, this one included, archiving a skill, pruning rollback snapshots) is a command for you. Before any change it reads that profile again from disk, and for a doctor finding it runs that check again. In a profile with `fleet_managed` off it changes nothing by itself.
- It does not approve, deny or route around Hermes approvals, and it never turns a refused approval into advice.
- It registers no middleware, provider, memory provider, redaction pattern or locale, and overrides nothing in Hermes core.
- The only Cron job it creates is the weekly digest, on your key (`schedule-digest`), as a script with no agent; the recipe of `report --schedule-spec` is printed for you. It creates no Kanban card.
- It sends no telemetry and has no network access of its own. It never updates itself: new code comes only from Hermes' own `plugins update`, "Update all" or `plugins.auto_apply`. Hermes downloads the plugin when you run `evolution update` or `install.sh` and when Auto mode installs it in another profile by its catalog name, and `hermes doctor` (your click) calls the providers. The daily doctor checks skip every check that uses the network. A model is called only by the reflector, through Hermes.
- It does not let the agent decide: decisions refuse to run in an agent's shell.

## Installation notes

- **From the Hermes plugin catalog.** `hermes plugins install hermes-atlas-evolution`, then `hermes plugins enable hermes-atlas-evolution`, in the default profile; `hermes -p <profile> plugins install hermes-atlas-evolution` and `hermes -p <profile> plugins enable hermes-atlas-evolution` in a named one. Hermes installs the catalog's reviewed pin, and `plugins update` moves it to the next reviewed pin.
- **From GitHub.** `hermes plugins install sesantanajr/hermes-atlas-evolution --enable` in the default profile, `hermes -p <profile> plugins install sesantanajr/hermes-atlas-evolution --enable` in a named one. Installing with `--enable` makes a running gateway load the plugin at once; its prompt section applies from the next session. Check with `hermes plugins doctor --ci hermes-atlas-evolution` and `hermes -p <profile> evolution status`.
- **Every profile you use.** Hermes loads plugins per profile, even when one gateway serves several profiles. From a clone of this repository, `sh install.sh --all --install-missing` (add `--catalog` to install by catalog name) runs Hermes' own commands in every profile. By hand, for every named profile: `for p in $(ls ~/.hermes/profiles); do hermes -p "$p" plugins install sesantanajr/hermes-atlas-evolution --enable; done`, plus the command for the default profile. `hermes -p <profile> evolution status` lists every profile of the same Hermes root, with the install command for each busy one that does not have the plugin.
- **Updating.** `hermes plugins update hermes-atlas-evolution`, with `-p <profile>` for each named profile, fetches the new code, but a running gateway keeps the code it loaded: Hermes reloads a running gateway on install, enable and disable, and on an update applied from Hermes Desktop, the dashboard or `/plugins update` in a chat, not on this command-line update. Finish with `hermes gateway restart`; when something is still running, it lists it and asks `Interrupt them and restart the gateway? [y/N]`. `status` flags a gateway or dashboard process that still runs an older version, on POSIX systems.
- **Old name.** If a profile still has the plugin under its old name `hermes-evolution`, run `hermes plugins remove hermes-evolution` and install `sesantanajr/hermes-atlas-evolution`; `status` lists such profiles with these commands.
- **Manually.** Copy the whole plugin folder, with `plugin.yaml` at its root, to `<HERMES_HOME>/plugins/hermes-atlas-evolution/` and run `hermes plugins enable hermes-atlas-evolution`. A link to a development checkout there works too and counts as installed. The default Hermes folder on Linux is `~/.hermes`. Windows installations usually use `%LOCALAPPDATA%\hermes`. Enabling makes a running gateway load it; if Hermes says no gateway answered, run `hermes gateway restart`.
- **Host isolation.** Under `plugins.isolation: host` Hermes skips `register_cli_command`, so use `python -m hermes_atlas_evolution --home <profile> ...` from the plugin folder. The runtime guard is off there (see [The runtime guard](#the-runtime-guard)). The reflector does not run in that standalone runner; waiting excerpts are kept for the next pass run by Hermes. The autopilot and the reflector were not verified under host isolation. See [Running outside Hermes](evolution-loop.md#running-outside-hermes).

### Cover image and the plugin catalog

Hermes shows a plugin's cover only for entries of its curated plugin catalog, the `plugin-catalog/` folder of the hermes-agent repository, which Nous Research reviews ([catalog submission](https://hermes-agent.nousresearch.com/docs/developer-guide/plugins/catalog-submission)). An entry's `image` must be an https image on a GitHub host, in a 2:1 proportion, pinned to the commit of the entry. Installed from GitHub, Atlas Evolution shows a generic card until its catalog entry is accepted. Its cover is [banner.jpg](https://raw.githubusercontent.com/sesantanajr/hermes-atlas-evolution/e2dc5a6162b3f87d15b4f042421b4898fc0dd29f/banner.jpg), 1280×640, pinned to a commit of the `assets` branch.

## Compatibility and limits

Requires Hermes Agent 0.23.1 or later and Python 3.11 or later.

**Verified on the development machine** (measurements, not guarantees):

- Over 700 unit and end-to-end tests against a simulated Hermes, also under Hermes' Python with its native redactor. They live on the repository's `tests` branch, so the copy Hermes installs in each profile carries only what Hermes loads. CI runs them on Linux (Python 3.11 to 3.14), macOS and Windows, with ruff, a byte-compile with Python 3.11, the syntax checks of the installer and of the panel's script and a smoke test of the standalone CLI; tests that are POSIX by design (permission bits, the liveness probe, symlinked runtimes) are skipped on Windows.
- Hermes' own install scan (`plugin-guard-v15`, the scanner of Hermes 0.23.2 and of its main branch on 2026-11-17, and the older `plugin-guard-v12`) gives the plugin the verdict `safe`, so an install with no terminal, such as the one Auto mode makes by catalog name in another profile, never waits for a confirmation. `hermes plugins validate` adds two notes that block nothing: the agent tool and `transform_tool_result` are declared but registered only while their settings are on.
- The backfill, on a copy of a real profile with 276 sessions: 373 turns and 3,566 tool calls, exactly one per logical message of the window (counting every copy Hermes' compaction keeps would give 6,731), in under a second. Of its 152 failures, 129 came from the owner's own turns.
- Hermes' doctor checks: about 7 seconds per profile on Hermes 0.23.1, with no network.
- The autopilot (one claim per profile, expiring lease, retry, profile pinning, a manual `learn` waiting for a running pass): verified in tests and in the CLI. The clock, the release of a pass at process exit, the stale-process check and the guard against two copies in one profile: verified in tests.
- Measured once and not repeated with the current code: about 0.1 ms per hook event; with a `state.db` of about 170 MB, `learn` about 0.3 s and 25 MB, `report` about 0.35 s.

**Verified in production:** three real reflector calls through Hermes (provider DeepSeek, about 600 tokens and about 2 seconds each) produced three drafts in Portuguese.

**Not verified:** lesson verdicts and skill outcomes over weeks of real use (there are no field results yet), the clock and the stale-process check in a long-running gateway that serves several profiles, removing an old-name copy on a running gateway, the daily doctor checks on Hermes versions other than 0.23.1 (they call Hermes' internal `DOCTOR_CHECKS`, which may change), the Kanban nudge of the autopilot (which needs `kanban.dispatch_in_gateway`), the autopilot and the reflector under `plugins.isolation: host`, other Hermes versions, and a Hermes gateway running on macOS or Windows (the tests run there, the gateway did not).

**Limits**

- Verdicts compare two periods; they are correlations, not controlled experiments.
- Only lessons bound to a failure (derived and reflector) get a measured effect.
- The database only gains tables and columns, so an older copy of the plugin still opens it. A very old copy refuses it; to go back that far, restore a backup of `evolution.sqlite3` or delete it.
- The autopilot needs a nudge: a turn, the clock or the Kanban tick. A host without `on_unload` gets no clock, so a quiet profile there waits for its next turn.
- The backfill reads Hermes' history only before the plugin started observing the profile, at most 14 days back. It does not replay model calls and tokens, it times tool calls only approximately (from the request to the result), and it cannot tell a command another plugin rewrote; a binary that failed live after a rewrite is kept out of the lessons from then on.
- Under `plugins.isolation: host` there is no `hermes evolution`: use `python -m hermes_atlas_evolution --home <profile> ...` (it reads `config.yaml` only with PyYAML; without it, the mode is Manual). The cron recipes need the Hermes CLI; a standalone pass drafts nothing and keeps waiting excerpts for a pass run inside Hermes.
- Review counts depend on a line Hermes 0.23.1 writes to `agent.log`. Owner signals are heuristics over the first words of a message.
- The runtime guard looks only at the command word of each part of a terminal command, after the wrappers it knows, and up to 8 levels into a command given as one string. A command nested deeper, one run over `ssh` or from a script, a command it cannot parse and a path relative to the working folder all pass. It is a safety net, not a sandbox.
- The stale-process check compares version numbers: a process that loaded different code under the same version number is not flagged, and on Windows no process is flagged.
- The operator guard reads process ancestry and cgroups from `/proc`, so outside Linux it relies on the environment markers alone.
- Who a chat turn serves comes from `owner_sender_ids` and `owner_platforms`. With both empty, every messaging chat counts as someone else's: its failures still count, but lessons from them wait for approval and the chat gets template lessons only. A platform listed in `owner_platforms` trusts everyone who writes there.

## Advanced: let the native background review propose lessons

Hermes can admit a named tool to the background review through `auxiliary.background_review.extra_tools`. Adding `hermes_atlas_evolution_lessons` lets the review record what it learned as a lesson proposal in the playbook, next to its usual skill and memory writes.

```yaml
# config.yaml of the profile
auxiliary:
  background_review:
    extra_tools:
      - hermes_atlas_evolution_lessons
```

- This is operator configuration in Hermes. The plugin never sets it.
- The tool must be available to the parent agent, so it also requires `agent_tools` to be on.
- A lesson proposed this way has origin `agent`: it is stored in quarantine, its proposal is high risk and it reaches the agent only after you approve it. The tool accepts at most 5 proposals per hour.
- An approved proposal is shown in the prompt section like any other lesson. It is not tied to a failure signature, so it gets no individual before-and-after verdict. Its activation still counts as a concurrent change for the other verdicts.
- This combination was not exercised on a production gateway.

## Where the next validation has the most value

1. Run the loop on a production gateway for a few weeks and compare the lesson verdicts and the skills flagged by outcome with a manual review of the same turns.
2. Follow the autopilot in a long-running gateway that serves several profiles, for several days: the passes `status` shows for each profile, their duration, and the hook latency while a pass runs.
3. Compare the daily doctor items with a full `hermes doctor` in the same profiles, and check that every problem Hermes lists reaches the Environment screen in plain words.
4. Review the reflector's drafts against the failures they came from, beyond the three real calls made so far, and choose a low-cost model for `auxiliary.evolution_reflector`.
5. Read the runtime guard's vetoes and the radar's proposals against what really happened on the host, to find false positives.
