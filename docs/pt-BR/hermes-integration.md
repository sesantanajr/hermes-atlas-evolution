# Atlas Evolution e as interfaces do Hermes

[English](../hermes-integration.md) | **Português (Brasil)**

A integração usa como referência a árvore do Hermes Agent 0.23.1 (commit `3b421578588243f920886e6fe79a6faa87ea026e`). Este documento lista o que o plugin registra no Hermes, o que ele lê de um perfil, qual configuração libera cada recurso, o que ele não faz e onde uma validação adicional é mais útil. [Release oficial](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.1) · [API pública de plugins](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/website/docs/developer-guide/plugins/public-api.md)

O plugin se apoia na API publicada de plugins: usa os métodos de `ctx` abaixo e só importa os módulos do Hermes `hermes_constants`, `hermes_cli.config`, `agent.redact` (`redact_sensitive_text`) e `agent.secret_scope`, todos listados na API pública de plugins do Hermes. Cada método opcional de `ctx` é consultado antes do uso, então um host que não o tenha ainda carrega o plugin, sem aquele recurso. Cinco leituras olham módulos que o Hermes já carregou no processo, sem importá-los, e nenhuma delas faz parte da API publicada de plugins: a guarda de runtime pega a localização do pacote `hermes_cli` para saber onde está o código do Hermes; o radar de saúde lê a lista de plugins do gerenciador de plugins do Hermes (`hermes_cli.plugins`); o comando `hermes evolution` lê a versão do pacote `hermes_cli` já carregado para a checagem de atualização; os hooks de turno perguntam ao `agent.session_source` a origem real da sessão em andamento (um worker do Kanban roda com plataforma `cli`); e o `status` pergunta ao `hermes_cli.plugin_isolation` se os plugins rodam num host de plugins. Quando um módulo não está carregado, aquela leitura é pulada e o plugin usa o que o payload do hook informa.

## O que o plugin registra

| Superfície | API de plugins | Registrada quando |
|---|---|---|
| 17 hooks, listados abaixo | `ctx.register_hook` | sempre, exceto `pre_tool_call`, registrado só enquanto `runtime_guard` está ligado, e `transform_tool_result`, registrado só enquanto `tool_hints` está ligado e as lições não estão desligadas (enquanto algum plugin o escuta, o Hermes lê cada resultado de ferramenta para ele numa thread própria; o `hermes plugins validate` o aponta como declarado, mas não registrado) |
| Seção de prompt `hermes-atlas-evolution.playbook`, até 1.400 caracteres | `ctx.register_system_prompt_section` | `lessons` é `suggest` ou `auto` |
| Ferramentas `hermes_atlas_evolution_plan` e `hermes_atlas_evolution_lessons`, toolset `hermes-atlas-evolution` | `ctx.register_tool` com `check_fn` | sempre; as duas ficam indisponíveis para o agente até `agent_tools` ser ligado |
| Skill `hermes-atlas-evolution:evolution-review` | `ctx.register_skill` | quando o host oferece o método |
| Variável `ATLAS_EVOLUTION_AGENT=1` em todo subprocesso de uma sessão do agente | `ctx.register_session_env` | quando o host oferece o método |
| Tarefa auxiliar `evolution_reflector`, herdando de `compression` | `ctx.register_auxiliary_task` e, depois, `ctx.llm.complete_structured` | `reflector` está ligado quando o plugin carrega e o host oferece os dois |
| Formulário de configurações com 12 opções | `config_schema` no `plugin.yaml` | sempre; o Hermes grava os valores em `plugins.entries.hermes-atlas-evolution.settings` |
| Comando de CLI `hermes evolution` | `ctx.register_cli_command` | só em plugins no mesmo processo; o Hermes o ignora com `plugins.isolation: host` |
| Comando de chat `/evolution` para as notas da 0.1 | `ctx.register_command` | `legacy_memory_commands` é `true` |
| Callback de descarregamento, que grava os contadores que estavam na fila e fecha o banco | `ctx.on_unload` | quando o host oferece o método |
| Aba **Evolution** do dashboard (`/evolution`) e a API dela: `GET /api/plugins/hermes-atlas-evolution/snapshot` e, para o dono com login, `POST .../decide` | `dashboard/manifest.json`, `dashboard/plugin_api.py` | o dashboard a encontra sozinho na pasta do plugin; o Hermes recusa a API dela num perfil em que o plugin está desligado ([O painel no dashboard](#o-painel-no-dashboard)) |
| Thread em segundo plano `hermes-atlas-evolution-autopilot`, um daemon que roda a passada | nenhuma; iniciada pelos hooks `post_llm_call`, `on_session_end` e `on_kanban_dispatch_tick`, e pelo relógio | `autopilot_minutes` não é 0 |
| Thread em segundo plano `hermes-atlas-evolution-clock`, um daemon que empurra a passada 2 minutos depois de o plugin carregar e depois a cada 10 minutos | nenhuma; parada por meio do `ctx.on_unload` | `autopilot_minutes` não é 0 e o host oferece `on_unload` |

Desde a 0.8.1 a maior parte das configurações vale em até um minuto, sem reiniciar ([O painel no dashboard](#o-painel-no-dashboard), Configurações). Quais hooks são registrados (`runtime_guard`, `tool_hints`), a seção de prompt de um perfil que carregou com as lições desligadas e a tarefa do refletor são definidos quando o plugin carrega. Cada passada do autopilot e cada comando leem as configurações de novo.

**Duas cópias num perfil.** Quando o perfil ainda tem a cópia instalada com o nome usado até a 0.5.0, `hermes-evolution`, e ela está ligada, o plugin não registra nada e avisa no log com o comando que remove a cópia antiga (`hermes plugins remove hermes-evolution`): as duas cópias observariam os mesmos turnos e gravariam no mesmo banco.

**A versão que um processo carregou.** Um processo de gateway ou de dashboard que carrega o plugin registra, no banco do plugin, a versão do plugin, o tipo do processo e quando ele começou, identificados pelo ID do processo, para que o `status` aponte um que ainda roda código antigo ([Status e aviso ao dono](evolution-loop.md#status-e-aviso-ao-dono)).

## Hooks

O manifesto declara os mesmos 17 hooks, e um teste compara as duas listas.

| Hook | O que o plugin faz com ele |
|---|---|
| `pre_tool_call` | Só com `runtime_guard` ligado. Roda a [guarda de runtime](#a-guarda-de-runtime): barra os comandos de terminal do agente que parariam o gateway, apagariam aquilo de que o Hermes em execução precisa, ou mudariam as configurações deste plugin ou o desligariam. Também guarda, só em memória, um hash do comando de cada chamada do tipo terminal, para saber depois se outro plugin o reescreveu. Não é registrado com a guarda desligada, nem onde o Hermes roda os plugins num host de plugins (veja a guarda). |
| `post_api_request` | Conta a chamada, os tokens e a duração por provedor e modelo. |
| `api_request_error` | Conta cada tentativa que falhou, classificada como limite de taxa, autenticação, timeout, upstream ou erro. |
| `post_auxiliary_call` | Conta chamadas auxiliares e falhas por tarefa. |
| `post_tool_call` | Conta o desfecho da ferramenta e a duração dela, classifica uma falha numa assinatura (como `rewritten_command` quando o `middleware_trace` do Hermes aponta uma alteração ou o comando que rodou difere do que o `pre_tool_call` viu), conta uma aprovação recusada por origem da sessão, conta a falha de novo quando o turno atendia o dono (veja [Quem é atendido](evolution-loop.md#quem-é-atendido)), cronometra turnos que usam ferramentas de pesquisa web e, com o refletor ligado, guarda um trecho mascarado de uma falha sem modelo fixo dos turnos do próprio dono. |
| `transform_tool_result` | Acrescenta a lição correspondente a um resultado que falhou quando `tool_hints` está em `true`, o que vem desligado: o Hermes só mantém a alteração do primeiro plugin num resultado de ferramenta. Numa sessão que não atende o dono, só entram lições de modelo fixo. Registrado só enquanto `tool_hints` está ligado e as lições não estão em `off`. |
| `pre_llm_call` | Descobre a superfície do turno e se ele atende o dono (um filho delegado pelo `parent_session_id` da mãe), inicia o cronômetro do turno, classifica em memória os sinais do dono e atribui uma correção do dono às skills do turno anterior. Só devolve contexto para a recuperação opcional das notas da 0.1. |
| `post_llm_call` | Fecha a medição de um turno de pesquisa e dá um empurrão no autopilot. |
| `on_session_end` | Registra o desfecho e a duração do turno e o desfecho de cada skill que ele carregou, e dá um empurrão no autopilot. |
| `on_skill_lifecycle` | Conta carregamentos, alterações e outros eventos do ciclo de vida das skills, e liga uma skill carregada ao seu turno. |
| `subagent_start`, `subagent_stop` | Contam delegações, desfechos e duração. O `subagent_start` também guarda, só em memória, qual sessão delegou cada filho, para o filho atender quem a mãe atendia, inclusive no prompt. |
| `post_compaction` | Registra tokens antes e depois de uma compactação quando o Hermes os informa, e leva o que o plugin sabe da sessão (quem ela atendia, a mãe de um filho) para o id que a compactação dá a ela. |
| `post_curator_run` | Conta execuções do Curator, simuladas ou reais. |
| `on_kanban_worker_exited` | Conta saídas de workers por tipo. |
| `on_session_finalize` | Devolve no máximo um aviso curto por dia UTC sobre decisões pendentes, só para uma sessão das superfícies locais do dono (CLI, TUI, Desktop) que não seja de subagente. O Hermes 0.23.1 só mostra esse texto quando a CLI clássica sai (`shutdown`) ou começa uma sessão nova (`session_boundary`) e quando a TUI ou o Desktop fecham uma sessão (sem motivo informado); em qualquer outro caso o plugin não devolve nada e o aviso do dia não é gasto; as decisões pendentes aparecem no `status`, no resumo e no painel do dashboard. |
| `on_kanban_dispatch_tick` | Dá um empurrão no autopilot. O Hermes o dispara uma vez por tick do despachante do Kanban, a cada 60 segundos, por padrão, para o perfil do próprio gateway, e só onde o despachante roda dentro do gateway (`kanban.dispatch_in_gateway`). A thread do relógio cobre os outros perfis que um gateway atende. |

Um empurrão só compara dois relógios; a passada em si roda na thread do autopilot (veja [O autopilot](evolution-loop.md#o-autopilot)). Nenhum callback bloqueia o turno quando falha: um hook nunca lança erro dentro de um turno, e uma falha é registrada no log no máximo uma vez por tipo de evento. As gravações dos hooks passam por uma conexão de banco por processo e perfil. Enquanto o banco está ocupado, uma atualização espera numa fila de até 512 entradas e é gravada junto com o próximo evento ou quando o plugin é descarregado. O excedente é contado e informado como `dropped_events`. A seção de prompt só lê o banco e conta a sua exibição pela mesma fila.

Na máquina de desenvolvimento, um evento de hook levou cerca de 0,1 ms com esse desenho, contra cerca de 6 ms antes, quando o desenho anterior também perdia 155 de 800 eventos com 8 threads concorrentes. São medições de desenvolvimento numa única máquina, não uma garantia.

## A guarda de runtime

Com `runtime_guard` ligado (o padrão), o callback de `pre_tool_call` do plugin roda a guarda (`guard`). O Hermes o chama antes de cada chamada de ferramenta do agente, e uma diretiva de bloqueio substitui a chamada: a mensagem dela vira o resultado da ferramenta que o agente lê. A guarda olha o argumento `command` de ferramentas do tipo terminal (`terminal`, `shell`, `bash`, `run_command`, `execute_command`), com o `workdir` delas, e o `data` que o `write` ou o `submit` do `process_manage` envia a um processo em segundo plano, que muitas vezes é um shell. Ela barra três tipos de comando.

| Tipo | Barrado | O que o agente recebe |
|---|---|---|
| `gateway_stop` | Linux: `systemctl` com `restart`, `stop`, `kill`, `try-restart`, `reload-or-restart`, `try-reload-or-restart`, `condrestart`, `force-reload` ou `disable --now` numa unidade `hermes-gateway`, inclusive a `hermes-gateway-<perfil>` de um perfil, a `hermes-gateway-<hash>` de uma pasta própria, uma instância e o sufixo `.service`; `service` com `restart` ou `stop` nessa unidade. macOS: `launchctl` com `kickstart -k`, `stop`, `bootout`, `unload`, `remove` ou `kill` no LaunchAgent `ai.hermes.gateway` ou `ai.hermes.gateway-<sufixo>`, citado sozinho, como `gui/<uid>/<rótulo>` ou pelo plist. Windows: `sc` ou `net` com `stop`, os cmdlets do PowerShell `Stop-Service`, `Restart-Service`, `Suspend-Service` e `Stop-ScheduledTask`, e `schtasks /End`, no serviço ou tarefa `Hermes_Gateway` ou `Hermes_Gateway_<sufixo>`. Também `condstop`, `freeze` e `mask --now`, opções do systemctl com valor antes da ação (`--job-mode replace`, `-s KILL`, `-t service`, `-M`, `-H`), uma unidade dada como glob (`'hermes-gateway*'`) e, quando o comando cita o Hermes em qualquer ponto, uma unidade que o shell preenche (`$U`, `xargs`); e o `RestartUnit`, o `StopUnit` ou o `KillUnit` do systemd chamados numa unidade do Hermes por meio do `busctl`, do `dbus-send` ou do `gdbus`. Em qualquer sistema: `pkill`, `killall`, `taskkill` ou `Stop-Process` com um argumento que contenha hermes, e `pkill` ou `killall` cujo padrão seleciona o próprio processo do gateway (`pkill -f python`, `killall python3`, `pkill -f 'gateway run'`), comparado com o nome e a linha de comando do próprio gateway; `kill` do `$PPID` (o shell do agente é filho do Hermes) ou de `-1`; `kill` cujos ids de processo o shell preenche, num comando que procura o Hermes (`kill $(pgrep -f hermes)`, `pgrep -f hermes_cli \| xargs kill`, ``kill `pidof hermes` ``, `kill $(cat ~/.hermes/gateway.pid)`); `hermes gateway stop`, `restart` e `uninstall`, `start --all`, `run --replace` e `install --force`, com opções globais em qualquer posição e um grupo ou uma ação que o shell preencha (`hermes $G restart`). O comando `hermes` conta por todos os nomes com que ele roda: `hermes-agent`, `python -m hermes_cli.main` (a forma da própria unidade do gateway), `python -m hermes_cli`, o `python .../bin/hermes` de um ambiente virtual, `uv run hermes`, `uvx hermes` e `npx hermes` | o comando cortaria os turnos em andamento, inclusive este; não tente de outra forma; diga ao dono que é preciso reiniciar e por quê; o dono roda `hermes gateway restart` no próprio terminal, e esse comando mostra os turnos ainda em andamento e pergunta antes de interrompê-los |
| `runtime_removal` | `rm`, `rmdir`, `unlink`, `shred`, `mv` (as origens, também com `-t` ou `--target-directory`) e, no Windows, `del`, `erase`, `rd`, `Remove-Item` e `Move-Item`, ou `find` com `-delete` ou com `-exec` rodando `rm`, apontados para um caminho protegido, para uma pasta que contenha um deles ou com um glob que case com um deles, depois da expansão de chaves do shell (`mv ~/.hermes{,.old}`); qualquer coisa dentro de uma árvore protegida (`rm -rf venv/lib`, `rm -rf venv/*`); um `xargs rm` alimentado por um comando que cita um caminho protegido (`ls -d <caminho> \| xargs rm -rf`); e o `hermes profile delete`, que apaga um perfil e para o gateway dele | o comando apagaria ou moveria esse caminho, e o Hermes pararia de funcionar até alguém consertar à mão; remover isso fica para o dono, no próprio terminal, com o Hermes parado |
| `plugin_settings` | `hermes config set` ou `unset` da seção `plugins` (os plugins que o Hermes liga, desliga ou isola) e de `plugins.entries.hermes-atlas-evolution` (ou o nome usado até a 0.5.0), mas não do `plugins.entries.<id>` de outro plugin; `hermes config edit`; `hermes plugins disable`, `remove`, `rm`, `uninstall` ou `trust` do `hermes-atlas-evolution`, e `hermes plugins install` de uma origem com esse nome, que substituiria o código dele; remover ou mover a própria pasta do plugin ou qualquer coisa dentro dela; e um comando que grava um `config.yaml` do Hermes (`sed -i`, `perl -i`, `yq -i`, um redirecionamento, `cp`, `tee`, uma linha de Python que o despeja ou grava) e cita a seção de plugins, este plugin ou uma das configurações de confiança dele. Opções globais que levam valor, como `-p <perfil>`, são lidas onde estiverem, como o Hermes as lê, e uma palavra que o shell preenche na chave, na ação ou no nome (`$VAR`, `$'...'`, uma substituição de comando) conta como essa mudança | o comando mudaria quem conta como o dono ou as proteções do plugin, ou desligaria o plugin; só o dono decide isso, no próprio terminal; não tente de outra forma; diga ao dono o que você queria mudar e por quê |

Os caminhos protegidos são aqueles de que o Hermes em execução precisa: os prefixos do interpretador Python em execução e do ambiente dele, o interpretador base para o qual um ambiente virtual aponta (a linha `home` do `pyvenv.cfg` e o `sys._base_executable`), o código do Hermes (a pasta que contém o pacote `hermes_cli`), a raiz do Hermes e este perfil. Cada um é protegido tanto como está escrito quanto resolvido, então um link conta pelos dois nomes: o link `cpython-3.11-...` do uv para `cpython-3.11.16-...`, ou um `~/.hermes` que aponta para outro disco. Um caminho com menos de três componentes, como `/usr`, nunca entra na lista, então um interpretador do sistema cujo prefixo é `/usr` não fica coberto.

Na maioria deles, só o próprio caminho e as pastas acima dele são protegidos. As **árvores protegidas** são protegidas também por dentro, porque apagar qualquer parte delas faz o Hermes parar: o ambiente virtual em que o Hermes roda, uma pasta de runtime Python só dele (uma cujo nome diz python, como `~/.hermes/tools/python-3.14...`), a biblioteca padrão e os pacotes Python e ambientes virtuais no topo do código do Hermes (`hermes_cli`, `gateway`, `agent`, `venv`, ...). Um prefixo compartilhado como `/usr/local` nunca é uma árvore; só a biblioteca padrão dentro dele é. O interior da raiz do Hermes e do perfil continua aberto ao agente, que trabalha ali. A própria pasta do plugin também é protegida por dentro, como um bloqueio `plugin_settings`: removê-la desliga o plugin.

Como um comando é lido:

- Ele é dividido em `;`, `&&`, `||`, `|`, `&`, parênteses e quebras de linha, e em cada parte só conta a palavra do comando, depois das palavras do shell que abrem ou negam um comando composto (`if`, `then`, `elif`, `else`, `while`, `until`, `do`, `!`, `{`, `coproc`), de atribuições de variáveis e de invólucros como `sudo` (com as opções longas dele), `env`, `nohup`, `timeout`, `nice`, `ionice`, `stdbuf`, `exec`, `command`, `builtin`, `time`, `chrt`, `doas`, `setsid`, `systemd-run` com as opções dele (inclusive temporizadores como `--on-active 30`), `runuser`, `watch`, `flock`, `xargs`, `taskset`, `unshare`, `nsenter`, `chroot`, `strace`, `ltrace`, `uv run`, `uvx`, `pipx run`, `npx` e `rtk run` (ou `rtk err` e os outros subcomandos do `rtk` que rodam um comando). As palavras que o `xargs` acrescenta a partir da entrada contam como palavras que o shell preenche. Um comando citado nos argumentos de outro, como num `echo`, não é um comando.
- Um comando passado como um único texto é lido um nível para dentro quando vai para um shell (`bash`, `sh`, `zsh`, `dash`, `ksh`) com `-c` ou um grupo de opções que o contenha, como `-lc` ou `-ec`, para `su`, `runuser`, `script` ou `flock` com `-c`, `--command` ou `--command=` (também `script -qc`), para o `eval`, para o PowerShell (`powershell`, `pwsh`) com `-Command` ou `-c`, para o `cmd` com `/c` e para o `env` com `-S` ou `--split-string`. Também são lidos assim as substituições de comando `$(...)` e `` `...` ``, inclusive dentro de aspas duplas, onde elas continuam rodando; o comando que o `find -exec` roda; o comando passado ao `ssh localhost` (ou `127.0.0.1`, `::1`); e os literais de texto do programa embutido de um interpretador (`python -c`, `perl -e`, `ruby -e`, `node -e`, `php -r`), cada um sozinho e todos juntos, que é como se lê um `subprocess.run(['systemctl', ...])`. Um comando executado a partir de um arquivo de script, ou via `ssh` para outro host, não é examinado.
- O corpo de um here-document é texto que vai ser gravado em algum lugar, não um comando que roda agora, então é ignorado.
- `~`, `~<nome de usuário do dono>`, `$HOME` e `$HERMES_HOME` (este perfil) são expandidos no começo de um caminho, também nas formas `${NOME}`, `${NOME:?...}` e `${NOME:-...}`, assim como `%USERPROFILE%`, `%LOCALAPPDATA%`, `%APPDATA%` e as formas `$NOME` e `$env:NOME` deles, quando estão definidos. No Windows, `C:\x`, `C:/x` e o `/c/x` do Git Bash são o mesmo caminho, comparado sem diferenciar maiúsculas. Um caminho relativo é tomado a partir do `workdir` da ferramenta de terminal, ou de um `cd` anterior no mesmo comando, quando essa pasta é conhecida; fora isso, ele não é checado, nem um que começa com outra variável.
- Qualquer dúvida deixa o comando passar: uma aspa sem par, um comando com mais de 20.000 caracteres, uma ferramenta que não é do tipo terminal.

A checagem é uma função pura sobre o comando: não lê nem grava nada, e o tamanho da entrada é limitado. O callback nunca lança erro, porque o Hermes trata como bloqueio um `pre_tool_call` que falha ou estoura o tempo. Cada bloqueio é contado por tipo na `guard_daily` (o comando não é gravado), e o `hermes evolution status` e o resumo mostram as contagens. A mensagem segue o idioma do plugin. O terminal do próprio operador não é afetado.

Na 0.8.0, a guarda foi testada contra cerca de 350 comandos escritos para contorná-la; os que ela ainda deixa passar são comandos que afetam o host inteiro (`reboot`, `systemctl isolate`), texto enviado por pipe a um shell ou a um interpretador, texto codificado decodificado para um deles, um caminho de outro usuário ou um caminho relativo que ela não consegue situar, e comandos agendados pelo `at` ou por um arquivo de script. Esses ficam para a política de aprovação do próprio Hermes.

Essa guarda existe porque, num servidor real, o agente reiniciou o próprio gateway com `systemctl` 13 vezes numa semana, 12 delas a partir de um único chat num único dia, cortando os turnos em andamento, e uma vez apagou o runtime Python que a unidade do gateway usava, o que deixou o Hermes fora do ar por cerca de uma hora. O mesmo histórico também tinha um reinício agendado por meio do `systemd-run`, e por isso a guarda olha o comando que está por trás dos invólucros (wrappers) acima. Desde a 0.6.0, o `hermes gateway restart` do agente também é barrado: sem terminal, o Hermes 0.23.1 se recusa a reiniciar enquanto há sessões rodando, e o `--yes` dele as interromperia, então o reinício fica com o dono. A guarda é uma rede de proteção para esses casos, não uma sandbox: a política de aprovação do próprio Hermes para comandos de terminal continua valendo.

**Guarda desligada ou host de plugins.** Com `runtime_guard: false`, ou onde o Hermes roda os plugins num processo separado (`plugins.isolation: host`), o plugin não registra nenhum `pre_tool_call`, então nem a guarda nem a checagem de um comando que outro plugin reescreveu rodam ali (o rastro de middleware do Hermes continua marcando as reescritas feitas por ele). Cada `pre_tool_call` vira uma chamada ao host, e o Hermes bloqueia uma ferramenta cujo `pre_tool_call` falha: um host que caísse bloquearia todas as ferramentas do perfil. O `status` diz que a guarda está desligada por esse motivo.

## O painel no dashboard

O plugin acrescenta uma aba, **Evolution**, ao dashboard do Hermes e ao Hermes Desktop, em Plugins na barra lateral. O Hermes a encontra sozinho na pasta `dashboard/` do plugin (`manifest.json`, um script sem etapa de build, uma folha de estilo que segue as cores do tema do dashboard e `plugin_api.py`); não é preciso configurar nada. Ela funciona para o perfil do próprio dashboard e para os outros perfis escolhidos nele.

| Aba | Mostra, e deixa você fazer |
|---|---|
| Visão geral | Lições ativas, o que espera a sua decisão, chamadas de ferramentas e turnos com as taxas de erro, vetos da guarda em 7 dias e a última passada. Cada lição que espera, com o texto exato, **Aprovar** e **Rejeitar**, e **Aprovar todas**, que antes lista cada frase que vai aprovar; uma lição proposta pelo agente fica de fora e é aprovada sozinha |
| Lições | Todas as lições com situação, origem, ferramenta, frase e efeito medido; aprovar ou rejeitar uma que espera, aposentar uma ativa, reativar uma aposentada |
| Propostas | Propostas abertas com o risco, a lição que ativariam e o comando; aprovar ou rejeitar. Uma proposta que muda o Hermes (uma skill, uma configuração) fica registrada e mostra o comando, para o Hermes rodar a partir do seu terminal |
| Configurações | Todas as opções do formulário de configurações, com **Aplicar a configuração recomendada** (lições em `auto`, refletor ligado e os canais de chat que são seus por construção), e **Quem é você nos chats**: cada canal dos últimos 30 dias com os remetentes, os sugeridos marcados |
| Histórico | Todas as decisões, do terminal e do painel, da mais recente para a mais antiga, com **Desfazer** |
| Resumo | O resumo de `hermes evolution report`, de 7, 14 ou 30 dias |
| Status | A página de `hermes evolution status` |

**Quem pode decidir.** Toda requisição é autenticada antes pelo dashboard. Uma decisão só é aceita de um dono com login (senha ou OAuth, que o Hermes liga quando o `dashboard.public_url` é um endereço público) ou da permissão que o Hermes Desktop envia, e nunca de uma requisição que traz o token de sessão do dashboard em qualquer forma (o cabeçalho dele, `?token=` ou `Authorization: Bearer`, a forma antiga do Hermes). Como o plugin sabe disso depende de onde o Hermes roda as rotas:

- **O perfil do próprio dashboard** roda no processo do dashboard, atrás da porta de login do Hermes. O painel aceita a sessão que a porta verificou (`request.state.session`), menos uma verificada pelo token de sessão de implantação (`HERMES_DASHBOARD_SESSION_TOKEN`), que não é o login de uma pessoa. Num host que não publica a sessão verificada, o cookie de login conta pelo nome, em cada forma que o Hermes dá a ele: `hermes_session_at` por HTTP, `__Host-hermes_session_at` por HTTPS (um endereço público atrás de um proxy), `__Secure-hermes_session_at` sob um prefixo de caminho, com `_<gateway>` no Webapp do gateway. A 0.8.1 só conhecia a primeira forma, então atrás de HTTPS o painel ficava só leitura.
- **Todo outro perfil** escolhido no dashboard roda a própria cópia do plugin no plugin host daquele perfil. O Hermes encaminha a requisição para lá sem nenhuma credencial (nem cookie, nem token), com um veredito que é o mesmo para um login e para o token do dashboard aberto, e sem as variáveis que diriam como o dashboard admite as pessoas. Por isso o plugin host nunca decide: responde só leitura, com o motivo `other_profile`. O painel então pergunta ao plugin no processo do próprio dashboard, com `?profile=current` (o perfil do dashboard, para o Hermes) e `target=<o perfil na tela>`, e esse processo lê e decide pelo perfil com a mesma regra de login acima, quando o Atlas Evolution está instalado e ativado nele (`plugins.enabled` no `config.yaml` dele); um nome que não é perfil deste Hermes, um link ou um caminho fora dele é recusado. Isso exige o plugin ativado também no perfil do próprio dashboard; sem ele, os outros perfis ficam só leitura no painel e são decididos pelo menu do terminal. Na 0.8.1 esses perfis nunca conseguiam decidir.

Um dashboard sem login entrega o token de sessão a quem abrir a página, inclusive o terminal do agente, então ali o painel fica só leitura, diz por quê e mostra o comando do menu do terminal no lugar; o retrato então deixa de fora os ids dos remetentes dos canais de chat. Uma decisão também precisa do cabeçalho `X-Atlas-Evolution: 1`, que uma página de outro site não consegue enviar sem o navegador perguntar antes ao dashboard. A guarda de runtime barra os comandos do agente que chamam a rota de decisões, seja qual for a grafia do endereço (escapes com `%`, `/./`, `/../`, aspas, um nome preenchido pelo shell). Um valor que o plugin não usaria como veio (`autopilot_minutes: 5`, um id de remetente que não é texto) é recusado antes de qualquer gravação, e um `settings.json` quebrado nunca derruba o painel: ele cai para o padrão como no gateway e o painel avisa.

**O que uma decisão faz.** O mesmo código decide no terminal e no painel (`decisions.py`), e cada decisão vai para um registro (`decision_log`: ids, situações, valores de configuração e impressões digitais, nunca o texto das lições ou da memória). **Aprovar todas** envia a lista exata de lições mostradas, cada uma com uma impressão digital da frase, e só aprova as que continuam esperando com essa mesma frase. **Desfazer** só volta atrás enquanto o que a decisão mudou continua como ela deixou: uma aprovação volta a esperar e a medição dela é descartada, uma aposentadoria é desfeita ativando a lição de novo, uma configuração recebe o valor anterior, e uma entrada retirada da memória do Hermes volta a partir da cópia guardada (só pelo menu do terminal ou pelo desfazer do painel).

**Configurações.** O painel e o menu do terminal as gravam com o próprio comando público do Hermes, `hermes --profile <nome> config set plugins.entries.hermes-atlas-evolution.settings.<chave> <valor>` (o Hermes confere a chave, pega a trava da configuração e grava de forma atômica), no `config.yaml` do perfil, depois de conferir cada valor pelas regras do próprio plugin. O gateway em execução aplica a mudança em até um minuto, sem reiniciar: cada hook e o relógio do plugin comparam os horários de modificação do `config.yaml` e do `settings.json` no máximo a cada 30 segundos e só os leem de novo quando mudaram. Quem conta como o dono, o modo das lições, o refletor e o limite dele, o idioma, os sinais do dono, o limite de turno lento e o intervalo do autopilot valem na hora. `runtime_guard` e `tool_hints` decidem quais hooks o Hermes chama, e um perfil que carregou com as lições desligadas não tem seção de prompt nenhuma, então esses esperam a próxima carga do plugin (o Hermes recarrega os plugins num gateway em execução quando um é ligado, desligado ou atualizado pelo Desktop); até lá o painel os lista.

A API tem duas rotas: `GET /api/plugins/hermes-atlas-evolution/snapshot?days=1..35&lang=en|pt` e `POST /api/plugins/hermes-atlas-evolution/decide`. Elas rodam nas threads de trabalho do dashboard, então o banco nunca segura o loop de eventos dele; enquanto o banco está ocupado elas respondem 503 e o painel avisa. A página segue o idioma do dashboard (inglês ou português do Brasil), e tudo, inclusive o texto das lições, é exibido como texto, nunca como marcação. Com `plugins.isolation: host`, o Hermes atende as rotas pelo host de plugins.

## O refletor e o acesso a modelos do Hermes

O refletor é a única parte do plugin que envolve um modelo de IA, e vem ligado. Quando `reflector` está ligado no carregamento, o plugin registra a tarefa auxiliar `evolution_reflector` com `inherit_from="compression"`: ela parte da configuração efetiva da tarefa de compressão, e você pode dar a ela provedor e modelo próprios em `auxiliary.evolution_reflector`, na configuração do perfil. Uma passada feita dentro do Hermes (pelo autopilot, pelo `hermes evolution learn` ou pelo `ops tick`) então chama `ctx.llm.complete_structured` com essa tarefa, um esquema JSON, no máximo 300 tokens de saída e prazo de 60 segundos. O Hermes resolve o provedor, envia a requisição e a contabiliza; o plugin não abre conexão, e nenhuma transação do plugin fica aberta durante a chamada. Quando o host não oferece acesso a modelos para plugins, ou enquanto `lessons` está em `off`, o ciclo roda sem rascunhos. Três chamadas reais pelo Hermes em produção (provedor DeepSeek, cerca de 600 tokens e cerca de 2 segundos cada) geraram três rascunhos em português. O que é enviado e o que é aceito de volta está descrito em [O ciclo de evolução](evolution-loop.md#o-refletor).

## O que o plugin não faz no Hermes

- Nunca arquiva, desfaz, edita ou cria uma skill. A única mudança em skills é `hermes curator lock` (e `unlock` para desfazer): na sua tecla, ou sozinho no Modo Auto para uma skill que o curador reescreve sem parar.
- Nunca muda uma configuração do Hermes além das próprias (`plugins.entries.hermes-atlas-evolution.settings.*`, por `hermes config set`, quando você muda uma). Uma proposta que mudaria outra configuração aparece como um comando `hermes config`.
- Memória do Hermes: só tira uma cópia de uma entrada que é exatamente o mesmo texto (sozinho nos Modos Assistido e Auto) ou a entrada que você escolhe, depois de guardar uma cópia do arquivo; não lê nada além das contagens de estrutura acima.
- Não reescreve um prompt já em uso, não injeta contexto por turno (exceto a recuperação opcional das notas 0.1) e não muda argumentos de ferramentas. As únicas mudanças no que o agente vê são a frase juntada ao resultado de uma ferramenta que falhou, com `tool_hints` ligado, e as lições no começo da sessão.
- Não para, não reinicia e não mata nada. A guarda de runtime só recusa um comando; nunca roda um.
- Não grava no histórico do Hermes: o `state.db` e os logs são abertos só para leitura.
- Outros perfis: no Modo Auto, a partir do perfil que cuida do Hermes inteiro, ele se instala (no próprio commit) num perfil usado nos últimos 7 dias que nunca o teve, e move a pasta de uma instalação que falhou (`plugins/.install-*`) para a lixeira dele. Desligar um de dois plugins só roda na sua tecla, naquela proposta. Todo o resto ali (remover ou atualizar um plugin, arquivar uma skill) é um comando para você. Antes de qualquer mudança ele lê aquele perfil de novo do disco.
- Não aprova, nega nem contorna aprovações do Hermes, e nunca transforma uma aprovação recusada em conselho.
- Não registra middleware, provedor, provedor de memória, padrão de redação ou idioma, e não substitui nada no núcleo do Hermes.
- O único job de Cron que ele cria é o resumo semanal, na sua tecla (`schedule-digest`), como um script sem agente; as outras receitas são impressas para você. O único cartão de Kanban que ele cria é o cartão bloqueado do `ops handoff`, que precisa de `kanban_handoff`.
- Não abre conexão de rede própria e não envia telemetria. O Hermes baixa o plugin do GitHub quando o Modo Auto o instala em outro perfil, e o `hermes doctor` (seu clique) chama os provedores. Um modelo só é chamado pelo refletor, por meio do Hermes.
- Não deixa o agente decidir: as decisões se recusam a rodar no shell de um agente.

## Notas de instalação

- **Pelo GitHub.** `hermes plugins install sesantanajr/hermes-atlas-evolution --enable` no perfil padrão, `hermes -p <perfil> plugins install sesantanajr/hermes-atlas-evolution --enable` num perfil com nome. Instalar com `--enable` faz um gateway em execução carregar o plugin na hora; a seção de prompt vale a partir da próxima sessão. Confira com `hermes plugins doctor --ci hermes-atlas-evolution` e `hermes evolution status`.
- **Em todo perfil que você usa.** O Hermes carrega os plugins por perfil, mesmo quando um único gateway atende vários perfis. Para todos os perfis com nome: `for p in $(ls ~/.hermes/profiles); do hermes -p "$p" plugins install sesantanajr/hermes-atlas-evolution --enable; done`, mais o comando do perfil padrão. O `hermes evolution status` lista todos os perfis da mesma raiz do Hermes, com o comando de instalação para cada perfil movimentado que não tem o plugin.
- **Atualização.** O `hermes plugins update hermes-atlas-evolution`, com `-p <perfil>` para cada perfil com nome, baixa o código novo, mas um gateway em execução continua com o código que carregou: o Hermes recarrega um gateway em execução na instalação, ao ligar e ao desligar um plugin, e numa atualização feita pelo Hermes Desktop, pelo dashboard ou pelo `/plugins update` num chat, não nessa atualização pela linha de comando. Termine com `hermes gateway restart`; se ainda houver algo rodando, ele lista o que é e pergunta, em inglês, `Interrupt them and restart the gateway? [y/N]`. O `status` aponta um processo de gateway ou de dashboard que ainda roda uma versão mais antiga, em sistemas POSIX.
- **Migração da 0.5.0.** Até a 0.5.0, o nome do plugin era `hermes-evolution`. Em cada perfil que o tem, rode `hermes plugins remove hermes-evolution` e depois `hermes plugins install sesantanajr/hermes-atlas-evolution --enable`, e não o `hermes plugins update`: o Hermes dá à pasta de um plugin o nome dele, então uma atualização não substituiria a cópia antiga. Remova primeiro: a instalação faz um gateway em execução procurar os plugins de novo, o que descarrega a cópia removida e carrega a nova; se você instalou primeiro, rode `hermes gateway restart` depois da remoção. Enquanto a cópia antiga está instalada e ligada, a nova não registra nada, nem o próprio comando, então o `hermes evolution` desse perfil continua sendo o da 0.5.0 (veja [O que o plugin registra](#o-que-o-plugin-registra)); o `status` rodado num perfil que já está na 0.6.0 marca esse perfil como tendo as duas cópias e imprime a correção. O `plugins remove` do Hermes também apaga o `plugins.entries.hermes-evolution` do `config.yaml` do perfil, então renomeie esse bloco para `hermes-atlas-evolution` antes, se você mudou opções no formulário de configurações. Os dados em `<HERMES_HOME>/evolution/` ficam. Onde uma lista explícita de toolsets ou o `auxiliary.background_review.extra_tools` citar `atlas-evolution` ou `atlas_evolution_lessons`, use `hermes-atlas-evolution` e `hermes_atlas_evolution_lessons`.
- **Manualmente.** Copie a pasta inteira do plugin, com o `plugin.yaml` na raiz, para `<HERMES_HOME>/plugins/hermes-atlas-evolution/` e execute `hermes plugins enable hermes-atlas-evolution`. A pasta padrão do Hermes no Linux é `~/.hermes`. Instalações Windows geralmente usam `%LOCALAPPDATA%\hermes`. Ao habilitar, um gateway em execução carrega o plugin; se o Hermes disser que nenhum gateway respondeu, rode `hermes gateway restart`.
- **Isolamento em host.** Com `plugins.isolation: host`, o Hermes ignora `register_cli_command`; use `python -m hermes_atlas_evolution --home <perfil> ...` a partir da pasta do plugin. A guarda de runtime fica desligada ali (veja [A guarda de runtime](#a-guarda-de-runtime)). O refletor não roda nesse executor independente; os trechos em espera ficam para a próxima passada feita pelo Hermes. O autopilot e o refletor não foram verificados com isolamento em host. Veja [Operações](operations.md#fora-do-hermes).

### Capa e o catálogo de plugins

O Hermes só mostra a capa de um plugin para os itens do catálogo curado de plugins dele, a pasta `plugin-catalog/` do repositório hermes-agent, revisada pela Nous Research ([envio ao catálogo](https://hermes-agent.nousresearch.com/docs/developer-guide/plugins/catalog-submission)). A `image` de um item precisa ser uma imagem https num host do GitHub, na proporção 2:1, fixada no commit do item. Instalado pelo GitHub, o Atlas Evolution aparece com um cartão genérico até o item dele no catálogo ser aceito. A capa dele é o [banner.jpg](../banner.jpg), de 1280×640.

## Compatibilidade e limites

Exige Hermes Agent 0.23.1 ou superior e Python 3.11 ou superior.

**Verificado na máquina de desenvolvimento** (medições, não garantias):

- Os testes unitários e de ponta a ponta contra um Hermes simulado, também com o Python do Hermes e a função nativa de mascaramento de segredos dele. A integração contínua roda os testes no Linux com Python 3.11 a 3.13 e em máquinas reais de macOS e Windows; os testes que são POSIX por desenho (bits de permissão, a checagem de processo vivo, runtimes com link simbólico) são pulados no Windows.
- `hermes plugins validate` do Hermes 0.23.1: sem avisos (2 ferramentas, 17 hooks), varredura de segurança `safe`, pronto para `plugins.isolation: host`.
- A leitura do histórico, numa cópia de um perfil real com 276 sessões: a 0.6.0 reprocessa 373 turnos e 3.566 chamadas de ferramentas, exatamente uma por mensagem lógica da janela (a 0.5.0 contava 6.731, cada cópia que a compactação do Hermes guarda, e 86 turnos interrompidos em vez de 23), em menos de um segundo. Das 152 falhas, 129 vieram dos turnos do próprio dono.
- O autopilot (uma reserva por perfil, reserva que expira, nova tentativa, fixação do perfil, um `learn` manual esperando a passada em andamento): verificado nos testes e na CLI. O relógio, a liberação de uma passada na saída do processo, a checagem de código antigo e a proteção contra duas cópias num perfil: verificados nos testes.
- Medido na 0.4.0 e não repetido desde então: cerca de 0,1 ms por evento de hook (antes, cerca de 6 ms, com perda de eventos sob concorrência); com um `state.db` de cerca de 170 MB, `learn` cerca de 0,3 s e 25 MB, `report` cerca de 0,35 s, `ops tick` cerca de 0,5 s.

**Verificado em produção:** três chamadas reais do refletor pelo Hermes (provedor DeepSeek, cerca de 600 tokens e cerca de 2 segundos cada) geraram três rascunhos em português.

**Não verificado:** vereditos de lições e skills pelo resultado ao longo de semanas de uso real (ainda não há resultados de campo), o relógio e a checagem de código antigo num gateway de longa duração que atende vários perfis, a migração da 0.5.0 num gateway em execução, o empurrão do Kanban no autopilot (que depende de `kanban.dispatch_in_gateway`), o autopilot e o refletor com `plugins.isolation: host`, ensaios no Linux com systemd real, outras versões do Hermes, e um gateway do Hermes rodando no macOS ou no Windows (os testes rodam lá, o gateway não).

**Limites**

- Os vereditos comparam dois períodos; são correlações, não experimentos controlados.
- Só as lições ligadas a uma falha (derivadas e do refletor) têm efeito medido.
- Um banco no esquema 8 (0.5.0 em diante) não abre na 0.4.0 ou anterior. Para voltar até lá, restaure um backup ou apague o `evolution.sqlite3`. A 0.6.0 mantém o esquema 8 e só acrescenta uma tabela, então a 0.5.0 ainda abre o banco dela; da 0.6.0 em diante, um banco num esquema mais novo também abre, porque as versões seguintes só acrescentam tabelas e colunas.
- O autopilot precisa de um empurrão: um turno, o relógio ou o tick do Kanban. Um host sem `on_unload` não tem relógio, então ali um perfil parado espera o próximo turno.
- A leitura do histórico só pega o que o Hermes registrou antes de o plugin começar a observar o perfil, até 14 dias para trás. Ela não reprocessa chamadas ao modelo nem tokens, mede as chamadas de ferramenta só de forma aproximada (do pedido ao resultado) e não reconhece um comando que outro plugin reescreveu; um binário que falhou ao vivo depois de uma reescrita fica fora das lições a partir daí.
- Com `plugins.isolation: host` não existe `hermes evolution`: use `python -m hermes_atlas_evolution --home <perfil> ...` (que só lê o `config.yaml` com o PyYAML). As receitas de cron dependem da CLI do Hermes; uma passada pelo executor independente não rascunha nada e mantém os trechos em espera para uma passada feita dentro do Hermes.
- A contagem de revisões depende de uma linha que o Hermes 0.23.1 grava no `agent.log`. Os sinais do dono são heurísticas sobre as primeiras palavras da mensagem.
- A guarda de runtime só olha a palavra do comando em cada parte de um comando de terminal, depois dos invólucros que ela conhece, e um nível dentro de um comando passado como um único texto. Um comando aninhado mais fundo, um executado via `ssh` ou a partir de um script, um comando que ela não consegue interpretar e um caminho relativo à pasta de trabalho passam. Ela é uma rede de proteção, não uma sandbox.
- A checagem de código antigo compara números de versão: um processo que carregou outro código com o mesmo número de versão não é apontado, e no Windows nenhum processo é apontado.
- A checagem de operador (que só deixa o dono decidir) lê a ancestralidade dos processos e os cgroups em `/proc`, então fora do Linux ela depende só dos marcadores do ambiente.
- Quem um turno de chat atende vem do `owner_sender_ids` e do `owner_platforms`. Com os dois vazios, todo chat de mensagens conta como de outra pessoa: as falhas dele continuam contadas, mas as lições que vêm delas esperam aprovação e o chat recebe só lições de modelo fixo. Uma plataforma listada em `owner_platforms` confia em todos que escrevem nela.

## Avançado: deixar a revisão nativa propor lições

O Hermes pode admitir uma ferramenta nomeada na revisão em segundo plano por meio de `auxiliary.background_review.extra_tools`. Incluir `hermes_atlas_evolution_lessons` permite que a revisão registre o que aprendeu como proposta de lição no playbook, ao lado das gravações habituais em skills e memória.

```yaml
# config.yaml do perfil
auxiliary:
  background_review:
    extra_tools:
      - hermes_atlas_evolution_lessons
```

- Essa é uma configuração do operador no Hermes. O plugin nunca a define.
- A ferramenta precisa estar disponível para o agente principal, então isso também exige `agent_tools` ligado.
- Uma lição proposta por esse caminho tem origem `agent`: fica em quarentena, a proposta tem risco alto e ela só chega ao agente depois que você aprova. A ferramenta aceita no máximo 5 propostas por hora.
- Uma proposta aprovada aparece na seção de prompt como qualquer outra lição. Ela não está ligada a uma assinatura de falha, por isso não recebe veredito individual de antes e depois. A ativação dela ainda conta como mudança simultânea nos demais vereditos.
- Essa combinação não foi testada num gateway de produção.

## Onde a próxima validação tem mais valor

1. Rode o ciclo num gateway de produção por algumas semanas e compare os vereditos das lições e as skills marcadas pelo resultado com uma revisão manual dos mesmos turnos.
2. Acompanhe o autopilot num gateway de longa duração que atende vários perfis, por vários dias: as passadas que o `status` mostra para cada perfil, a duração delas e a latência dos hooks enquanto uma passada roda.
3. Migre alguns perfis reais da 0.5.0 e confira com o `status` que cada um conta os seus turnos uma vez só e mantém as suas lições.
4. Revise os rascunhos do refletor contra as falhas de origem, além das três chamadas reais feitas até agora, e escolha um modelo de baixo custo para `auxiliary.evolution_reflector`.
5. Confira os bloqueios da guarda de runtime e as propostas do radar contra o que de fato aconteceu no host, para achar falsos positivos.
6. Compare a duração e a qualidade de pesquisas reais antes e depois dos planos. Use o mesmo conjunto de perguntas, valide as fontes e registre onde o orçamento deixou uma lacuna material.
7. Cruze falhas dos workers, sobreposição de horários e volume de fila. Faça uma mudança por vez e acompanhe latência, taxa de erro e acúmulo de trabalho.
8. Monte um conjunto controlado de cenários Linux com pressão de CPU, I/O e memória. Verifique o valor efetivo do controlador, o impacto no Hermes e o rollback com o agente e a unidade auxiliar em execução.
