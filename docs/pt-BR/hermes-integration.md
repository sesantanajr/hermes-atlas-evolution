# Atlas Evolution e as interfaces do Hermes

[English](../en-US/hermes-integration.md) | **Português (Brasil)**

A integração usa como referência a árvore do Hermes Agent 0.23.1 (commit `3b421578588243f920886e6fe79a6faa87ea026e`). Este documento lista o que o plugin registra no Hermes, o que ele lê de um perfil, qual configuração libera cada recurso, o que ele não faz e onde uma validação adicional é mais útil. [Release oficial](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.1) · [API pública de plugins](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/website/docs/developer-guide/plugins/public-api.md)

O plugin se apoia na API publicada de plugins: usa os métodos de `ctx` abaixo e só importa os módulos do Hermes `hermes_constants`, `hermes_cli.config`, `agent.redact` (`redact_sensitive_text`) e `agent.secret_scope`, todos listados na API pública de plugins do Hermes. Cada método opcional de `ctx` é consultado antes do uso, então um host que não o tenha ainda carrega o plugin, sem aquele recurso.

Algumas leituras olham módulos que o Hermes já carregou no processo, sem importá-los. Nenhuma delas faz parte da API publicada de plugins:

- a Proteção do Hermes pega a localização do pacote `hermes_cli` para saber onde está o código do Hermes;
- o radar de saúde lê a lista de plugins do gerenciador de plugins do Hermes (`hermes_cli.plugins`);
- o comando `hermes evolution` lê a versão do pacote `hermes_cli` já carregado para a checagem de atualização;
- os hooks de turno perguntam ao `agent.session_source` a origem real da sessão em andamento (um worker do Kanban roda com plataforma `cli`);
- o `status` pergunta ao `hermes_cli.plugin_isolation` se os plugins rodam num host de plugins;
- a checagem de configurações pergunta ao `hermes_cli.managed_scope` quais são os arquivos de configuração gerenciados pelo administrador;
- quando um serviço roda sem o `hermes` no `PATH`, o plugin procura o lançador `hermes` ao lado do pacote `hermes_cli` já carregado.

Quando um módulo não está carregado, aquela leitura é pulada e o plugin usa o que o payload do hook informa.

**As checagens do doctor do Hermes** são o único ponto que usa partes internas do Hermes diretamente: uma vez por dia, um processo curto e separado do próprio Python do Hermes importa o `hermes_cli.doctor` e chama o `DOCTOR_CHECKS` dele ([Manutenção](maintenance.md#o-doctor-do-próprio-hermes-uma-vez-por-dia)). Nada disso é importado no processo do plugin. Num Hermes sem `DOCTOR_CHECKS`, as checagens não rodam e a tela do Ambiente diz isso.

## O que o plugin registra

Ligá-lo depois pede `hermes gateway restart`; desligar vale na hora (o `check_fn` responde não). Um toolset registrado desligado apareceria como "system dependency not met" no `hermes doctor` |
| Skill `hermes-atlas-evolution:evolution-review` | `ctx.register_skill` | quando o host oferece o método |

| Tarefa auxiliar `evolution_reflector`, herdando de `compression` | `ctx.register_auxiliary_task` e, depois, `ctx.llm.complete_structured` | `reflector` está ligado quando o plugin carrega e o host oferece os dois. Ligado depois, espera o `hermes gateway restart`; desligado, para na próxima rodada de aprendizado |
| Formulário de configurações com 14 opções | `config_schema` no `plugin.yaml` | sempre; o Hermes grava os valores em `plugins.entries.hermes-atlas-evolution.settings` |

| Aba **Evolution** do dashboard (`/evolution`) e a API dela: `GET /api/plugins/hermes-atlas-evolution/snapshot` e, para o dono com login, `POST .../decide` | `dashboard/manifest.json`, `dashboard/plugin_api.py` | o dashboard a encontra sozinho na pasta do plugin; o Hermes recusa a API dela num perfil em que o plugin está desligado ([O painel no dashboard](#o-painel-no-dashboard)) |
| Thread em segundo plano `hermes-atlas-evolution-autopilot`, um daemon que faz a rodada | nenhuma; iniciada pelos hooks `post_llm_call`, `on_session_end` e `on_kanban_dispatch_tick`, e pelo relógio | `autopilot_minutes` não é 0 |
| Thread em segundo plano `hermes-atlas-evolution-clock`, um daemon que empurra a rodada 2 minutos depois de o plugin carregar e depois a cada 10 minutos | nenhuma; parada por meio do `ctx.on_unload` | `autopilot_minutes` não é 0 e o host oferece `on_unload` |

A maior parte das configurações vale em até um minuto, sem reiniciar ([O painel no dashboard](#o-painel-no-dashboard), Configurações). Quatro coisas são definidas quando o plugin carrega: quais hooks são registrados (`runtime_guard`, `tool_hints`), se as ferramentas do agente são registradas (`agent_tools`), a seção de prompt de um perfil que carregou com as lições desligadas e a tarefa do refletor. Cada rodada do autopilot e cada comando leem as configurações de novo.

**Duas cópias num perfil.** Quando o perfil também tem uma cópia ligada com o nome antigo `hermes-evolution`, o plugin não registra nada e avisa no log com o comando que remove a cópia antiga (`hermes plugins remove hermes-evolution`): as duas cópias observariam os mesmos turnos e gravariam no mesmo banco.

**A versão que um processo carregou.** Um processo de gateway ou de dashboard que carrega o plugin registra, no banco do plugin, a versão do plugin, o tipo do processo e quando ele começou, identificados pelo ID do processo, para que o `status` aponte um que ainda roda código antigo ([Status e aviso ao dono](evolution-loop.md#status-e-aviso-ao-dono)).

## Hooks

O manifesto declara os mesmos 16 hooks, e um teste compara as duas listas.

| Hook | O que o plugin faz com ele |
|---|---|
| `pre_tool_call` | Só com `runtime_guard` ligado. Roda a [Proteção do Hermes](#a-proteção-do-hermes): barra os comandos de terminal do agente que parariam o gateway, apagariam aquilo de que o Hermes em execução precisa, ou mudariam as configurações deste plugin ou o desligariam. Também guarda, só em memória, um hash do comando de cada chamada do tipo terminal, para saber depois se outro plugin o reescreveu. Não é registrado com a Proteção do Hermes desligada, nem onde o Hermes roda os plugins num host de plugins (veja a guarda). |
| `post_api_request` | Conta a chamada, os tokens e a duração por provedor e modelo. |
| `api_request_error` | Conta cada tentativa que falhou, classificada como limite de taxa, autenticação, timeout, upstream ou erro. |
| `post_auxiliary_call` | Conta chamadas auxiliares e falhas por tarefa. |
| `post_tool_call` | Conta o desfecho da ferramenta e a duração dela, classifica uma falha numa assinatura (como `rewritten_command` quando o `middleware_trace` do Hermes aponta uma alteração ou o comando que rodou difere do que o `pre_tool_call` viu), conta uma aprovação recusada por origem da sessão, conta a falha de novo quando o turno atendia o dono (veja [Quem é atendido](evolution-loop.md#quem-é-atendido)), cronometra turnos que usam ferramentas de pesquisa web e, com o refletor ligado, guarda um trecho mascarado de uma falha sem padrão fixo dos turnos do próprio dono. |
| `transform_tool_result` | Acrescenta a lição correspondente a um resultado que falhou quando `tool_hints` está em `true`, o que vem desligado: o Hermes só mantém a alteração do primeiro plugin num resultado de ferramenta. Numa sessão que não atende o dono, só entram lições de padrão fixo. Registrado só enquanto `tool_hints` está ligado e as lições não estão em `off`. |
| `pre_llm_call` | Descobre a superfície do turno e se ele atende o dono (um filho delegado pelo `parent_session_id` da mãe), inicia o cronômetro do turno, classifica em memória os sinais do dono e atribui uma correção do dono às skills do turno anterior. Não devolve contexto, a não ser uma vez por conversa: quando quem escreve se revela o dono (`owner_sender_ids`) numa conversa direta (DM, nunca um grupo, fio ou tópico) cujo prompt este processo montou só com lições de padrão fixo, ele devolve as lições que esse prompt deixou de fora (no máximo 5 linhas e 900 caracteres), que o Hermes junta à mensagem do usuário daquele turno. Nunca num chat em que outra pessoa escreveu. |
| `post_llm_call` | Fecha a medição de um turno de pesquisa e dá um empurrão no autopilot. |
| `on_session_end` | Registra o desfecho e a duração do turno e o desfecho de cada skill que ele carregou, e dá um empurrão no autopilot. |
| `on_skill_lifecycle` | Conta carregamentos, alterações e outros eventos do ciclo de vida das skills, e liga uma skill carregada ao seu turno. |
| `subagent_start` | Guarda, só em memória, qual sessão delegou cada filho, para o filho atender quem a mãe atendia, inclusive no prompt. |
| `post_compaction` | Conta a compactação, com os tokens antes e depois quando o Hermes os informa, para a leitura de compactação do radar e para o resumo, e leva o que o plugin sabe da sessão (quem ela atendia, a mãe de um filho) para o id que a compactação dá a ela. |
| `on_session_finalize` | Devolve no máximo um aviso curto por dia UTC sobre decisões pendentes, só para uma sessão das superfícies locais do dono (CLI, TUI, Desktop) que não seja de subagente. O Hermes 0.23.1 só mostra esse texto quando a CLI clássica sai (`shutdown`) ou começa uma sessão nova (`session_boundary`) e quando a TUI ou o Desktop fecham uma sessão (sem motivo informado); em qualquer outro caso o plugin não devolve nada e o aviso do dia não é gasto; as decisões pendentes aparecem no `status`, no resumo e no painel do dashboard. |
| `on_session_reset` | Um `/new` ou `/reset` encerrou uma sessão: descarta o que o plugin guarda na memória sobre a sessão que terminou (quem ela atendia, os filhos delegados, se o prompt dela foi contado, as lições do dono e as dicas de ferramenta dadas, as skills e as palavras do último turno). |
| `on_session_delete` | Uma sessão foi apagada ou arquivada: descarta o mesmo, para cada sessão citada. |
| `on_kanban_dispatch_tick` | Dá um empurrão no autopilot. O Hermes o dispara uma vez por tick do despachante do Kanban, a cada 60 segundos, por padrão, para o perfil do próprio gateway, e só onde o despachante roda dentro do gateway (`kanban.dispatch_in_gateway`). A thread do relógio cobre os outros perfis que um gateway atende. |

Um empurrão só compara dois relógios; a rodada em si roda na thread do autopilot (veja [O autopilot](evolution-loop.md#o-autopilot)). Nenhum callback bloqueia o turno quando falha: um hook nunca lança erro dentro de um turno, e uma falha é registrada no log no máximo uma vez por tipo de evento. As gravações dos hooks passam por uma conexão de banco por processo e perfil. Enquanto o banco está ocupado, uma atualização espera numa fila de até 512 entradas e é gravada junto com o próximo evento ou quando o plugin é descarregado. O excedente é contado e informado como `dropped_events`. A seção de prompt só lê o banco e conta a sua exibição pela mesma fila.

Na máquina de desenvolvimento, um evento de hook leva cerca de 0,1 ms. É uma medição numa única máquina, não uma garantia.

## A Proteção do Hermes

Com `runtime_guard` ligado (o padrão), o callback de `pre_tool_call` do plugin roda a Proteção do Hermes (`guard`). O Hermes o chama antes de cada chamada de ferramenta do agente, e uma diretiva de bloqueio substitui a chamada: a mensagem dela vira o resultado da ferramenta que o agente lê. A Proteção olha o argumento `command` de ferramentas do tipo terminal (`terminal`, `shell`, `bash`, `run_command`, `execute_command`), com o `workdir` delas, e o `data` que o `write` ou o `submit` do `process_manage` envia a um processo em segundo plano, que muitas vezes é um shell. Ela barra três tipos de comando.

| Tipo | Barrado | O que o agente recebe |
|---|---|---|
| `gateway_stop` | Linux: `systemctl` com `restart`, `stop`, `kill`, `try-restart`, `reload-or-restart`, `try-reload-or-restart`, `condrestart`, `force-reload` ou `disable --now` numa unidade `hermes-gateway`, inclusive a `hermes-gateway-<perfil>` de um perfil, a `hermes-gateway-<hash>` de uma pasta própria, uma instância e o sufixo `.service`; `service` com `restart` ou `stop` nessa unidade. macOS: `launchctl` com `kickstart -k`, `stop`, `bootout`, `unload`, `remove` ou `kill` no LaunchAgent `ai.hermes.gateway` ou `ai.hermes.gateway-<sufixo>`, citado sozinho, como `gui/<uid>/<rótulo>` ou pelo plist. Windows: `sc` ou `net` com `stop`, os cmdlets do PowerShell `Stop-Service`, `Restart-Service`, `Suspend-Service` e `Stop-ScheduledTask`, e `schtasks /End`, no serviço ou tarefa `Hermes_Gateway` ou `Hermes_Gateway_<sufixo>`. Uma palavra de comando com curinga (`sys*ctl`, `/usr/bin/sys?ctl`) é comparada com os comandos em que ela poderia se expandir, e um applet do busybox ou do toybox (`busybox kill`) conta como esse comando. Também `condstop`, `freeze` e `mask --now`, opções do systemctl com valor antes da ação (`--job-mode replace`, `-s KILL`, `-t service`, `-M`, `-H`), uma unidade dada como glob (`'hermes-gateway*'`) e, quando o comando cita o Hermes em qualquer ponto, uma unidade que o shell preenche (`$U`, `xargs`); e o `RestartUnit`, o `StopUnit` ou o `KillUnit` do systemd chamados numa unidade do Hermes por meio do `busctl`, do `dbus-send` ou do `gdbus`. Em qualquer sistema: `pkill`, `killall`, `taskkill` ou `Stop-Process` com um argumento que contenha hermes, e `pkill` ou `killall` cujo padrão seleciona o próprio processo do gateway (`pkill -f python`, `killall python3`, `pkill -f 'gateway run'`), comparado com o nome e a linha de comando do próprio gateway; `kill` do `$PPID` (o shell do agente é filho do Hermes) ou de `-1`; `kill` cujos ids de processo o shell preenche, num comando que procura o Hermes (`kill $(pgrep -f hermes)`, `pgrep -f hermes_cli \| xargs kill`, ``kill `pidof hermes` ``, `kill $(cat ~/.hermes/gateway.pid)`) ou seleciona o próprio processo do gateway (`kill $(pgrep -f 'gateway run')`, `ps aux \| awk '/gateway run/{print $2}' \| xargs kill`): o `pgrep` é comparado com a linha de comando do gateway com `-f` ou `--full` e com o nome do processo sem essa opção (`-x` exato), o `pidof` com o nome exato, e `grep`, `rg` ou `awk '/re/{...}'` só quando leem uma lista de processos de um pipe (sem arquivo para ler). Valores de opções (`-u root`, `-m1`) não são padrões de busca, e um padrão que casa com o texto vazio é ignorado, então `kill $(cat app.pid)`, `kill $(pgrep -u root worker)` e `kill $(grep -o '[0-9]*' app.pid)` passam; `hermes gateway stop`, `restart` e `uninstall`, `start --all`, `run --replace` e `install --force`, com opções globais em qualquer posição e um grupo ou uma ação que o shell preencha (`hermes $G restart`). O comando `hermes` conta por todos os nomes com que ele roda: `hermes-agent`, `python -m hermes_cli.main` (a forma da própria unidade do gateway), `python -m hermes_cli`, o `python .../bin/hermes` de um ambiente virtual, `uv run hermes`, `uvx hermes` e `npx hermes` | o comando cortaria os turnos em andamento, inclusive este; não tente de outra forma; diga ao dono que é preciso reiniciar e por quê; o dono roda `hermes gateway restart` no próprio terminal, e esse comando mostra os turnos ainda em andamento e pergunta antes de interrompê-los |
| `runtime_removal` | `rm`, `rmdir`, `unlink`, `shred`, `mv` (as origens, também com `-t` ou `--target-directory`) e, no Windows, `del`, `erase`, `rd`, `Remove-Item` e `Move-Item`, ou `find` com `-delete` ou com `-exec` rodando `rm`, apontados para um caminho protegido, para uma pasta que contenha um deles ou com um glob que case com um deles, depois da expansão de chaves do shell (`mv ~/.hermes{,.old}`); qualquer coisa dentro de uma árvore protegida (`rm -rf venv/lib`, `rm -rf venv/*`); um `xargs rm` alimentado por um comando que cita um caminho protegido (`ls -d <caminho> \| xargs rm -rf`); e o `hermes profile delete`, que apaga um perfil e para o gateway dele. Seja qual for o verbo: gravar, truncar ou mudar os atributos dentro do interpretador em execução ou de uma árvore protegida (`truncate`, `dd of=`, `tee`, um redirecionamento, `chmod`, `chown`, `chgrp`, `ln -sf`, `rsync --delete`, e `cp`, `mv` ou `install` para dentro dela), e `chmod`, `chown`, `chgrp`, `ln` ou `rsync --delete` apontados para a pasta do perfil, a raiz do Hermes ou uma pasta acima delas ou acima de uma árvore protegida, também depois de um `cd` ou por uma atribuição literal `VAR=` anterior no comando (cópias comuns continuam permitidas: veja abaixo da tabela) | o comando apagaria ou moveria esse caminho, e o Hermes pararia de funcionar até alguém consertar à mão; remover isso fica para o dono, no próprio terminal, com o Hermes parado |
| `plugin_settings` | `hermes config set` ou `unset` da seção `plugins` (os plugins que o Hermes liga, desliga ou isola) e de `plugins.entries.hermes-atlas-evolution` (ou o nome antigo `hermes-evolution`), mas não do `plugins.entries.<id>` de outro plugin; `hermes config edit`; `hermes plugins disable`, `remove`, `rm`, `uninstall` ou `trust` do `hermes-atlas-evolution`, e `hermes plugins install` de uma origem com esse nome, que substituiria o código dele; remover ou mover a própria pasta do plugin ou qualquer coisa dentro dela; um comando que grava um `config.yaml` do Hermes (`sed -i`, `perl -i`, `yq -i`, um redirecionamento, `cp`, `tee`, uma linha de Python que o despeja ou grava) e cita a seção de plugins, este plugin ou uma das configurações de confiança dele; um comando que substitui um `config.yaml` do Hermes, o do perfil, o da raiz ou o de outro perfil (`cp`, `mv` ou `install` por cima dele, `ln`, `truncate`, `dd`, `tee`, um redirecionamento `>`), mesmo sem citar nenhuma configuração de plugin, enquanto acrescentar ao fim dele com `>>` só conta quando o comando cita as configurações do plugin; e qualquer gravação, truncamento ou mudança de atributos dentro da própria pasta do plugin. Opções globais que levam valor, como `-p <perfil>`, são lidas onde estiverem, como o Hermes as lê, e uma palavra que o shell preenche na chave, na ação ou no nome (`$VAR`, `$'...'`, uma substituição de comando) conta como essa mudança | o comando mudaria quem conta como o dono ou as proteções do plugin, ou desligaria o plugin; só o dono decide isso, no próprio terminal; não tente de outra forma; diga ao dono o que você queria mudar e por quê |

O trabalho comum continua permitido: gravar ou copiar normalmente para a pasta pessoal, para a raiz do Hermes ou para uma pasta compartilhada como `/usr/local/lib` (`cp relatorio.pdf` para a sua pasta pessoal, `cp notas.md` para dentro de `.hermes/`) nunca é barrado; só o que muda o interior de uma árvore protegida, ou as permissões, o dono, os links ou o conteúdo de uma pasta acima dela, é.

Os caminhos protegidos são aqueles de que o Hermes em execução precisa: os prefixos do interpretador Python em execução e do ambiente dele, o interpretador base para o qual um ambiente virtual aponta (a linha `home` do `pyvenv.cfg` e o `sys._base_executable`), o código do Hermes (a pasta que contém o pacote `hermes_cli`), a raiz do Hermes e este perfil. Cada um é protegido tanto como está escrito quanto resolvido, então um link conta pelos dois nomes: o link `cpython-3.11-...` do uv para `cpython-3.11.16-...`, ou um `~/.hermes` que aponta para outro disco. Um caminho com menos de três componentes, como `/usr`, nunca entra na lista, então um interpretador do sistema cujo prefixo é `/usr` não fica coberto.

Na maioria deles, só o próprio caminho e as pastas acima dele são protegidos. As **árvores protegidas** são protegidas também por dentro, porque apagar qualquer parte delas faz o Hermes parar: o ambiente virtual em que o Hermes roda, uma pasta de runtime Python só dele (uma cujo nome diz python, como `~/.hermes/tools/python-3.14...`), a biblioteca padrão e os pacotes Python e ambientes virtuais no topo do código do Hermes (`hermes_cli`, `gateway`, `agent`, `venv`, ...). Um prefixo compartilhado como `/usr/local` nunca é uma árvore; só a biblioteca padrão dentro dele é. O interior da raiz do Hermes e do perfil continua aberto ao agente, que trabalha ali. A própria pasta do plugin também é protegida por dentro, como um bloqueio `plugin_settings`: removê-la ou mexer nela desliga o plugin.

Como um comando é lido:

- Ele é dividido em `;`, `&&`, `||`, `|`, `&`, parênteses e quebras de linha, e em cada parte só conta a palavra do comando, depois das palavras do shell que abrem ou negam um comando composto (`if`, `then`, `elif`, `else`, `while`, `until`, `do`, `!`, `{`, `coproc`), de atribuições de variáveis, dos multiplexadores de applets `busybox` e `toybox` e de invólucros como `sudo` (com as opções longas dele), `env`, `nohup`, `timeout`, `nice`, `ionice`, `stdbuf`, `exec`, `command`, `builtin`, `time`, `chrt`, `doas`, `setsid`, `systemd-run` com as opções dele (inclusive temporizadores como `--on-active 30`), `runuser`, `watch`, `flock`, `xargs`, `taskset`, `unshare`, `nsenter`, `chroot`, `strace`, `ltrace`, `uv run`, `uvx`, `pipx run`, `npx` e `rtk run` (ou `rtk err` e os outros subcomandos do `rtk` que rodam um comando). As palavras que o `xargs` acrescenta a partir da entrada contam como palavras que o shell preenche. Uma atribuição literal feita antes no mesmo comando (`X=systemctl`, `export X=~/.hermes`, também com `declare`, `local`, `typeset` ou `readonly`) é posta no lugar de `$X` e `${X}` depois dela; qualquer outra variável continua desconhecida. Uma palavra de comando com curinga é comparada com os comandos que a Proteção examina. Um comando citado nos argumentos de outro, como num `echo`, não é um comando.
- Um comando passado como um único texto é lido, até 8 níveis para dentro, quando vai para um shell (`bash`, `sh`, `zsh`, `dash`, `ksh`) com `-c` ou um grupo de opções que o contenha, como `-lc` ou `-ec`, para `su`, `runuser`, `script` ou `flock` com `-c`, `--command` ou `--command=` (também `script -qc`), para o `eval`, para o PowerShell (`powershell`, `pwsh`) com `-Command` ou `-c`, para o `cmd` com `/c`, para o `env` com `-S` ou `--split-string` e para o `watch`, que roda os operandos como um texto de shell. Também são lidos assim as substituições de comando `$(...)` e `` `...` ``, inclusive dentro de aspas duplas, onde elas continuam rodando; o comando que o `find -exec` roda; o comando passado ao `ssh localhost` (ou `127.0.0.1`, `::1`); o que um shell lê como script pela entrada padrão: os here-documents dele (`bash <<EOF`), uma here-string (`<<<'…'`, também colada ao shell), as palavras de um `echo` ou `printf` passadas a ele por pipe, e um here-document que um `cat` passa a ele por pipe (`cat <<EOF | bash`); e os literais de texto do programa embutido de um interpretador (`python -c`, `perl -e`, `ruby -e`, `node -e`, `php -r`), cada um sozinho e todos juntos, que é como se lê um `subprocess.run(['systemctl', ...])`. Um comando executado a partir de um arquivo de script, ou via `ssh` para outro host, não é examinado.
- O corpo dos outros here-documents é texto que vai ser gravado em algum lugar, não um comando que roda agora, então é ignorado, assim como os comentários do shell.
- `~`, `~<nome de usuário do dono>`, `$HOME` e `$HERMES_HOME` (este perfil) são expandidos no começo de um caminho, também nas formas `${NOME}`, `${NOME:?...}` e `${NOME:-...}`, assim como `%USERPROFILE%`, `%LOCALAPPDATA%`, `%APPDATA%` e as formas `$NOME` e `$env:NOME` deles, quando estão definidos. No Windows, `C:\x`, `C:/x` e o `/c/x` do Git Bash são o mesmo caminho, comparado sem diferenciar maiúsculas. Um caminho relativo é tomado a partir do `workdir` da ferramenta de terminal, ou de um `cd` anterior no mesmo comando, quando essa pasta é conhecida; fora isso, ele não é checado, nem um que começa com outra variável.
- Qualquer dúvida deixa o comando passar: uma aspa sem par, uma ferramenta que não é do tipo terminal. Um comando longo é lido nos primeiros 20.000 caracteres, depois de cortados os comentários e os corpos de here-document, então enchimento não empurra um comando para fora da checagem. O trabalho com comandos dentro de comandos tem um orçamento só (2.000 checagens): qualquer comando de até 20.000 caracteres leva menos de 0,7 segundo, bem abaixo dos 30 segundos depois dos quais o Hermes bloqueia uma ferramenta.

A checagem é uma função pura sobre o comando: não lê nem grava nada, e o tamanho da entrada é limitado. O callback nunca lança erro, porque o Hermes trata como bloqueio um `pre_tool_call` que falha ou estoura o tempo: uma falha interna deixa o comando passar e fica no log, uma vez por processo, com os detalhes. Cada bloqueio é contado por tipo na `guard_daily` (o comando não é gravado), e o `hermes -p <perfil> evolution status` e o resumo mostram as contagens. A mensagem segue o idioma do plugin. O terminal do próprio operador não é afetado.

A guarda foi testada contra cerca de 350 comandos escritos para contorná-la. Os que ela ainda deixa passar são comandos que afetam o host inteiro (`reboot`, `systemctl isolate`), texto enviado por pipe a um shell ou a um interpretador a partir de um arquivo, de um download ou de outro programa, texto codificado decodificado para um deles, um caminho de outro usuário ou um caminho relativo que ela não consegue situar, e comandos agendados pelo `at` ou por um arquivo de script. Esses ficam para a política de aprovação do próprio Hermes.

Essa guarda existe porque, num servidor real, o agente reiniciou o próprio gateway com `systemctl` 13 vezes numa semana, 12 delas a partir de um único chat num único dia, cortando os turnos em andamento, e uma vez apagou o runtime Python que a unidade do gateway usava, o que deixou o Hermes fora do ar por cerca de uma hora. O mesmo histórico também tinha um reinício agendado por meio do `systemd-run`, e por isso a Proteção olha o comando que está por trás dos invólucros (wrappers) acima. O `hermes gateway restart` do agente também é barrado: sem terminal, o Hermes 0.23.1 se recusa a reiniciar enquanto há sessões rodando, e o `--yes` dele as interromperia, então o reinício fica com o dono. A Proteção do Hermes é uma rede de proteção para esses casos, não uma sandbox: a política de aprovação do próprio Hermes para comandos de terminal continua valendo.

**Guarda desligada ou host de plugins.** Com `runtime_guard: false`, ou onde o Hermes roda os plugins num processo separado (`plugins.isolation: host`), o plugin não registra nenhum `pre_tool_call`, então nem a Proteção do Hermes nem a checagem de um comando que outro plugin reescreveu rodam ali (o rastro de middleware do Hermes continua marcando as reescritas feitas por ele). Cada `pre_tool_call` vira uma chamada ao host, e o Hermes bloqueia uma ferramenta cujo `pre_tool_call` falha: um host que caísse bloquearia todas as ferramentas do perfil. O `status` diz que a guarda está desligada por esse motivo.

## O painel no dashboard

O plugin acrescenta uma aba, **Evolution**, ao dashboard do Hermes e ao Hermes Desktop, em Plugins na barra lateral. O Hermes a encontra sozinho na pasta `dashboard/` do plugin (`manifest.json`, um script sem etapa de build, uma folha de estilo que segue as cores do tema do dashboard e `plugin_api.py`); não é preciso configurar nada. Ela funciona para o perfil do próprio dashboard e para os outros perfis escolhidos nele.

| Aba | Mostra, e deixa você fazer |
|---|---|
| Visão geral | Lições ativas, o que espera a sua decisão, chamadas de ferramentas e turnos com as taxas de erro, vetos da Proteção do Hermes em 7 dias e a última rodada. Cada lição que espera, com o texto exato, **Aprovar** e **Rejeitar**, e **Aprovar todas**, que antes lista cada frase que vai aprovar; uma lição proposta pelo agente fica de fora e é aprovada sozinha |
| Lições | Todas as lições com situação, origem, ferramenta, frase e efeito medido; aprovar ou rejeitar uma que espera, aposentar uma ativa, reativar uma aposentada |
| Propostas | Propostas abertas agrupadas em mudanças que o plugin aplica, lições, mudanças que você aplica e observações, cada uma com o risco, o que foi visto, o que fazer, o que aplicá-la faz e o desfazer. **Aplicar agora** aplica uma mudança com o próprio comando do Hermes, e **Aplicar todas** aplica de uma vez todas as que podem ir em lote (nunca desligar um plugin nem mover um cache); **Dispensar** esconde uma observação por 30 dias, e ela só volta se a situação continuar; uma lição é aprovada ou rejeitada. Uma mudança que o plugin não aplica mostra o comando, com Copiar, para você rodar no seu terminal |
| Saúde | A saúde do Hermes e o sistema operacional: o gateway, o disco livre, a memória, o swap, o banco de sessões, versões antigas de ferramentas, atualizações esperando e um reinício que o sistema espera; o que pede atenção, e o comando do menu do terminal para as ações ([Manutenção](maintenance.md)) |
| Ambiente | Para cada perfil em uso, a última checagem do doctor do próprio Hermes (problemas, avisos e quando), e depois todos os perfis deste Hermes e o que arrumar neles, cada item com o comando ([O ambiente](evolution-loop.md#o-ambiente)) |
| Configurações | Todas as opções do formulário de configurações, com **Aplicar a configuração recomendada** (lições em `auto`, refletor ligado e os canais de chat que são seus por construção), e **Quem é você nos chats**: cada canal dos últimos 30 dias com os remetentes, os sugeridos marcados |
| Histórico | Todas as decisões, do terminal e do painel, da mais recente para a mais antiga, com **Desfazer** |
| Resumo | O resumo de `hermes -p <perfil> evolution report`, de 7, 14 ou 30 dias |
| Status | A página de `hermes -p <perfil> evolution status` |

**Quem pode decidir.** Toda requisição é autenticada antes pelo dashboard. Uma decisão só é aceita de um dono com login (senha ou OAuth, que o Hermes liga quando o `dashboard.public_url` é um endereço público) ou da permissão que o Hermes Desktop envia, e nunca de uma requisição que traz o token de sessão do dashboard em qualquer forma (o cabeçalho dele, `?token=` ou `Authorization: Bearer`, a forma antiga do Hermes). Como o plugin sabe disso depende de onde o Hermes roda as rotas:

- **O perfil do próprio dashboard** roda no processo do dashboard, atrás da porta de login do Hermes. O painel aceita a sessão que a porta verificou (`request.state.session`), menos uma verificada pelo token de sessão de implantação (`HERMES_DASHBOARD_SESSION_TOKEN`), que não é o login de uma pessoa. Num host que não publica a sessão verificada, o cookie de login conta pelo nome, em cada forma que o Hermes dá a ele: `hermes_session_at` por HTTP, `__Host-hermes_session_at` por HTTPS (um endereço público atrás de um proxy), `__Secure-hermes_session_at` sob um prefixo de caminho, com `_<gateway>` no Webapp do gateway.
- **Todo outro perfil** escolhido no dashboard roda a própria cópia do plugin no plugin host daquele perfil. O Hermes encaminha a requisição para lá sem nenhuma credencial (nem cookie, nem token), com um veredito que é o mesmo para um login e para o token do dashboard aberto, e sem as variáveis que diriam como o dashboard admite as pessoas. Por isso o plugin host nunca decide: responde só leitura, com o motivo `other_profile`. O painel então pergunta ao plugin no processo do próprio dashboard, com `?profile=current` (o perfil do dashboard, para o Hermes) e `target=<o perfil na tela>`, e esse processo lê e decide pelo perfil com a mesma regra de login acima, quando o Atlas Evolution está instalado e ativado nele (`plugins.enabled` no `config.yaml` dele); um nome que não é perfil deste Hermes, um link ou um caminho fora dele é recusado. Isso exige o plugin ativado também no perfil do próprio dashboard; sem ele, os outros perfis ficam só leitura no painel e são decididos pelo menu do terminal.

Um dashboard sem login entrega o token de sessão a quem abrir a página, inclusive o terminal do agente, então ali o painel fica só leitura, diz por quê e mostra o comando do menu do terminal no lugar; o retrato então deixa de fora os ids dos remetentes dos canais de chat e o texto das lições escritas por você, pelo refletor ou pelo agente (lições, lições que esperam, propostas, o resumo), que aparece como "(texto oculto: leia no seu terminal)", como o terminal faz no shell de um agente. Um erro inesperado responde `unexpected` com uma frase simples; os detalhes vão só para o log do dashboard. Uma decisão também precisa do cabeçalho `X-Atlas-Evolution: 1`, que uma página de outro site não consegue enviar sem o navegador perguntar antes ao dashboard. A Proteção do Hermes barra os comandos do agente que chamam a rota de decisões, seja qual for a grafia do endereço (escapes com `%`, `/./`, `/../`, aspas, um nome preenchido pelo shell). Um valor que o plugin não usaria como veio (`autopilot_minutes: 5`, um id de remetente que não é texto) é recusado antes de qualquer gravação, e um `settings.json` quebrado nunca derruba o painel: ele cai para o padrão como no gateway e o painel avisa.

**O que uma decisão faz.** O mesmo código decide no terminal e no painel (`decisions.py`), e cada decisão vai para um registro (`decision_log`: ids, situações, valores de configuração e impressões digitais, nunca o texto das lições ou da memória). **Aprovar todas** envia a lista exata de lições mostradas, cada uma com uma impressão digital da frase, e só aprova as que continuam esperando com essa mesma frase. **Desfazer** só volta atrás enquanto o que a decisão mudou continua como ela deixou: uma aprovação volta a esperar e a medição dela é descartada, uma aposentadoria é desfeita ativando a lição de novo, uma configuração recebe o valor anterior, e uma entrada retirada da memória do Hermes volta a partir da cópia guardada (só pelo menu do terminal ou pelo desfazer do painel).

**Configurações.** O painel e o menu do terminal as gravam com o próprio comando público do Hermes, `hermes --profile <nome> config set plugins.entries.hermes-atlas-evolution.settings.<chave> <valor>` (o Hermes confere a chave, pega a trava da configuração e grava de forma atômica), no `config.yaml` do perfil, depois de conferir cada valor pelas regras do próprio plugin. O gateway em execução aplica a mudança em até um minuto, sem reiniciar: cada hook e o relógio do plugin comparam os horários de modificação do `config.yaml` e do `settings.json` no máximo a cada 30 segundos e só os leem de novo quando mudaram. Quem conta como o dono, o modo das lições, desligar o refletor e o limite dele, o idioma, os sinais do dono, o limite de turno lento, o intervalo do autopilot e o `fleet_managed` valem na hora. Algumas configurações esperam o `hermes gateway restart` (no terminal: a próxima sessão): `runtime_guard` e `tool_hints`, que decidem quais hooks o Hermes chama, `agent_tools` quando é ligado (desligá-lo vale na hora), e `reflector` quando é ligado depois de um carregamento com ele desligado (a tarefa auxiliar dele é registrada no carregamento). O painel e o `status` listam as que esperam, menos o `agent_tools`, comparando com o que este carregamento registrou. Um perfil que carregou com as lições desligadas também fica sem seção de prompt até a próxima carga. O Hermes também recarrega os plugins num gateway em execução quando um é ligado, desligado ou atualizado pelo Desktop.

A API tem duas rotas: `GET /api/plugins/hermes-atlas-evolution/snapshot?days=1..35&lang=en|pt` e `POST /api/plugins/hermes-atlas-evolution/decide`. Elas rodam nas threads de trabalho do dashboard, então o banco nunca segura o loop de eventos dele; enquanto o banco está ocupado elas respondem 503 e o painel avisa. O painel fala inglês ou português do Brasil: a configuração `language` do plugin quando ela é `en` ou `pt`; com `auto`, o idioma escolhido para o perfil no Hermes (`HERMES_LANGUAGE` ou `display.language`), depois o idioma do dashboard, depois o idioma do sistema da máquina e, por fim, inglês. Tudo, inclusive o texto das lições, é exibido como texto, nunca como marcação. Com `plugins.isolation: host`, o Hermes atende as rotas pelo host de plugins.

## O refletor e o acesso a modelos do Hermes

O refletor é a única parte do plugin que envolve um modelo de IA, e vem ligado. Quando `reflector` está ligado no carregamento, o plugin registra a tarefa auxiliar `evolution_reflector` com `inherit_from="compression"`: ela parte do prazo e de outras configurações da tarefa de compressão, e só recebe também o provedor e o modelo dela depois que você autoriza (`plugins.entries.hermes-atlas-evolution.llm.allow_task_override: true`; sem isso vale a rota padrão do Hermes para tarefas auxiliares). Você pode dar a ela provedor e modelo próprios em `auxiliary.evolution_reflector`, na configuração do perfil. Uma rodada feita dentro do Hermes (pelo autopilot, pelo `hermes -p <perfil> evolution learn` ou pela receita semanal) então chama `ctx.llm.complete_structured` com essa tarefa, um esquema JSON, no máximo 300 tokens de saída e prazo de 60 segundos. O Hermes resolve o provedor, envia a requisição e a contabiliza; o plugin não abre conexão, e nenhuma transação do plugin fica aberta durante a chamada. Quando o host não oferece acesso a modelos para plugins, ou enquanto `lessons` está em `off`, o ciclo roda sem rascunhos. Três chamadas reais pelo Hermes em produção (provedor DeepSeek, cerca de 600 tokens e cerca de 2 segundos cada) geraram três rascunhos em português. O que é enviado e o que é aceito de volta está descrito em [O ciclo de evolução](evolution-loop.md#o-refletor).

## O que o plugin não faz no Hermes

- Nunca arquiva, desfaz, edita ou cria uma skill. A única mudança em skills é `hermes curator lock` (e `unlock` para desfazer): na sua tecla, ou sozinho no Modo Auto para uma skill que o curador reescreve sem parar.
- Nunca muda uma configuração do Hermes além das próprias (`plugins.entries.hermes-atlas-evolution.settings.*`, por `hermes config set`, quando você muda uma). Uma proposta que mudaria outra configuração aparece como um comando `hermes config`.
- Memória do Hermes: só remove uma entrada dita, exatamente o mesmo texto, no `MEMORY.md` e no `USER.md` (sozinho nos Modos Assistido e Auto, nunca a última cópia), ou a entrada que você escolhe, depois de guardar uma cópia do arquivo; não lê nada além das contagens de estrutura acima.
- Não reescreve um prompt já em uso e não muda argumentos de ferramentas. As únicas mudanças no que o agente vê são as lições no começo da sessão, a frase juntada ao resultado de uma ferramenta que falhou com `tool_hints` ligado, e, uma vez por conversa direta em que quem escreve é o dono, as lições que o prompt daquele chat deixou de fora, juntadas à mensagem do dono.
- Não para, não reinicia e não mata nada. O único serviço que ele inicia é o do gateway, logo depois de repará-lo, e só quando nenhum gateway deste Hermes está rodando. Fora da configuração do Hermes, o único arquivo que ele edita é o desse serviço (com uma cópia guardada, desfeito com `care undo-gateway`). A Proteção do Hermes só recusa um comando; nunca roda um.
- Não grava no histórico do Hermes: o `state.db` e os logs são abertos só para leitura.
- Outros perfis: no Modo Auto, a partir do perfil que cuida do Hermes inteiro, ele se instala num perfil usado nos últimos 7 dias que nunca o teve (nunca onde você o removeu: a pasta de dados `evolution/evolution.sqlite3` fica e marca isso), mantém a cópia deste plugin em cada perfil no commit dele, e move a pasta de uma instalação que falhou (`plugins/.install-*`) para a lixeira dele. Só na sua tecla, uma proposta por vez: desligar um de dois plugins e mover para a lixeira um cache de pacotes que se refaz sozinho (`uv`, `pnpm`, `npm`, `pip`, `yarn`, `huggingface`, `piper-voices`). Qualquer outra pasta de cache (os logins do navegador, os anexos das conversas, as imagens geradas…) nunca é movida: o item dá um comando `du` para olhar dentro. Todo o resto ali (remover ou atualizar um plugin, arquivar uma skill, enxugar pontos de restauração) é um comando para você. Antes de qualquer mudança ele lê aquele perfil de novo do disco, e, para um achado do doctor, roda aquela checagem de novo. Num perfil com o `fleet_managed` desligado ele não muda nada sozinho.
- Não aprova, nega nem contorna aprovações do Hermes, e nunca transforma uma aprovação recusada em conselho.
- Não registra middleware, provedor, provedor de memória, padrão de redação ou idioma, e não substitui nada no núcleo do Hermes.
- A única tarefa agendada do Hermes (cron) que ele cria é o resumo semanal, na sua tecla (`schedule-digest`), como um script sem agente; a receita do `report --schedule-spec` é impressa para você. Ele não cria nenhum cartão de Kanban.
- Não envia telemetria. O único acesso à rede do próprio plugin é o `git ls-remote` do próprio repositório, para manter atualizada a cópia de cada perfil (o Modo Auto, a partir do líder, e o `update`). O Hermes baixa o plugin do GitHub quando o Modo Auto o instala ou sincroniza em outro perfil, e o `hermes doctor` (seu clique) chama os provedores. As checagens diárias do doctor pulam toda checagem que usa a rede. Um modelo só é chamado pelo refletor, por meio do Hermes.
- Não deixa o agente decidir: as decisões se recusam a rodar no shell de um agente.

## Notas de instalação

- **Pelo GitHub.** `hermes plugins install sesantanajr/hermes-atlas-evolution --enable` no perfil padrão, `hermes -p <perfil> plugins install sesantanajr/hermes-atlas-evolution --enable` num perfil com nome. Instalar com `--enable` faz um gateway em execução carregar o plugin na hora; a seção de prompt vale a partir da próxima sessão. Confira com `hermes plugins doctor --ci hermes-atlas-evolution` e `hermes -p <perfil> evolution status`.
- **Em todo perfil que você usa.** O Hermes carrega os plugins por perfil, mesmo quando um único gateway atende vários perfis. Para todos os perfis com nome: `for p in $(ls ~/.hermes/profiles); do hermes -p "$p" plugins install sesantanajr/hermes-atlas-evolution --enable; done`, mais o comando do perfil padrão. O `hermes -p <perfil> evolution status` lista todos os perfis da mesma raiz do Hermes, com o comando de instalação para cada perfil movimentado que não tem o plugin.
- **Atualização.** O `hermes plugins update hermes-atlas-evolution`, com `-p <perfil>` para cada perfil com nome, baixa o código novo, mas um gateway em execução continua com o código que carregou: o Hermes recarrega um gateway em execução na instalação, ao ligar e ao desligar um plugin, e numa atualização feita pelo Hermes Desktop, pelo dashboard ou pelo `/plugins update` num chat, não nessa atualização pela linha de comando. Termine com `hermes gateway restart`; se ainda houver algo rodando, ele lista o que é e pergunta, em inglês, `Interrupt them and restart the gateway? [y/N]`. O `status` aponta um processo de gateway ou de dashboard que ainda roda uma versão mais antiga, em sistemas POSIX.
- **Nome antigo.** Se um perfil ainda tem o plugin com o nome antigo `hermes-evolution`, rode `hermes plugins remove hermes-evolution` e instale o `sesantanajr/hermes-atlas-evolution`; o `status` lista esses perfis com esses comandos.
- **Manualmente.** Copie a pasta inteira do plugin, com o `plugin.yaml` na raiz, para `<HERMES_HOME>/plugins/hermes-atlas-evolution/` e execute `hermes plugins enable hermes-atlas-evolution`. Um link para uma cópia de desenvolvimento ali também funciona e conta como instalado. A pasta padrão do Hermes no Linux é `~/.hermes`. Instalações Windows geralmente usam `%LOCALAPPDATA%\hermes`. Ao habilitar, um gateway em execução carrega o plugin; se o Hermes disser que nenhum gateway respondeu, rode `hermes gateway restart`.
- **Isolamento em host.** Com `plugins.isolation: host`, o Hermes ignora `register_cli_command`; use `python -m hermes_atlas_evolution --home <perfil> ...` a partir da pasta do plugin. A Proteção do Hermes fica desligada ali (veja [A Proteção do Hermes](#a-proteção-do-hermes)). O refletor não roda nesse executor independente; os trechos em espera ficam para a próxima rodada feita pelo Hermes. O autopilot e o refletor não foram verificados com isolamento em host. Veja [Fora do Hermes](evolution-loop.md#fora-do-hermes).

### Capa e o catálogo de plugins

O Hermes só mostra a capa de um plugin para os itens do catálogo curado de plugins dele, a pasta `plugin-catalog/` do repositório hermes-agent, revisada pela Nous Research ([envio ao catálogo](https://hermes-agent.nousresearch.com/docs/developer-guide/plugins/catalog-submission)). A capa dele é o [banner.jpg](https://raw.githubusercontent.com/sesantanajr/hermes-atlas-evolution/assets/banner.jpg), de 1280×640.

## Compatibilidade e limites

Exige Hermes Agent 0.23.1 ou superior e Python 3.11 ou superior.

**Verificado na máquina de desenvolvimento** (medições, não garantias):

- Mais de 700 testes unitários e de ponta a ponta contra um Hermes simulado, também com o Python do Hermes e a função nativa de mascaramento de segredos dele. Eles ficam no ramo `tests` do repositório, então a cópia que o Hermes instala em cada perfil leva só o que o Hermes carrega. A integração contínua os roda no Linux (Python 3.11 a 3.14), no macOS e no Windows, com o ruff, uma compilação com Python 3.11, as checagens de sintaxe do instalador e do script do painel e um teste de fumaça da CLI avulsa; os testes que são POSIX por desenho (bits de permissão, a checagem de processo vivo, runtimes com link simbólico) são pulados no Windows.
- A varredura de instalação do próprio Hermes (`plugin-guard-v15`, a do Hermes 0.23.2 e do seu ramo principal em 2026-11-17, e a mais antiga `plugin-guard-v12`) dá à 0.12.0 o veredito `safe`, então uma instalação sem terminal, como a do próprio plugin em outro perfil, nunca espera uma confirmação. O `hermes plugins validate` acrescenta duas notas que não bloqueiam nada: a ferramenta do agente e o `transform_tool_result` são declarados, mas registrados só enquanto as suas configurações estão ligadas.
- A leitura do histórico, numa cópia de um perfil real com 276 sessões: 373 turnos e 3.566 chamadas de ferramentas, exatamente uma por mensagem lógica da janela (contar cada cópia que a compactação do Hermes guarda daria 6.731), em menos de um segundo. Das 152 falhas, 129 vieram dos turnos do próprio dono.
- As checagens do doctor do Hermes: cerca de 7 segundos por perfil no Hermes 0.23.1, sem rede.
- O autopilot (uma reserva por perfil, reserva que expira, nova tentativa, fixação do perfil, um `learn` manual esperando a rodada em andamento): verificado nos testes e na CLI. O relógio, a liberação de uma rodada na saída do processo, a checagem de código antigo e a proteção contra duas cópias num perfil: verificados nos testes.
- Medido uma vez e não repetido com o código atual: cerca de 0,1 ms por evento de hook; com um `state.db` de cerca de 170 MB, `learn` cerca de 0,3 s e 25 MB, `report` cerca de 0,35 s.

**Verificado em produção:** três chamadas reais do refletor pelo Hermes (provedor DeepSeek, cerca de 600 tokens e cerca de 2 segundos cada) geraram três rascunhos em português.

**Não verificado:** vereditos de lições e skills pelo resultado ao longo de semanas de uso real (ainda não há resultados de campo), o relógio e a checagem de código antigo num gateway de longa duração que atende vários perfis, a remoção de uma cópia com o nome antigo num gateway em execução, as checagens diárias do doctor em versões do Hermes que não a 0.23.1 (elas chamam o `DOCTOR_CHECKS` interno do Hermes, que pode mudar), o empurrão do Kanban no autopilot (que depende de `kanban.dispatch_in_gateway`), o autopilot e o refletor com `plugins.isolation: host`, outras versões do Hermes, e um gateway do Hermes rodando no macOS ou no Windows (os testes rodam lá, o gateway não).

**Limites**

- Os vereditos comparam dois períodos; são correlações, não experimentos controlados.
- Só as lições ligadas a uma falha (derivadas e do refletor) têm efeito medido.
- O banco só ganha tabelas e colunas, então uma cópia mais antiga do plugin ainda o abre. Uma cópia muito antiga o recusa; para voltar até lá, restaure um backup do `evolution.sqlite3` ou apague o arquivo.
- O autopilot precisa de um empurrão: um turno, o relógio ou o tick do Kanban. Um host sem `on_unload` não tem relógio, então ali um perfil parado espera o próximo turno.
- A leitura do histórico só pega o que o Hermes registrou antes de o plugin começar a observar o perfil, até 14 dias para trás. Ela não reprocessa chamadas ao modelo nem tokens, mede as chamadas de ferramenta só de forma aproximada (do pedido ao resultado) e não reconhece um comando que outro plugin reescreveu; um binário que falhou ao vivo depois de uma reescrita fica fora das lições a partir daí.
- Com `plugins.isolation: host` não existe `hermes evolution`: use `python -m hermes_atlas_evolution --home <perfil> ...` (que só lê o `config.yaml` com o PyYAML; sem ele, o modo é Manual). As receitas de cron dependem da CLI do Hermes; uma rodada pelo executor independente não rascunha nada e mantém os trechos em espera para uma rodada feita dentro do Hermes.
- A contagem de revisões depende de uma linha que o Hermes 0.23.1 grava no `agent.log`. Os sinais do dono são heurísticas sobre as primeiras palavras da mensagem.
- A Proteção do Hermes só olha a palavra do comando em cada parte de um comando de terminal, depois dos invólucros que ela conhece, e até 8 níveis dentro de um comando passado como um único texto. Um comando aninhado mais fundo, um executado via `ssh` ou a partir de um script, um comando que ela não consegue interpretar e um caminho relativo à pasta de trabalho passam. Ela é uma rede de proteção, não uma sandbox.
- A checagem de código antigo compara números de versão: um processo que carregou outro código com o mesmo número de versão não é apontado, e no Windows nenhum processo é apontado.
- A checagem de operador (que só deixa o dono decidir) lê a ancestralidade dos processos e os cgroups em `/proc`, então fora do Linux ela depende só dos marcadores do ambiente.
- Quem um turno de chat atende vem do `owner_sender_ids` e do `owner_platforms`. Com os dois vazios, todo chat de mensagens conta como de outra pessoa: as falhas dele continuam contadas, mas as lições que vêm delas esperam aprovação e o chat recebe só lições de padrão fixo. Uma plataforma listada em `owner_platforms` confia em todos que escrevem nela.

## Avançado: deixar a revisão nativa propor lições

O Hermes pode admitir uma ferramenta nomeada na revisão em segundo plano por meio de `auxiliary.background_review.extra_tools`. Incluir `hermes_atlas_evolution_lessons` permite que a revisão registre o que aprendeu como proposta de lição, ao lado das gravações habituais em skills e memória.

```yaml
# config.yaml do perfil
auxiliary:
  background_review:
    extra_tools:
      - hermes_atlas_evolution_lessons
```

- Essa é uma configuração do operador no Hermes. O plugin nunca a define.
- A ferramenta precisa estar disponível para o agente principal, então isso também exige `agent_tools` ligado.
- Uma lição proposta por esse caminho tem origem `agent`: fica em quarentena, a proposta tem risco alto e ela só chega ao agente depois que você aprova. A ferramenta aceita no máximo 5 propostas por hora.
- Uma proposta aprovada aparece na seção de prompt como qualquer outra lição. Ela não está ligada a uma assinatura de falha, por isso não recebe veredito individual de antes e depois. A ativação dela ainda conta como mudança simultânea nos demais vereditos.
- Essa combinação não foi testada num gateway de produção.
