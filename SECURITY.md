# Security policy

Atlas Evolution runs inside Hermes Agent, observes its work, can place text in front of the agent and can veto some of the agent's terminal commands. This document explains how to report a problem, states the threat model in short, and lists exactly what the plugin stores, reads and executes, so that you can check it against the code.

> **Em português:** para relatar uma vulnerabilidade, use o relato privado do GitHub (aba **Security**, **Report a vulnerability**) e nunca uma issue pública. O plugin guarda só contagens, assinaturas de falha filtradas, lições e decisões, em `<HERMES_HOME>/evolution/`, com permissões só do dono. Não envia telemetria; o único acesso à rede do próprio plugin é o `git ls-remote` do próprio repositório, para manter atualizada a cópia de cada perfil, e o único modelo chamado é o do refletor, pelo Hermes. Ele muda o Hermes de forma reversível e registrada: com os próprios comandos do Hermes e, para reparar o gateway, editando o arquivo do serviço no systemd (com uma cópia guardada) e rodando o `systemctl`, nunca com um gateway deste Hermes rodando. Só decide quem está no próprio terminal ou logado no painel, nunca o agente. A Proteção do Hermes barra os comandos do agente que derrubariam o gateway ou apagariam ou alterariam o que o Hermes usa. Uma vez por dia, o perfil líder roda as checagens do `hermes doctor` sem rede, sem SSH ou container e sem `--fix`, num processo separado do Python do Hermes. Os detalhes abaixo estão em inglês; a documentação em português fica em [docs/pt-BR](docs/pt-BR/).

## Reporting a vulnerability

Please do not open a public issue with the details.

1. Use GitHub's private vulnerability reporting for this repository: the **Security** tab, then **Report a vulnerability**.
2. If that option is not available, contact the author through [LinkedIn](https://www.linkedin.com/in/sergiosantanacloud/) and ask for a private channel before sharing details.

Include the plugin version, the Hermes Agent version, the operating system, what you observed and the smallest set of steps that reproduces it. Remove conversation content, credentials and personal paths from anything you attach.

This is a volunteer project and there is no guaranteed response time. Fixes are released for the latest version only.

Reports of these kinds are especially welcome:

- conversation text, tool arguments, tool output, memory content, credentials or file paths reaching the plugin's databases or its command output;
- a lesson reaching the agent without operator approval in `suggest` mode or with lessons `off`, or, in `auto` mode, lesson text that does not come from a fixed template (a reflector draft, an agent proposal, an operator lesson added without `--activate`) reaching it without approval;
- a playbook decision that succeeds from an agent's shell;
- a refused approval that turns into advice for the agent;
- reflector input that survives scrubbing with a secret, or a draft that carries instructions into the playbook;
- the plugin changing Hermes (a skill, a setting, a unit) without the explicit setting that authorizes it, or in a profile with `fleet_managed` off;
- the gateway repair starting a second gateway, or writing or starting a service that belongs to another Hermes home;
- `hermes pm gc` run by the plugin while a service or a running program uses a folder it deletes;
- a hook callback raising an error into a turn or blocking it;
- a read that follows a link out of the profile or blocks on a named pipe or a device, or a generated recipe that could run something other than what it prints;
- an agent command that restarts the gateway or deletes what Hermes runs on and passes the runtime guard, or a veto that blocks ordinary work;
- the backfill, the radar or `status` writing to Hermes' files or to another profile, or text from Hermes' history reaching the plugin's databases;
- an owner notice shown in a gateway chat;
- `status` or anything the agent can run showing a chat sender's id, or a sender or platform becoming the owner without the operator's command;
- a value written to `settings.json`, which the agent's own file tools can write, widening whom the plugin trusts or what it does (owner ids or platforms, the agent tools, `tool_hints`, a reflector limit above 6, a mode other than manual) or switching the runtime guard off;
- someone other than the owner, in a chat, making a lesson activate by itself, getting operator, reflector or agent lesson text (the owner's lessons reaching a group, a thread or a topic included), getting an answer from the agent tools, or getting an error excerpt of theirs to the reflector;
- a dashboard without a login showing a lesson written by the owner, the reflector or the agent.

## Threat model

**What is protected.** What the agent reads (its system prompt and tool results), the profile's skills and configuration, the user's data, and the running Hermes itself (its gateway, interpreter, source and profile) against the agent's own terminal commands.

**Who can write to the playbook**, the only plugin data the agent reads:

| Writer | How | State when created | Reaches the agent |
|---|---|---|---|
| The plugin | a pass, from a recurring failure, live or replayed from Hermes' history, using a fixed template | `active` in `auto` mode, the default, once the owner's own turns hit the failure twice, also at a later pass; otherwise, and in `suggest`, `candidate` | at once when active; otherwise after approval |
| The operator | `hermes -p <profile> evolution lessons add` in their own terminal | `quarantined`, or `active` with `--activate` after a confirmation | after approval |
| A lesson pack | `hermes -p <profile> evolution lessons import` in the operator's own terminal, after every sentence was shown; each entry is checked as untrusted (identifier tool, known template class, filtered detail, text rules) | a template lesson waits (`candidate`, or `active` in `auto` once the owner's own turns hit its failure twice); a written one is `quarantined`; both `active` with `--activate` | at once when active; otherwise after approval |
| The reflector (a model) | a pass with `reflector` on, the default | `quarantined`, in every mode | after approval |
| The agent | `hermes_atlas_evolution_lessons` with `agent_tools` on, at most 5 per hour, also through the background review if you allow it | `quarantined`, high-risk proposal | after approval |

Error messages and command output are untrusted, whether they arrive through a hook or are replayed from Hermes' history. They never become lesson text: only a class and a short detail filtered as a name reach a template, and a detail read from command output must look like a lower-case command or module name. Lesson text from any writer is NFKC-normalized, and control, bidirectional, zero-width and private-use characters and secret-shaped values are refused, so the text the operator approves is the text the agent gets.

**Automatic actions.** `mode` (default `auto`; its older name `auto_actions` is still read) counts from Hermes' configuration, like `runtime_guard: false`: the plugin's `settings.json`, which the agent's file tools can write, may only narrow it to `manual` (any other value there, and any `auto_actions` but `off`, is ignored), and the runtime guard vetoes the agent's commands that change the plugin's settings. In Auto mode the plugin changes by itself only what can be undone, in every profile of the Hermes it runs in, with Hermes' own commands except for the gateway repair below: it locks skills the curator keeps rewriting, installs itself in a profile used without it that never had it (never where the owner turned it off, removed it or configured it; the data folder `evolution/evolution.sqlite3` that a removal leaves marks the profile, and the lead remembers every profile where the plugin was seen), only while the repository's latest commit is the one the lead runs and pinned to the lead's own commit only when the lead's copy is a checkout of the published repository, keeps every other profile's copy on the lead's commit (only where that profile's own mode is auto too), repairs the gateway's service when Hermes removed the Python it started, moves a failed install's folder (`plugins/.install-*`) to its `evolution/trash/`, and runs `hermes pm gc` at most weekly, once for the whole Hermes from the lead, only when no folder it would delete is used by a service or a running program, `tools/facts.json` can be read and both systemd scopes could be read. A profile with `fleet_managed` off is never changed by itself (`settings.json` can only turn it off), and when `config.yaml` cannot be read the mode is manual. On the owner's key only, one at a time and never in **Apply all**, it also moves a package cache that rebuilds itself (`cache/uv`, `pnpm`, `npm`, `pip`, `yarn`, `huggingface` or `piper-voices`) to the same trash; any other cache folder (the browser tool's logins and cookies, conversation attachments, generated images…) is never moved. It never turns off or removes another plugin, archives a skill, prunes rollback snapshots or changes a Hermes setting by itself. **Nothing stored is trusted for a change in a profile**: the proposal, the cached scan and every other profile's files (their catalog copy included) can be written by an agent with a terminal, so before it runs anything the plugin reads the target profile again from disk (for a finding of Hermes' doctor, it runs that doctor check again) and runs the command only if the same situation is still there; the command and its undo are rebuilt from fixed shapes (`plugins disable|enable <manifest name>`, `plugins install sesantanajr/hermes-atlas-evolution --enable [--ref <40-hex commit>]`, `plugins update hermes-atlas-evolution --force`, `plugins install <repository url> --force [--ref <40-hex commit>]`, `plugins remove hermes-atlas-evolution`, a trash move of `plugins/.install-*` or `cache/<name>` and its way back), never read from a record; the fallback reinstall never replaces a fork's copy with the published one. A profile is only what Hermes counts as one: a folder under `profiles/` whose name follows Hermes' rule (`[a-z0-9][a-z0-9_-]{0,63}`), that is not a link, holds one of Hermes' identity files and was not deleted (`profiles/.deleted`); `profiles/default` is not one. Turning off one of two plugins runs on the owner's key for that one proposal only. The trash move refuses any link in either path, never replaces something already there (an undo is refused when the folder exists again, and the copy stays in the trash) and uses `rename`, never a copy. Every learning pass, whatever the mode, deletes what entered the trash more than 30 days ago (an entry's date is set when it is moved in). Every file the plugin reads is opened without following a link and without blocking, only when it is a regular file and up to a size limit; in the other profiles the one link followed is a plugin folder installed as a link (a development checkout), read as Hermes loads it. So a named pipe, a device, a huge or deeply nested file, or a `SKILL.md` that links to `/dev/zero`, planted in a profile, cannot block, flood or fail the pass; each plugin's Python source is parsed with `ast` and never imported or run. Every automatic action is recorded in the decision history with `automatic` as the actor and can be undone; an undone one is never repeated, whichever profile leads later, and an older decision is never undone over a newer one on the same proposal. Undo writes down that the change must not come back before it runs Hermes.

**The gateway repair.** When Hermes replaced its bundled Python and the gateway's systemd service still starts the old one, `care fix-gateway` (on the owner's key) or the Mode auto (from the lead, at most once a day, a user service only) repairs the service. This is the one change not made with a Hermes command: the plugin rewrites the program's path on every `Exec*=` line of the file that sets `ExecStart` (the unit file or a drop-in), keeping a copy of the file next to it as `<file>.atlas-<time>-<random>.bak`, then runs `systemctl daemon-reload`, `reset-failed` and `start --no-block` for that service. The gateway is repaired (by the Mode auto or `care fix-gateway`) only when no gateway of this Hermes runs, degraded and starting ones included, and no gateway service of either scope runs, starts or stops, and only the service Hermes names for this home and that runs this `HERMES_HOME`. Whether a gateway runs is read from its process (pid with its start time or command line), a fresh heartbeat, `gateway.pid`, the lock it holds on `gateway.lock` (from `/proc/locks`) and `host-gateway.json`; a scope that cannot be read blocks the repair. A service name follows Hermes' own rule (the bare `hermes-gateway.service` only for the account's own `~/.hermes` or the home it pins), so a staging or test home never touches production's service, and the service's `HERMES_HOME` is checked before the file is written. The Mode auto never touches a service that runs, nor a profile's legacy per-profile service when the root's gateway serves that profile. Every repair and undo goes to a journal of the whole Hermes (`<root>/evolution/gateway-repair.json`, the latest 40); `care undo-gateway` works from any profile, puts the file back one repair at a time and runs `systemctl daemon-reload`, and refuses when the file changed since the repair. A repair the owner undid is never repeated by itself.

**Who decides.** Only the operator: in their own terminal (the commands, or the interactive menu, which opens only where those commands may run), or in the Evolution tab of a dashboard that asks for a login. The panel's decision route accepts a request only from a login Hermes verified or Hermes Desktop's grant, never with the dashboard's session token in any form (its header, `?token=`, `Authorization: Bearer`), which a dashboard without a login hands to any program on the machine, the agent's terminal included, so there the panel stays read-only; the decision is taken only in the dashboard's own process, where Hermes' login gate leaves the session it verified (a session verified by the deployment session token `HERMES_DASHBOARD_SESSION_TOKEN` does not count), and never in a profile's plugin host, which receives no credential from Hermes: the panel of another profile decides through the dashboard's own process, naming that profile, which must have the plugin installed and enabled ([details](docs/en-US/hermes-integration.md#the-dashboard-panel)). A decision also needs the header `X-Atlas-Evolution: 1`; **Approve all** decides only on the sentences it showed and never on a lesson the agent proposed; every decision is recorded and can be undone; and the runtime guard vetoes the agent's commands that call the route. Settings changed there or in the menu go through Hermes' public `hermes config set` into `config.yaml`. In the terminal, the menu, `lessons approve`, `retire`, `add`, `review`, `import` and `export`, `decisions undo`, and `proposals approve` and `reject` refuse to run when the environment carries `HERMES_SESSION_ID`, `HERMES_KANBAN_TASK`, `HERMES_DELEGATED_CHILD_CONTEXT` or `ATLAS_EVOLUTION_AGENT`, which the plugin adds to every subprocess of an agent session through `register_session_env`. So do `owner`, `schedule-digest`, `update` (except `--list`), `care` (except `check`) and `system` `plan`, `upgrade` and `repair`. On Linux they also refuse when a Hermes process is an ancestor of the command or the command runs in the systemd cgroup of a Hermes gateway, both read from `/proc`, so clearing those variables is not enough, and neither is detaching with `setsid` where the gateway runs as a systemd unit; a gateway started some other way leaves no trace a detached command could be traced to. Only the command's own `hermes evolution` launcher, the unbroken chain from the command up, is skipped: a Hermes ancestor further up counts even when its own words include "evolution" (a one-shot `hermes -z "...evolution..."`, a profile named evolution), and so does a virtual environment's `python .../bin/hermes`. A command the agent hands to something that starts it outside its own process tree and environment (`systemd-run`, `at`, a crontab entry, another user's session) leaves no trace either; the runtime guard vetoes the gateway and settings commands scheduled through `systemd-run`, and Hermes' approval policy is the control for the rest. In an agent's terminal, `lessons list` and `proposals list` leave out the sentence of every written lesson: the terminal of a stranger's chat is an agent's terminal too. A dashboard without a login leaves it out the same way, in every tab. Activation shows the exact text and asks. This guard keeps the agent from using the plugin's commands; it is not a sandbox. An agent that can run arbitrary commands as the same user could still write the database file directly, and Hermes' own approval policy for terminal commands is the control for that.

**Settings the agent cannot widen.** The agent's file tools (`write_file`, `patch`) need no approval to write `<HERMES_HOME>/evolution/settings.json`; Hermes refuses their writes to `config.yaml` only, and flags terminal writes to it for approval. So a value that would widen whom the plugin trusts or switch a protection off counts only from the Hermes configuration (the plugin settings form, stored in `config.yaml`): `owner_sender_ids`, `owner_platforms`, `agent_advice: true`, `tool_hints: true`, a `reflector_daily_limit` above 6, a `mode` other than `manual` and `runtime_guard: false` are ignored in `settings.json`, `fleet_managed` there can only be turned off, and `status` lists the keys it ignored. `hermes -p <profile> evolution owner` prints the `hermes -p <profile> config set` command for the owner to run instead of writing anything. The runtime guard vetoes the agent's own `hermes config set` or `unset` of the `plugins` section (which enables, disables and isolates plugins) and of this plugin's settings, leaving other plugins' settings open, its `hermes config edit`, its `hermes plugins disable`, `remove` or `trust` of this plugin and an install over it, the removal of the plugin's own folder, a terminal write to a Hermes `config.yaml` that names the plugins section, this plugin or one of its trust settings, and a command that replaces a Hermes `config.yaml` (`cp`, `mv` or `install` over it, a `>` redirect), wherever global options such as `-p <profile>` sit in the command, under every name the `hermes` command runs by (`python -m hermes_cli.main` included), and also when the shell fills in a word there (`$VAR`, `$'...'`, a command substitution). The one other option of `settings.json`, the cost rates (`rates_usd_per_million`), is not part of this boundary.

**Chats with other people.** A turn serves the owner on their own surfaces (CLI, TUI, Desktop, ACP), in their automations, in a subagent delegated from a turn that served the owner (a child of someone else's chat serves that person, and a child whose parent the plugin has not seen serves someone else), or in a chat with a sender listed in `owner_sender_ids`; every other chat, integration or A2A peer serves someone else, and so does a session the plugin has not seen a turn of since it loaded. What someone else does is measured, but it cannot change the owner's prompt: their failures alone never activate a lesson (it waits for approval), they never leave an excerpt for the reflector, a chat that may serve someone else gets template lessons only (fixed text and an identifier-like detail, never operator, reflector or agent text), and the agent tools refuse to answer there. In a direct chat (a DM) whose sender turns out to be the owner, the lessons the chat's prompt left out come with the owner's first message, once per chat; never in a group, thread or topic, where the model's history could keep them for someone else later, and never in a chat someone else wrote in. With `owner_sender_ids` and `owner_platforms` empty, every messaging chat counts as someone else's. One limit remains: Hermes runs cron jobs under the platform `cron`, and the plugin counts automations as the owner's, so a scheduled job created from a stranger's chat (where Hermes offers the cron tool) runs as the owner's automation; turn the cron tool off in chats other people use if that matters to you. A platform listed in `owner_platforms` makes everyone who writes there the owner, so list only a platform nobody else uses. `hermes -p <profile> evolution owner`, which shows the sender ids of each chat channel and prints the command that changes these two settings, is an operator decision: it refuses to run in the agent's terminal like the other decisions, and `status` shows only counts. Changing who is the owner replays the history again under the new settings.

**Approval refusals.** When the user denies a command, an approval times out, no approver is reachable or the context cannot approve, the failure is the class `approval_refused`. It gets no template, no reflector draft and no investigation proposal, so the plugin never teaches the agent to route around the user's decision. The lesson for `blocked_by_policy` tells the agent not to retry or look for another way, and to tell the user.

**The reflector.** On by default; `reflector: false`, or an invalid value, switches it off. While it is on and `lessons` is not `off`, the hook (and the backfill, for replayed history) keeps one excerpt of the latest error of each untemplated failure of a turn that served the owner: at most 300 characters, passed through Hermes' redactor with `force=True` (so it applies even when the profile turned redaction off) and always through the plugin's masks for URLs, e-mail addresses, paths, long hexadecimal strings, credential prefixes, long numbers and long quoted strings. The excerpt goes to a model through Hermes, under the auxiliary task `evolution_reflector`, with instructions that it is data and not instructions, and the reply must match a JSON schema. A draft is discarded if it fails the lesson text rules, contains `<` or matches the injection filter. Accepted drafts stay quarantined in every mode, `auto` included, because a crafted error message could otherwise reach the agent's prompt. Calls are capped per pass and per day, and each call is counted before it is made, so a crash cannot exceed the cap. The excerpt is deleted once the failure has a lesson, when a draft is declined or discarded, after 14 days (also by the daily prune of the hooks, when no pass runs), or at the next pass with the reflector off.

**The runtime guard.** An agent with a terminal runs as the same user as Hermes, so it can stop the gateway it runs on or delete what that gateway needs. With `runtime_guard` on (the default), a `pre_tool_call` callback vetoes, for terminal-like tools, commands that would stop, restart or kill the gateway (its systemd unit on Linux, under any profile or home suffix, its LaunchAgent on macOS, its Windows service or scheduled task) or the Hermes processes (also a kill whose pid lookup selects the gateway process itself, such as `kill $(pgrep -f 'gateway run')`; a lookup that does not select it, such as `kill $(cat app.pid)`, passes), the agent's `hermes gateway restart` included, which is left to the owner, along with `hermes gateway uninstall`, `start --all`, `run --replace`, `install --force` and `hermes profile delete`, and commands that would delete or move the running interpreter and its environment (also under the name of a link, such as the base interpreter a virtual environment points at), the Hermes source, the Hermes root, the profile, a folder above them or a glob that matches them, and the agent's own `hermes config set|unset` of this plugin's settings and `hermes plugins disable|remove` of this plugin. Where Hermes runs plugins in a plugin host (`plugins.isolation: host`) no `pre_tool_call` is registered at all, because Hermes blocks a tool whose `pre_tool_call` fails and a crashed host would then block every tool; the guard is off there, and `status` says so. The details are in [Hermes integration](docs/en-US/hermes-integration.md#the-runtime-guard). Whatever the verb, it also vetoes a write, truncation or attribute change inside the running interpreter, its environment, Hermes' packages or the plugin's own folder (`truncate`, `dd of=`, `tee`, a redirect, `chmod`, `chown`, `chgrp`, `ln -sf`, `rsync --delete`, `cp`, `mv` or `install` into them), `chmod`, `chown`, `chgrp`, `ln` or `rsync --delete` aimed at the profile's folder, Hermes' root or a folder above them or above a protected tree, and replacing a Hermes `config.yaml` with `cp`, `mv` or `install`; plain copies into the home folder, the Hermes root or a shared folder stay allowed. The guard is a safety net for these three failure modes, not a sandbox: it looks at the command word of each part of a command, after the shell words, wrappers and applet multiplexers (busybox, toybox) it knows, puts in literal `VAR=value` assignments made earlier in the command, follows a `cd`, ignores comments and the here-document bodies no shell reads as its script, looks up to 8 levels into a command given as one string (`bash -c`, `su -c`, `eval`, `watch`, command substitutions, `find -exec`, `ssh localhost`, what a shell reads on standard input from a here-document, a here-string, `echo` or `printf`, the strings of `python -c` and similar), and lets any doubt through, such as a command it cannot parse, text piped into a shell from a file or a download, encoded text, a script file, or a relative path whose folder it cannot know. A command is read on its first 20,000 characters after comments and here-document bodies are cut, so padding cannot push it past the check, and one budget bounds the work on nested commands: any command up to 20,000 characters is checked in under 0.7 seconds. An internal failure lets the command through, because Hermes blocks a tool whose `pre_tool_call` fails, and is logged once per process. It was checked against about 350 commands written to get around it ([details](docs/en-US/hermes-integration.md#the-runtime-guard)). An invalid `runtime_guard` value keeps it on. Hermes' own approval policy for terminal commands remains the control for everything else.

**The autopilot and the history.** The pass runs in a background thread of each long-running Hermes process (a gateway, the dashboard, `hermes serve`, the TUI or Desktop backend, an ACP server, an interactive CLI; a one-shot run only reads the settings), claimed so that only one process of a profile runs it at a time. A clock thread per loaded profile only nudges it, 2 minutes after the plugin loads and then every 10 minutes. The thread binds its own profile's home and secret scope, so in a gateway that serves several profiles a reflector call uses that profile's provider keys and never another profile's. The pass reads Hermes' records, including `state.db` read-only, and writes only the plugin's own database. It has a deadline inside its lease (12 of the lease's 15 minutes), so a slow pass never runs alongside the next one. It changes nothing in Hermes, except the automatic actions of the `mode` at its end: with `assist`, it removes an entry said, the very same text character for character, in both `MEMORY.md` and `USER.md`, never the last copy (a copy of the file is kept); with `auto` (the default), also `hermes curator lock` for skills the curator keeps rewriting, and, in the profile that looks after the whole Hermes, a weekly `hermes pm gc` for the whole Hermes, installing the plugin in a profile used without it that never had it, keeping every profile's copy on the lead's commit, repairing the gateway's service and moving failed install folders to its trash, after reading that profile again from disk (see **Automatic actions** and **The gateway repair** above); at most 3 changes to Hermes per pass, each started only with time left to finish it. In that same profile, the pass also runs Hermes' doctor checks once a day per profile in use (see **Hermes' doctor checks** below). Each one is recorded with its undo; an undo is derived again from what was run, never read from the record.

**Hermes' doctor checks.** Once a day, the profile that looks after the whole Hermes runs the checks of `hermes doctor` for each profile in use. They run Hermes' own code, in a separate short-lived process of the Python running Hermes (`-I`, the profile's folder as working directory, standard input closed), never in the plugin's process. The environment is rebuilt from a short list (`PATH`, `HOME`, the user and locale, temporary folders, and a few system variables), so the provider keys and tokens in the environment of the process that runs the plugin do not pass; Hermes' own code then reads the profile's files as it always does. Each check is called as `hermes doctor` calls it without `--fix`, and an error in one check (Hermes' own `SystemExit`-style exits included) is caught there. Five checks are skipped: the provider API probes, `npm audit`, the dashboard import, the Skills Hub (they use the network or take minutes) and the terminal backend (it may open an SSH connection or start a container). So nothing leaves the machine and no setting changes; the footprint is Hermes' own logs and lock files. Like `hermes doctor`, the run loads the profile's plugins to list their tools, so those plugins' code runs in that process, as it does in any Hermes command of that profile. The process starts in a process group of its own; at the 120-second limit the whole group is killed, so nothing a check started outlives it. Its output is read up to 2 MB and parsed as data. A run starts only while the machine has at least 600 MB of memory free. A result older than 3 days is not shown, and when a change is found stale on disk, that profile's stored result is dropped and the checks run again at the next look. What Hermes printed is kept in the lead's database as Hermes wrote it (see **What the plugin stores**) and shown to the owner as text; it never reaches the agent.

**Other profiles.** `status` reads every profile of the same Hermes root, read-only: the number of sessions in the last 7 days from its `state.db`, whether its `plugins/` folder holds this plugin or the copy under the old id, and, where the plugin has data, the end of its last pass and its lesson counts from the plugin's own database there. It never writes to another profile; it prints the install or migration command for the operator to run.

**Long-running processes.** A gateway or dashboard that loads the plugin records, in the plugin's database of its profile, the plugin version it loaded, its kind and when it started, keyed by its process ID. `status` checks whether each recorded process is still alive with a signal-0 probe, which does not affect the process and runs only on POSIX systems, flags one that runs another version than the code on disk, and deletes the record of one that is gone.

**Owner notices.** At the end of a local session the plugin may return a short notice about decisions waiting. It is shown only on the owner's local surfaces (CLI, TUI, Desktop), never for a subagent and never in a gateway chat, where the other side may be someone else, and it carries counts only. Hermes 0.23.1 shows this text only at the classic CLI's exit or new session and at a TUI or Desktop close, so the plugin returns nothing for any other end and does not spend the day's notice.

## What the plugin stores

Everything is local, under `<HERMES_HOME>/evolution/`. On POSIX systems the folder is created with mode `0700` and the databases with mode `0600`.

| File | Content |
|---|---|
| `evolution.sqlite3` | Daily counters for tools, turns per surface, owner feedback kinds, skill events, the outcome of turns per loaded skill, background reviews, model calls and tokens per provider and model, and compactions with the tokens before and after. Failure signatures: tool name, failure class, a short filtered detail, counts, first and last time seen, and a truncated hash of the last failing session, with a daily count of the failures in the owner's turns. Refused approvals per day by session origin (a label such as `cron` or `telegram`), tool name and the name of the Hermes setting that decided a refusal nobody could answer. The ids of the derived lessons waiting only for the owner's own turns to hit their failure. Lessons, when the agent first read each one in its current activation (where its measurement starts), tracked changes with their verdicts, proposals and reading cursors. With the reflector on, one scrubbed error excerpt per untemplated failure, prefixed with the name of the program that failed when the tool ran a command. Counts of the commands the runtime guard vetoed, by kind only. The backfill position and totals, the autopilot lease and the status of the last pass, and the day of the last owner notice. For each gateway or dashboard process that loaded the plugin, keyed by its process ID: the plugin version, the process kind and when it started, deleted once `status` finds the process gone. The radar's last snapshot of the plugins of a process: plugin keys, hook counts and the exception name of a load error; radar proposals also keep the session end reasons as Hermes records them. Hashes that prevent counting one event twice. |
| `evolution.sqlite3` of the profile that looks after the whole Hermes | Also its last look at every profile (counts, plugin names and versions, skill folder names, the findings with their commands) and, per profile in use, the last result of Hermes' doctor checks: the lines each check printed and the problems it listed, as Hermes wrote them. Those lines can name files, folders, packages, MCP servers, settings and tools; proposals keep up to 600 characters of one of them as evidence. Each run replaces the previous one; a result older than 3 days is not shown. |
| `gateway-repair.json` | Only in the root profile's folder: the latest 40 repairs and undos of the gateway's service, each with the unit's name and scope, the paths of its file and of the copy kept, the program before and after, a hash of the file as the repair left it, the time, the profile and whether the owner or the Mode auto made it. Owner-only, never written through a link. |
| `fleet-state.json` | Only in the default profile's folder: the names of the profiles where the plugin was ever seen, and the codes of the automatic changes the owner undid, so they are never applied by themselves again. |
| `trash/<profile>/` | Only in the profile that looks after the whole Hermes: failed install folders and, on the owner's key, package caches moved there, owner-only (`0700`). Every learning pass deletes what entered it more than 30 days ago. |
| `memory-backups/` | Only when you take an entry out of Hermes' memory from the menu or the panel: a copy of the memory file as it was, owner-only (`0600` in a `0700` folder), the latest 100. It holds memory text, as Hermes' own files do. |
| `settings.json` | Written by you; the plugin only reads it. The agent's file tools can write it too, so values that would widen trust are ignored there (see "Settings the agent cannot widen" above). Values set in the Hermes settings form are stored by Hermes in the profile configuration. |

Older versions also left data that the plugin no longer reads or writes, and does not delete: the notes of version 0.1 (the table `evolution_memories` of `evolution.sqlite3`, text the owner saved; `status` says how many remain and prints a read-only command that shows them), the maintenance finding codes of the old `tick`, and `supervisor.sqlite3`, the operations supervisor's incidents, baselines and systemd trials. Delete `supervisor.sqlite3` if you want it gone.

Next to a gateway service file the plugin repaired: `<file>.atlas-<time>-<random>.bak`, the file as it was, with its mode, which `care undo-gateway` puts back.

Only when the owner updates or repairs the operating system, as root: `/var/lib/hermes-atlas-evolution/system/<time>-<random>/`, outside every Hermes profile so it never goes into a Hermes backup, the folder and its parent only root's (`0700`; the plugin refuses a folder another user owns or can write). Each run keeps the list of installed packages before and after, a copy of `/etc` before (it may hold secrets of the machine; `0600`), the check before, the packages it holds while it runs, the update's script, log, exit status and report. Every file is created new with `O_EXCL|O_NOFOLLOW`, so a planted link is never followed. The latest 5 runs are kept, never one that may still hold packages.

Text that is stored as written, because someone wrote it on purpose:

- **Lessons.** A sentence of 12 to 240 characters from `hermes -p <profile> evolution lessons add`, the agent's `hermes_atlas_evolution_lessons` or the reflector, checked as described above.
- **Proposal notes.** The optional `--note` of a decision, up to 200 characters.

## What the plugin does not store

- Conversation text, prompts or model responses, including those replayed from `state.db`.
- Tool arguments or tool output. Error text is classified in memory and discarded; only the reflector, when on, keeps the scrubbed excerpt described above.
- The commands the runtime guard vetoes. The hash of each terminal command that `pre_tool_call` keeps to tell whether another plugin rewrote it stays in memory, at most 512 at a time, and is never stored.
- Memory content, except the copy of a memory file kept when the owner takes an entry out (see `memory-backups/` above). Native memory files are read to count entries, check their encoding and, in the owner's menu, show what repeats; the decision log keeps a fingerprint of the entry taken out, never its text.
- Raw log lines. From `agent.log` the plugin keeps numbers and a fixed result label.
- Session, turn or request identifiers in clear. They are hashed.
- Paths, URLs or credential-shaped values, except in Hermes' own doctor lines kept by the lead (see above). A failure detail is kept only when it is a short name of at most 32 characters that passes `signals._clean_hint`, including Hermes' redactor with `force=True`. Tool, skill, provider and model names pass an allowlist, and a name that fails it is stored as `unknown` or dropped.
- Configuration values that are not plain labels. They are stored as a short fingerprint.

Retention is 35 days for observer metrics and 90 days for the evolution loop's aggregates. The guard's daily counts (`guard_daily`), the daily failures in the owner's turns (`failure_owner_daily`) and the refused approvals per origin (`approval_daily`) follow the 90-day retention. The delivery IDs that stop one event from being counted twice (`seen`) are kept 2 days, and reflector excerpts (`failure_sample`) at most 14 days. Lessons are kept, retired and withdrawn ones included, so a lesson id never points to another lesson and a sentence the owner turned down stays down.

## What the plugin reads

Hermes files are opened read-only, with size limits, and the databases with a short deadline. This includes, for `status`, the `state.db` of the other profiles of the same Hermes root, where it only counts sessions, and the plugin's own database in those profiles, where it reads the end of the last pass and the lesson counts. In the profile's own `state.db`, `status` counts the sessions and senders of each chat channel, and `hermes -p <profile> evolution owner`, which only the operator can run, lists the sender ids per channel so the operator can pick theirs; neither stores them. On Linux, a decision command also reads `/proc` to find its ancestor processes and its cgroup. To tell whether a gateway runs and what `hermes pm gc` would break, the plugin reads Hermes' gateway records (`gateway_state.json`, `gateway.pid`, the heartbeat, `host-gateway.json`), `/proc/locks`, the start time and command line of the gateway's process, the unit files and drop-ins of Hermes' gateway services through `systemctl`, `tools/facts.json` and the programs running now (`/proc/*/exe`). The profile that looks after the whole Hermes reads every profile for the environment: plugin manifests, git records and Python source (parsed, never imported or run), skill frontmatter and usage, and Hermes' plugin catalog. The list is in [Hermes integration](docs/en-US/hermes-integration.md#what-the-plugin-reads).

## What the plugin executes

- **No telemetry; its only network access is `git ls-remote` of its own repository, to keep every profile's copy current:** `git ls-remote https://github.com/sesantanajr/hermes-atlas-evolution.git HEAD`, with an argument list, a 20-second limit and no terminal prompt, at most once per pass from the lead in Auto mode before it installs or syncs a copy, and in `update`. The only model call is the reflector's, on by default, made by Hermes through `ctx.llm` with the provider configured for `auxiliary.evolution_reflector`, which inherits the compression model unless you set another.
- Two background daemon threads per profile loaded in a Hermes process: the clock, which only nudges the pass, and the autopilot, which runs it. Neither executes a command.
- `status` probes whether a recorded Hermes process is still alive with signal 0, which sends nothing to the process, on POSIX systems only.
- The runtime guard executes nothing. It returns a block directive to Hermes, which then does not run the command.
- `hermes --profile <name> config set plugins.entries.hermes-atlas-evolution.settings.<key> <value>`, one per changed setting, only when the owner changes a setting in the panel or the terminal menu, with an argument list (no shell) and a 60-second limit.
- `hermes --profile <name> curator lock|unlock <skill>`, the same way with a 180-second limit, only to apply a lock the owner approved in the menu, the panel or `proposals approve`, to undo it, or, in Auto mode, to lock a skill the curator keeps rewriting (at most 3 per pass, never one whose automatic lock the owner undid, one Hermes refused only a day later). The skill name must be a plain name (letters, digits, `.`, `_`, `:`, `-`). The undo is always `unlock` of the skill that was locked, derived again from what was run; a skill the owner had locked is left as it is, with no undo recorded.
- `hermes --profile <profile> plugins disable|enable <plugin>` (by the plugin's manifest name) and `plugins install sesantanajr/hermes-atlas-evolution --enable [--ref <commit>]` (undone with `plugins remove hermes-atlas-evolution`), for a profile of the same Hermes root that is a real folder with a `config.yaml`, the same way with a 180-second limit: `disable`/`enable` only on the owner's key for one proposal; the install on the owner's key, or by itself in Auto mode in a profile used in the last 7 days that never had the plugin, with `--ref` only when the lead's copy is a checkout of the published repository. Each runs only after the profile was read again from disk and the situation is still there.
- `hermes --profile <profile> plugins update hermes-atlas-evolution --force`, `plugins install https://github.com/sesantanajr/hermes-atlas-evolution.git --force --ref <40-hex commit>` for a pinned copy, or `plugins install <that url> --force` for a half-installed one, with a 180-second limit in a learning pass (300 seconds in `update`): in Auto mode, from the lead, to bring another profile's copy to the lead's commit (at most two per pass, once per situation, only where that profile's mode is auto and `fleet_managed` is on), and in `hermes -p <profile> evolution update` on the owner's key. A development link and a fork's pinned or half-installed copy are never touched.
- The gateway repair (see **The gateway repair** above): an atomic rewrite of the file that sets the gateway service's `ExecStart`, after keeping a copy, then `systemctl [--user] daemon-reload`, `reset-failed <unit>` and `start --no-block <unit>`, and `is-active <unit>` every 2 seconds for up to 180 seconds; the undo writes the copy back and runs `daemon-reload`. On the owner's key with `care fix-gateway` and `care undo-gateway`, or in Auto mode at most once a day, from the lead, for a user service only.
- A `rename` of a failed install's folder (`plugins/.install-*`) or of a package cache (`cache/uv`, `pnpm`, `npm`, `pip`, `yarn`, `huggingface`, `piper-voices`) of a profile into the lead's `evolution/trash/<profile>/`, and back on undo; no command runs. A package cache moves only on the owner's key, one at a time, after the doctor check that found it ran again for that profile. Every learning pass deletes what entered the trash more than 30 days ago.
- Hermes' doctor checks: the running Python with `-I -c <a fixed script>`, in the profile's folder and in a process group of its own, with the rebuilt environment described above, standard input closed, a 120-second limit (the whole group is killed then) and output read up to 2 MB. It imports `hermes_cli.doctor` and calls each check of `DOCTOR_CHECKS` as `hermes doctor` does without `--fix`, skipping the provider API probes, `npm audit`, the dashboard import, the Skills Hub and the terminal backend; like `hermes doctor`, it loads the profile's plugins to list their tools. Once a day per profile in use, from the lead; at once when the owner asks for a new look (screen 14, `v`, or `hermes -p <profile> evolution environment scan`); and for one profile before a package cache is moved.
- `hermes --profile <name> pm doctor`, `doctor`, `doctor --fix` (after `backup --quick --label atlas-evolution`; nothing is repaired if the backup fails) and `pm gc`, the same way with a 900-second limit each, only on the owner's click in the menu or `hermes -p <profile> evolution care`; `pm gc` also by itself in Auto mode, from the profile that looks after the whole Hermes (one tool store, at the root), at most once a week, when the health check found 300 MB or more of tool versions nothing references. Hermes' gc deletes every folder of the store that `tools/facts.json` does not name, so the plugin runs it, from the menu, `care gc` or the Mode auto, only when no such folder is used by a service (any `Exec*=` line) or a running program (`/proc/*/exe`), `facts.json` can be read and both systemd scopes could be read, checked again right before it runs. `hermes doctor --fix` may create missing folders and the `.env` file, migrate `config.yaml` (Hermes keeps its own copy first), repair the session database, recreate the `hermes` launcher and download Chromium when the browser tool needs it; the quick backup keeps `config.yaml`, `.env`, the session database and the cron jobs, restored with `/snapshot restore <id>`. `hermes doctor` calls the configured providers' APIs and pings an endpoint ending in `/anthropic` with a one-token request; the others make no model call.
- `hermes --profile <name> cron create ... --no-agent --script hermes-atlas-evolution-digest.py` (and `cron remove <job>` to undo it), only when the owner schedules the weekly digest; the script, written owner-only under the profile's `scripts/`, runs `hermes -p <profile> evolution learn --notify-only` and `report`.
- Read-only commands of the operating system for the daily check, Linux with apt only: `apt list --upgradable`, `dpkg --audit`, `apt-get -o Debug::NoLocking=1 check` (it takes no lock), `apt-mark showhold`, `apt-config dump APT::Periodic::Unattended-Upgrade`, `uname -r`, `systemctl list-unit-files|list-units|is-active|show` and `loginctl show-user` (for the profile's owner); and it reads `/proc` (process names, memory, the locks held on dpkg's and apt's lock files in `/proc/locks`), `/etc/os-release` and the dates of apt's `Release` files under `/var/lib/apt/lists/`.
- Only when the owner runs the system's update or repair, as root in their own terminal (never the agent, refused in an agent's shell) and only when Hermes' profile and the plugin's code belong to root (otherwise another user could change what root runs): `apt-get update`, a simulation (`apt-get -s`), then `systemd-run --unit=hermes-evolution-os-upgrade-<run> --collect /bin/sh <script>` (`...-os-repair-<run>` for the repair), where the script, written root-only with every path quoted, runs `apt-get -y --with-new-pkgs upgrade` (or `full-upgrade` with `--full`) with `--force-confdef --force-confold` and `NEEDRESTART_MODE=l`, holding the packages the owner chose to leave out (written down first, released by a shell trap when the run ends, fails or receives SIGINT, SIGTERM or SIGHUP, and taken off the list only once `apt-mark unhold` succeeded, tried again for up to 3 minutes while dpkg holds its lock); before it, `dpkg-query` and a copy of `/etc` into the root-only run folder above; and, for the repair, `apt-mark unhold` of the packages a stopped run still held, `dpkg --configure -a` and `apt-get -f install`. Package names reach the script only when they match apt's own rules; any other name is refused. The plugin never reboots the machine.
- An atomic rewrite of `memories/MEMORY.md` or `memories/USER.md`, keeping the file's mode and owner, only when the owner takes an entry out (or undoes that) in the menu or the panel, or, in Assist or Auto mode, to remove an entry said, the very same text character for character, in both files (never one the owner put back, never the last copy, never when `config.yaml` was not read), under Hermes' own memory lock on both files, after a copy of the file is kept.

On POSIX systems every command runs in a process group of its own and a timeout ends the whole group; on Windows a timeout ends the whole process tree.

The cron recipe of `report --schedule-spec` is printed for review: that command does not write the script and does not create the job.

The one optional package is used only when you install it yourself: PyYAML lets the standalone runner read `config.yaml`.

**The dashboard panel.** The Evolution tab of the Hermes dashboard reads the profile's data through a `GET` route and decides through a `POST` route, both authenticated by Hermes and scoped to the profile on screen, and refused where the plugin is disabled. Only a logged-in owner decides there (see "Who decides" above); everywhere else it is read-only and shows the command of the terminal menu. Everything it shows, lesson text included, is rendered as text, never as markup.

## What reaches the agent

A lesson is text placed in the system prompt of new sessions and, with `tool_hints` on (off by default, and on only from Hermes' configuration), in the result of a failing tool call. Treat approving a lesson like editing the system prompt.

- Template lessons vary only in the tool name and the filtered detail. In `auto` mode, the default, a new template lesson reaches the agent once the owner's own turns hit its failure twice, is measured from the first time the agent read it, and is retired when it is measured as ineffective 14 days or more after that; in `suggest` mode it waits for your approval.
- Lessons from you without `--activate`, from the agent and from the reflector start in quarantine and are never shown before you approve them, in every mode. So do written lessons from a pack you import without `--activate`.
- The agent tools are hidden until `agent_tools` is on.
- In a direct chat whose sender is the owner (`owner_sender_ids`), the lessons the chat's prompt left out (written by the owner, the reflector or the agent) are added to the owner's first message there, once per chat, at most 5 lines and 900 characters; never in a group, thread or topic, and never in a chat someone else wrote in.
- With `lessons` set to `off` no lesson surface is registered.
- When the runtime guard vetoes a command, the agent reads the guard's fixed refusal, in the plugin's language, in place of the tool result. It names the protected path, or tells the agent to ask the owner, who runs `hermes gateway restart` from their own terminal.
- Owner notices are shown to the owner outside the conversation. They do not reach the agent and never start a turn.

## Verification status

The plugin is covered by unit and end-to-end tests against a simulated Hermes context, including tests that assert sensitive-looking input is absent from the stored rows, also for history replayed from `state.db`, that decisions refuse to run with agent markers, that every approval refusal text of Hermes 0.23.1 is classified as `approval_refused`, that the runtime guard vetoes the known commands, lets ordinary administration through and never raises, and that a profile with the copy under the old id registers nothing. It passes `hermes plugins validate` on Hermes Agent 0.23.1, with the security scan reporting it safe. In production, three real reflector calls through Hermes produced three drafts. The autopilot is verified in tests and in the CLI, and its clock and the stale-process check in tests. The test suite, over 700 tests on the repository's `tests` branch, runs in CI on Linux with Python 3.11 to 3.14 and on real macOS and Windows runners (where POSIX-only tests are skipped); the plugin has not run inside a Hermes gateway on macOS or Windows yet. The loop has gone through independent reviews (security, compatibility with Hermes 0.23.1, the learning loop) and a full audit of the automatic actions, the runtime guard, the learning loop, privacy and the interface, and each fix they led to comes with a test that fails without it. Hermes' doctor checks were measured at about 7 seconds per profile on Hermes 0.23.1; they rely on Hermes' internal `DOCTOR_CHECKS`, which is not part of the public plugin API, so another Hermes version may need an update of the plugin. It has not been audited by a third party, and lesson verdicts have not been observed over weeks of real use yet.
