# Security policy

Atlas Evolution runs inside Hermes Agent, observes its work, can place text in front of the agent and can veto some of the agent's terminal commands. This document explains how to report a problem, states the threat model in short, and lists exactly what the plugin stores, reads and executes, so that you can check it against the code.

## Reporting a vulnerability

Please do not open a public issue with the details.

1. Use GitHub's private vulnerability reporting for this repository: the **Security** tab, then **Report a vulnerability**.
2. If that option is not available, contact the author through [LinkedIn](https://www.linkedin.com/in/sergiosantanacloud/) and ask for a private channel before sharing details.

Include the plugin version, the Hermes Agent version, the operating system, what you observed and the smallest set of steps that reproduces it. Remove conversation content, credentials and personal paths from anything you attach.

This is a volunteer project and there is no guaranteed response time. Fixes are released for the latest version only.

Reports of these kinds are especially welcome:

- conversation text, tool arguments, tool output, memory content, credentials or file paths reaching the plugin's databases or its command output;
- a lesson reaching the agent without operator approval in `suggest` mode or with lessons `off`, or, in `auto` mode, lesson text that does not come from a fixed template (a reflector draft, an agent proposal, an operator lesson added without `--activate`) reaching it without approval;
- a playbook decision that succeeds from an agent's shell;
- a refused approval that turns into advice for the agent;
- reflector input that survives scrubbing with a secret, or a draft that carries instructions into the playbook;
- the plugin changing Hermes (a skill, a setting, a unit) without the explicit setting that authorizes it;
- a hook callback raising an error into a turn or blocking it;
- a read that follows a link out of the profile, or a generated recipe that could run something other than what it prints;
- an agent command that restarts the gateway or deletes what Hermes runs on and passes the runtime guard, or a veto that blocks ordinary work;
- the backfill, the radar or `status` writing to Hermes' files or to another profile, or text from Hermes' history reaching the plugin's databases;
- an owner notice shown in a gateway chat;
- `status` or anything the agent can run showing a chat sender's id, or a sender or platform becoming the owner without the operator's command;
- a value written to `settings.json`, which the agent's own file tools can write, widening whom the plugin trusts (owner ids or platforms, the agent tools) or switching the runtime guard off;
- someone other than the owner, in a chat, making a lesson activate by itself, getting operator, reflector or agent lesson text, getting an answer from the agent tools, or getting an error excerpt of theirs to the reflector.

## Threat model

**What is protected.** What the agent reads (its system prompt and tool results), the profile's skills and configuration, the user's data, and the running Hermes itself (its gateway, interpreter, source and profile) against the agent's own terminal commands.

**Who can write to the playbook**, the only plugin data the agent reads:

| Writer | How | State when created | Reaches the agent |
|---|---|---|---|
| The plugin | a pass, from a recurring failure, live or replayed from Hermes' history, using a fixed template | `active` in `auto` mode, the default, once the owner's own turns hit the failure twice, also at a later pass; otherwise, and in `suggest`, `candidate` | at once when active; otherwise after approval |
| The operator | `hermes evolution lessons add` in their own terminal | `quarantined`, or `active` with `--activate` after a confirmation | after approval |
| A lesson pack | `hermes evolution lessons import` in the operator's own terminal, after every sentence was shown; each entry is checked as untrusted (identifier tool, known template class, filtered detail, text rules) | a template lesson waits (`candidate`, or `active` in `auto` once the owner's own turns hit its failure twice); a written one is `quarantined`; both `active` with `--activate` | at once when active; otherwise after approval |
| The reflector (a model) | a pass with `reflector` on, the default | `quarantined`, in every mode | after approval |
| The agent | `hermes_atlas_evolution_lessons` with `agent_tools` on, at most 5 per hour, also through the background review if you allow it | `quarantined`, high-risk proposal | after approval |

Error messages and command output are untrusted, whether they arrive through a hook or are replayed from Hermes' history. They never become lesson text: only a class and a short detail filtered as a name reach a template, and a detail read from command output must look like a lower-case command or module name. Lesson text from any writer is NFKC-normalized, and control, bidirectional, zero-width and private-use characters and secret-shaped values are refused, so the text the operator approves is the text the agent gets.

**Automatic actions.** `mode` (default `auto`; `auto_actions`, its 0.8.3 name, is still read) counts from Hermes' configuration, like `runtime_guard: false`: the plugin's `settings.json`, which the agent's file tools can write, may only narrow it to `manual` (any other value there, and any `auto_actions` but `off`, is ignored), and the runtime guard vetoes the agent's commands that change the plugin's settings. In auto the plugin changes by itself only what can be undone, in every profile of the Hermes it runs in, always with Hermes' own commands: it locks skills the curator keeps rewriting, installs itself at its own commit in a profile used without it that never had it (never where the owner turned it off, removed it or configured it), moves a failed install's folder (`plugins/.install-*`, nothing else) to its `evolution/trash/` and runs `hermes pm gc` at most weekly. It never turns off or removes another plugin, archives a skill or changes a Hermes setting by itself. **Nothing stored is trusted for a change in a profile**: the proposal, the cached scan and every other profile's files (their catalog copy included) can be written by an agent with a terminal, so before it runs anything the plugin reads the target profile again from disk and runs the command only if the same situation is still there; the command and its undo are rebuilt from fixed shapes (`plugins disable|enable <manifest name>`, `plugins install sesantanajr/hermes-atlas-evolution --enable [--ref <40-hex commit>]`, `plugins remove hermes-atlas-evolution`), never read from a record. Turning off one of two plugins runs on the owner's key for that one proposal only. The trash move refuses any link in either path and uses `rename`, never a copy. Reading the other profiles never follows a link and never opens anything but a regular file, up to a size limit, so a named pipe or a huge or deeply nested file planted in a profile cannot block or fail the pass; each plugin's Python source is parsed with `ast` and never imported or run. Every automatic action is recorded in the decision history with `automatic` as the actor and can be undone; an undone one is never repeated, whichever profile leads later.

**Who decides.** Only the operator: in their own terminal (the commands, or since 0.8.2 the interactive menu, which opens only where those commands may run), or, since 0.8.1, in the Evolution tab of a dashboard that asks for a login. The panel's decision route accepts a request only from a login Hermes verified or Hermes Desktop's grant, never with the dashboard's session token in any form (its header, `?token=`, `Authorization: Bearer`), which a dashboard without a login hands to any program on the machine, the agent's terminal included, so there the panel stays read-only; the decision is taken only in the dashboard's own process, where Hermes' login gate leaves the session it verified (a session verified by the deployment session token `HERMES_DASHBOARD_SESSION_TOKEN` does not count), and never in a profile's plugin host, which receives no credential from Hermes: the panel of another profile decides through the dashboard's own process, naming that profile, which must have the plugin installed and enabled ([details](docs/hermes-integration.md#the-dashboard-panel)). A decision also needs the header `X-Atlas-Evolution: 1`; **Approve all** decides only on the sentences it showed and never on a lesson the agent proposed; every decision is recorded and can be undone; and the runtime guard vetoes the agent's commands that call the route. Settings changed there or in the menu go through Hermes' public `hermes config set` into `config.yaml`. In the terminal, the menu, `lessons approve`, `retire`, `add`, `review`, `import` and `export`, `decisions undo`, `proposals approve` and `reject`, and the 0.1 notes' `memory remember` and `forget` refuse to run when the environment carries `HERMES_SESSION_ID`, `HERMES_KANBAN_TASK`, `HERMES_DELEGATED_CHILD_CONTEXT` or `ATLAS_EVOLUTION_AGENT`, which the plugin adds to every subprocess of an agent session through `register_session_env`. On Linux they also refuse when a Hermes process is an ancestor of the command or the command runs in the systemd cgroup of a Hermes gateway, both read from `/proc`, so clearing those variables is not enough, and neither is detaching with `setsid` where the gateway runs as a systemd unit; a gateway started some other way leaves no trace a detached command could be traced to. Only the command's own `hermes evolution` launcher, the unbroken chain from the command up, is skipped: a Hermes ancestor further up counts even when its own words include "evolution" (a one-shot `hermes -z "...evolution..."`, a profile named evolution), and so does a virtual environment's `python .../bin/hermes`. A command the agent hands to something that starts it outside its own process tree and environment (`systemd-run`, `at`, a crontab entry, another user's session) leaves no trace either; the runtime guard vetoes the gateway and settings commands scheduled through `systemd-run`, and Hermes' approval policy is the control for the rest. In an agent's terminal, `lessons list` and `proposals list` leave out the sentence of every written lesson: the terminal of a stranger's chat is an agent's terminal too. Activation shows the exact text and asks. This guard keeps the agent from using the plugin's commands; it is not a sandbox. An agent that can run arbitrary commands as the same user could still write the database file directly, and Hermes' own approval policy for terminal commands is the control for that.

**Settings the agent cannot widen.** The agent's file tools (`write_file`, `patch`) need no approval to write `<HERMES_HOME>/evolution/settings.json`; Hermes refuses their writes to `config.yaml` only, and flags terminal writes to it for approval. So a value that would widen whom the plugin trusts or switch a protection off counts only from the Hermes configuration (the plugin settings form, stored in `config.yaml`): `owner_sender_ids`, `owner_platforms`, `agent_advice: true`, `runtime_guard: false`, `legacy_memory_commands: true` and `automatic_shared_recall: true` are ignored in `settings.json`, and `status` lists the keys it ignored. `hermes evolution owner` prints the `hermes config set` command for the owner to run instead of writing anything. The runtime guard vetoes the agent's own `hermes config set` or `unset` of the `plugins` section (which enables, disables and isolates plugins) and of this plugin's settings, leaving other plugins' settings open, its `hermes config edit`, its `hermes plugins disable`, `remove` or `trust` of this plugin and an install over it, the removal of the plugin's own folder, and a terminal write to a Hermes `config.yaml` that names the plugins section, this plugin or one of its trust settings, wherever global options such as `-p <profile>` sit in the command, under every name the `hermes` command runs by (`python -m hermes_cli.main` included), and also when the shell fills in a word there (`$VAR`, `$'...'`, a command substitution). Other options in `settings.json` (the operations supervisor, cost rates, Kanban hand-off) are not part of this boundary.

**Chats with other people.** A turn serves the owner on their own surfaces (CLI, TUI, Desktop, ACP), in their automations, in a subagent delegated from a turn that served the owner (a child of someone else's chat serves that person, and a child whose parent the plugin has not seen serves someone else), or in a chat with a sender listed in `owner_sender_ids`; every other chat, integration or A2A peer serves someone else, and so does a session the plugin has not seen a turn of since it loaded. What someone else does is measured, but it cannot change the owner's prompt: their failures alone never activate a lesson (it waits for approval), they never leave an excerpt for the reflector, a chat that may serve someone else gets template lessons only (fixed text and an identifier-like detail, never operator, reflector or agent text), and the agent tools refuse to answer there. With `owner_sender_ids` and `owner_platforms` empty, every messaging chat counts as someone else's. The 0.1 shared notes, when the owner switched their recall on, are recalled only into turns that serve the owner. One limit remains: Hermes runs cron jobs under the platform `cron`, and the plugin counts automations as the owner's, so a scheduled job created from a stranger's chat (where Hermes offers the cron tool) runs as the owner's automation; turn the cron tool off in chats other people use if that matters to you. A platform listed in `owner_platforms` makes everyone who writes there the owner, so list only a platform nobody else uses. `hermes evolution owner`, which shows the sender ids of each chat channel and prints the command that changes these two settings, is an operator decision: it refuses to run in the agent's terminal like the other decisions, and `status` shows only counts. Changing who is the owner replays the history again under the new settings.

**Approval refusals.** When the user denies a command, an approval times out, no approver is reachable or the context cannot approve, the failure is the class `approval_refused`. It gets no template, no reflector draft and no investigation proposal, so the plugin never teaches the agent to route around the user's decision. The lesson for `blocked_by_policy` tells the agent not to retry or look for another way, and to tell the user.

**The reflector.** On by default since 0.5.0; `reflector: false`, or an invalid value, switches it off. While it is on and `lessons` is not `off`, the hook (and the backfill, for replayed history) keeps one excerpt of the latest error of each untemplated failure of a turn that served the owner: at most 300 characters, passed through Hermes' redactor with `force=True` (so it applies even when the profile turned redaction off) and always through the plugin's masks for URLs, e-mail addresses, paths, long hexadecimal strings, credential prefixes, long numbers and long quoted strings. The excerpt goes to a model through Hermes, under the auxiliary task `evolution_reflector`, with instructions that it is data and not instructions, and the reply must match a JSON schema. A draft is discarded if it fails the lesson text rules, contains `<` or matches the injection filter. Accepted drafts stay quarantined in every mode, `auto` included, because a crafted error message could otherwise reach the agent's prompt. Calls are capped per pass and per day, and each call is counted before it is made, so a crash cannot exceed the cap. The excerpt is deleted once the failure has a lesson, when a draft is declined or discarded, after 14 days (also by the daily prune of the hooks, when no pass runs), or at the next pass with the reflector off.

**The runtime guard.** An agent with a terminal runs as the same user as Hermes, so it can stop the gateway it runs on or delete what that gateway needs. With `runtime_guard` on (the default), a `pre_tool_call` callback vetoes, for terminal-like tools, commands that would stop, restart or kill the gateway (its systemd unit on Linux, under any profile or home suffix, its LaunchAgent on macOS, its Windows service or scheduled task) or the Hermes processes, the agent's `hermes gateway restart` included, which is left to the owner, along with `hermes gateway uninstall`, `start --all`, `run --replace`, `install --force` and `hermes profile delete`, and commands that would delete or move the running interpreter and its environment (also under the name of a link, such as the base interpreter a virtual environment points at), the Hermes source, the Hermes root, the profile, a folder above them or a glob that matches them, and the agent's own `hermes config set|unset` of this plugin's settings and `hermes plugins disable|remove` of this plugin. Where Hermes runs plugins in a plugin host (`plugins.isolation: host`) no `pre_tool_call` is registered at all, because Hermes blocks a tool whose `pre_tool_call` fails and a crashed host would then block every tool; the guard is off there, and `status` says so. The details are in [Hermes integration](docs/hermes-integration.md#the-runtime-guard). The guard is a safety net for these three failure modes, not a sandbox: it looks at the command word of each part of a command, after the shell words and wrappers it knows, ignores here-document bodies, looks one level into a command given as one string (`bash -c`, `su -c`, `eval`, command substitutions, `find -exec`, `ssh localhost`, the strings of `python -c` and similar), protects the inside of the interpreter, its environment, Hermes' packages and the plugin's own folder, and lets any doubt through, such as a command it cannot parse, a command piped into a shell, encoded text, a script file, or a relative path whose folder it cannot know. Since 0.8.0 it was checked against about 350 commands written to get around it ([details](docs/hermes-integration.md#the-runtime-guard)). An invalid `runtime_guard` value keeps it on. Hermes' own approval policy for terminal commands remains the control for everything else.

**The autopilot and the history.** The pass runs in a background thread of each Hermes process, claimed so that only one process of a profile runs it at a time. A clock thread per loaded profile only nudges it, 2 minutes after the plugin loads and then every 10 minutes. The thread binds its own profile's home and secret scope, so in a gateway that serves several profiles a reflector call uses that profile's provider keys and never another profile's. The pass reads Hermes' records, including `state.db` read-only, and writes only the plugin's own database. It runs no command and changes nothing in Hermes, except the automatic actions of `auto_actions` at its end: with `safe` (the default), copies of a memory entry that are the very same text are taken out (a copy of the file is kept); with `full`, also `hermes curator lock` for skills the curator keeps rewriting, at most 3 per pass. Each one is recorded with its undo; an undo is derived again from what was run, never read from the record.

**Other profiles.** `status` reads every profile of the same Hermes root, read-only: the number of sessions in the last 7 days from its `state.db`, whether its `plugins/` folder holds this plugin or the copy under the old id, and, where the plugin has data, the end of its last pass and its lesson counts from the plugin's own database there. It never writes to another profile; it prints the install or migration command for the operator to run.

**Long-running processes.** A gateway or dashboard that loads the plugin records, in the plugin's database of its profile, the plugin version it loaded, its kind and when it started, keyed by its process ID. `status` checks whether each recorded process is still alive with a signal-0 probe, which does not affect the process and runs only on POSIX systems, flags one that runs another version than the code on disk, and deletes the record of one that is gone.

**Owner notices.** At the end of a local session the plugin may return a short notice about decisions waiting. It is shown only on the owner's local surfaces (CLI, TUI, Desktop), never for a subagent and never in a gateway chat, where the other side may be someone else, and it carries counts only. Hermes 0.23.1 shows this text only at the classic CLI's exit or new session and at a TUI or Desktop close, so the plugin returns nothing for any other end and does not spend the day's notice.

## What the plugin stores

Everything is local, under `<HERMES_HOME>/evolution/`. On POSIX systems the folder is created with mode `0700` and the databases with mode `0600`.

| File | Content |
|---|---|
| `evolution.sqlite3` | Daily counters for tools, turns per surface, owner feedback kinds, skill events, the outcome of turns per loaded skill, background reviews, model calls and tokens per provider and model, and native delegation, compaction, Curator and Kanban worker events. Failure signatures: tool name, failure class, a short filtered detail, counts, first and last time seen, and a truncated hash of the last failing session, with a daily count of the failures in the owner's turns. Refused approvals per day by session origin (a label such as `cron` or `telegram`), tool name and the name of the Hermes setting that decided a refusal nobody could answer. The ids of the derived lessons waiting only for the owner's own turns to hit their failure. Lessons, tracked changes with their verdicts, proposals and reading cursors. With the reflector on, one scrubbed error excerpt per untemplated failure, prefixed with the name of the program that failed when the tool ran a command. Counts of the commands the runtime guard vetoed, by kind only. The backfill position and totals, the autopilot lease and the status of the last pass, and the day of the last owner notice. For each gateway or dashboard process that loaded the plugin, keyed by its process ID: the plugin version, the process kind and when it started, deleted once `status` finds the process gone. The radar's last snapshot of the plugins of a process: plugin keys, hook counts and the exception name of a load error; radar proposals also keep the session end reasons as Hermes records them. Maintenance finding codes with their feedback. Hashes that prevent counting one event twice. |
| `supervisor.sqlite3` | Incident codes with the plugin's own hypothesis text, daily baselines, adaptive samples, alert feedback and the journal of systemd trials (unit names, weights and pressure values). |
| `memory-backups/` | Only when you take an entry out of Hermes' memory from the menu or the panel: a copy of the memory file as it was, owner-only (`0600` in a `0700` folder), the latest 100. It holds memory text, as Hermes' own files do. |
| `settings.json` | Written by you; the plugin only reads it. The agent's file tools can write it too, so values that would widen trust are ignored there (see "Settings the agent cannot widen" above). Values set in the Hermes settings form are stored by Hermes in the profile configuration. |

Only when the owner updates or repairs the operating system, as root: `/var/lib/hermes-atlas-evolution/system/<time>-<random>/`, outside every Hermes profile so it never goes into a Hermes backup, the folder and its parent only root's (`0700`; the plugin refuses a folder another user owns or can write). Each run keeps the list of installed packages before and after, a copy of `/etc` before (it may hold secrets of the machine; `0600`), the check before, the packages it holds while it runs, the update's script, log, exit status and report. Every file is created new with `O_EXCL|O_NOFOLLOW`, so a planted link is never followed. The latest 5 runs are kept, never one that may still hold packages.

Text that is stored as written, because someone wrote it on purpose:

- **Lessons.** A sentence of 12 to 240 characters from `hermes evolution lessons add`, the agent's `hermes_atlas_evolution_lessons` or the reflector, checked as described above.
- **Proposal notes.** The optional `--note` of a decision, up to 200 characters.
- **Legacy notes.** Only when `legacy_memory_commands` is enabled: notes saved with the 0.1 commands.

## What the plugin does not store

- Conversation text, prompts or model responses, including those replayed from `state.db`.
- Tool arguments or tool output. Error text is classified in memory and discarded; only the reflector, when on, keeps the scrubbed excerpt described above.
- The commands the runtime guard vetoes. The hash of each terminal command that `pre_tool_call` keeps to tell whether another plugin rewrote it stays in memory, at most 512 at a time, and is never stored.
- Memory content, except the copy of a memory file kept when the owner takes an entry out (see `memory-backups/` above). Native memory files are read to count entries, check their encoding and, in the owner's menu, show what repeats; the decision log keeps a fingerprint of the entry taken out, never its text.
- Raw log lines. From `agent.log` the plugin keeps numbers and a fixed result label.
- Session, turn or request identifiers in clear. They are hashed.
- Paths, URLs or credential-shaped values. A failure detail is kept only when it is a short name of at most 32 characters that passes `signals._clean_hint`, including Hermes' redactor with `force=True`. Tool, skill, provider and model names pass an allowlist, and a name that fails it is stored as `unknown` or dropped.
- Configuration values that are not plain labels. They are stored as a short fingerprint.

Retention is 35 days for observer metrics and 90 days for the evolution loop's aggregates, incidents and closed trials. The guard's daily counts (`guard_daily`), the daily failures in the owner's turns (`failure_owner_daily`) and the refused approvals per origin (`approval_daily`) follow the 90-day retention. The delivery IDs that stop one event from being counted twice (`seen`) are kept 2 days, and reflector excerpts (`failure_sample`) at most 14 days. Lessons are kept, retired and withdrawn ones included, so a lesson id never points to another lesson and a sentence the owner turned down stays down.

## What the plugin reads

Hermes files are opened read-only, with size limits, and the databases with a short deadline. This includes, for `status`, the `state.db` of the other profiles of the same Hermes root, where it only counts sessions, and the plugin's own database in those profiles, where it reads the end of the last pass and the lesson counts. In the profile's own `state.db`, `status` counts the sessions and senders of each chat channel, and `hermes evolution owner`, which only the operator can run, lists the sender ids per channel so the operator can pick theirs; neither stores them. The operations supervisor reads skill files and the start of other plugins' `__init__.py` to find duplicates and provider plugins, keeping only hashes and titles. On Linux, a decision command also reads `/proc` to find its ancestor processes and its cgroup. The list is in [Hermes integration](docs/hermes-integration.md#what-the-plugin-reads).

## What the plugin executes

- **No network connection of its own and no telemetry.** The only model call is the reflector's, on by default, made by Hermes through `ctx.llm` with the provider configured for `auxiliary.evolution_reflector`, which inherits the compression model unless you set another.
- Two background daemon threads per profile loaded in a Hermes process: the clock, which only nudges the pass, and the autopilot, which runs it. Neither executes a command.
- `status` probes whether a recorded Hermes process is still alive with signal 0, which sends nothing to the process, on POSIX systems only.
- The runtime guard executes nothing. It returns a block directive to Hermes, which then does not run the command.
- `systemctl show` for the two units named in `linux_supervisor`, when that policy is configured.
- `systemctl --runtime set-property` on the auxiliary unit, only with `linux_supervisor.mode: "apply"`, under a lock, with the previous value recorded and restored.
- `hermes kanban ... create` with a blocked card, only for `hermes evolution ops handoff` and only with `kanban_handoff.enabled`.
- `hermes --profile <name> config set plugins.entries.hermes-atlas-evolution.settings.<key> <value>`, one per changed setting, only when the owner changes a setting in the panel or the terminal menu, with an argument list (no shell) and a 60-second limit.
- `hermes --profile <name> curator lock|unlock <skill>`, the same way with a 180-second limit, only to apply a lock the owner approved in the menu, the panel or `proposals approve`, to undo it, or, with `auto_actions: full`, to lock a skill the curator keeps rewriting (at most 3 per pass, never one whose automatic lock the owner undid, one Hermes refused only a day later). The skill name must be a plain name (letters, digits, `.`, `_`, `:`, `-`). The undo is always `unlock` of the skill that was locked, derived again from what was run; a skill the owner had locked is left as it is, with no undo recorded.
- `hermes --profile <profile> plugins disable|enable <plugin>` (by the plugin's manifest name) and `plugins install sesantanajr/hermes-atlas-evolution --enable [--ref <commit>]` (undone with `plugins remove hermes-atlas-evolution`), for a profile of the same Hermes root that is a real folder with a `config.yaml`, the same way with a 180-second limit: `disable`/`enable` only on the owner's key for one proposal; the install on the owner's key, or by itself in mode auto in a profile used in the last 7 days that never had the plugin. Each runs only after the profile was read again from disk and the situation is still there.
- `hermes --profile <name> pm doctor`, `doctor`, `doctor --fix` (after `backup --quick --label atlas-evolution`) and `pm gc`, the same way with a 300-second limit, only on the owner's click in the menu or `hermes evolution care`; `pm gc` also by itself in mode auto, at most once a week, when the health check found 300 MB or more of tool versions nothing references. `hermes doctor` calls the configured providers' APIs and pings an endpoint ending in `/anthropic` with a one-token request; the others make no model call.
- `hermes --profile <name> cron create ... --no-agent --script hermes-atlas-evolution-digest.py` (and `cron remove <job>` to undo it), only when the owner schedules the weekly digest; the script, written owner-only under the profile's `scripts/`, runs `hermes evolution learn --notify-only` and `report`.
- Read-only commands of the operating system for the daily check, Linux with apt only: `apt list --upgradable`, `dpkg --audit`, `apt-get -o Debug::NoLocking=1 check` (it takes no lock), `apt-mark showhold`, `uname -r`, `systemctl list-unit-files|list-units|is-active|show` and `loginctl show-user` (for the profile's owner); and it reads `/proc` (process names, memory, the locks held on dpkg's and apt's lock files in `/proc/locks`) and `/etc/os-release`.
- Only when the owner runs the system's update or repair, as root in their own terminal (never the agent, refused in an agent's shell) and only when Hermes' profile and the plugin's code belong to root (otherwise another user could change what root runs): `apt-get update`, a simulation (`apt-get -s`), then `systemd-run --unit=hermes-evolution-os-upgrade-<run> --collect /bin/sh <script>` (`...-os-repair-<run>` for the repair), where the script, written root-only with every path quoted, runs `apt-get -y --with-new-pkgs upgrade` (or `full-upgrade` with `--full`) with `--force-confdef --force-confold` and `NEEDRESTART_MODE=l`, holding the packages the owner chose to leave out (written down first, released by a shell trap when the run ends, fails or receives SIGINT, SIGTERM or SIGHUP, and taken off the list only once `apt-mark unhold` succeeded, tried again for up to 3 minutes while dpkg holds its lock); before it, `dpkg-query` and a copy of `/etc` into the root-only run folder above; and, for the repair, `apt-mark unhold` of the packages a stopped run still held, `dpkg --configure -a` and `apt-get -f install`. Package names reach the script only when they match apt's own rules; any other name is refused. The plugin never reboots the machine.
- An atomic rewrite of `memories/MEMORY.md` or `memories/USER.md`, only when the owner takes an entry out (or undoes that) in the menu or the panel, or, with `auto_actions` `safe` or `full`, to take out a copy of an entry that is the very same text, character for character (never one the owner put back), under Hermes' own memory lock, after a copy of the file is kept.

The cron recipes (`report --schedule-spec` and `ops schedule-spec`) are printed for review. The plugin does not write the script and does not create the job.

Optional packages are used only when you install them yourself: PyYAML lets the standalone runner read `config.yaml`, and a local SentenceTransformers model can be configured for `ops similar`, loaded from local files with remote code disabled.

**The dashboard panel.** The Evolution tab of the Hermes dashboard reads the profile's data through a `GET` route and decides through a `POST` route, both authenticated by Hermes and scoped to the profile on screen, and refused where the plugin is disabled. Only a logged-in owner decides there (see "Who decides" above); everywhere else it is read-only and shows the command of the terminal menu. Everything it shows, lesson text included, is rendered as text, never as markup.

## What reaches the agent

A lesson is text placed in the system prompt of new sessions and, with `tool_hints` on (off by default), in the result of a failing tool call. Treat approving a lesson like editing the system prompt.

- Template lessons vary only in the tool name and the filtered detail. In `auto` mode, the default, a new template lesson reaches the agent at once and is retired when it is measured as ineffective 14 days or more after activation; in `suggest` mode it waits for your approval.
- Lessons from you without `--activate`, from the agent and from the reflector start in quarantine and are never shown before you approve them, in every mode. So do written lessons from a pack you import without `--activate`.
- The agent tools are hidden until `agent_tools` is on.
- With `lessons` set to `off` no lesson surface is registered.
- When the runtime guard vetoes a command, the agent reads the guard's fixed refusal, in the plugin's language, in place of the tool result. It names the protected path, or tells the agent to ask the owner, who runs `hermes gateway restart` from their own terminal.
- Owner notices are shown to the owner outside the conversation. They do not reach the agent and never start a turn.

## Verification status

The plugin is covered by unit and end-to-end tests against a simulated Hermes context, including tests that assert sensitive-looking input is absent from the stored rows, also for history replayed from `state.db`, that decisions refuse to run with agent markers, that every approval refusal text of Hermes 0.23.1 is classified as `approval_refused`, that the runtime guard vetoes the known commands, lets ordinary administration through and never raises, and that a profile with the copy under the old id registers nothing. It passes `hermes plugins validate` on Hermes Agent 0.23.1, with the security scan reporting it safe. In production, three real reflector calls through Hermes produced three drafts. The autopilot is verified in tests and in the CLI, and its clock and the stale-process check in tests. The test suite runs in CI on Linux with Python 3.11 to 3.14 and on real macOS and Windows runners (where POSIX-only tests are skipped); the plugin has not run inside a Hermes gateway on macOS or Windows yet. The loop went through an independent review before the 0.4.0 release, and 0.8.0 fixes what three independent reviews of 0.7.0 found (security, compatibility with Hermes 0.23.1, the learning loop), each with a test that fails without its fix. It has not been audited by a third party, and lesson verdicts have not been observed over weeks of real use yet.
